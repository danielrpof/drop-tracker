<objective>
Bound `detectDeluxeChanges`'s per-cycle MusicBrainz fetch loop to release-groups that are still plausibly able to gain a deluxe/reissue edition, by skipping the `ReleasesByReleaseGroup` call for any already-seen release-group whose `FirstReleaseDate` falls outside a rolling window (default 90 days).

Purpose: `detectDeluxeChanges` currently calls `ReleasesByReleaseGroup` for EVERY release-group in an artist's `preCycleSeen` set, every poll cycle (default 15m), forever, with no cap and no age check. It is the single largest unbounded consumer of the shared, process-wide MusicBrainz `rate.Limiter` (1 req/sec, burst 1). That same limiter serves interactive artist search (`GET /search`) and artist-art lookups, so search requests queue behind this bulk traffic and hit the client's 10s timeout before their turn, surfacing as "MusicBrainz unavailable". Old, already-released albums' tracklists essentially never change, so the vast majority of those requests buy nothing.

Output: one named constant, one pure prefix-comparison helper, one gate inside the existing loop, one aggregate log field, and tests pinning the skip, the check, the undated-defaults-to-check policy, and the inclusive boundary.

Explicitly OUT of scope (do not touch): `deluxeDetectionEnabled`'s per-artist opt-in semantics, `advanceGroupBaseline`'s atomicity contract, the event-insertion logic and its documented accepted-edge ordering, and `detectGuestFeatures`'s `maxNewGuestFeatureLookupsPerCycle` cap.
</objective>

These were confirmed by reading the code during planning. Trust them; do not re-derive.

1. **`freshGroups` already carries the date.** `detectDeluxeChanges(ctx, logger, entry, freshGroups []musicbrainz.ReleaseGroup, preCycleSeen, notifiedAt)` receives the same `groups` slice `DetectMusicBrainz` was handed, and `musicbrainz.ReleaseGroup` has a `FirstReleaseDate string` field (`internal/musicbrainz/releasegroups.go:46`). The gate needs **no new DB column, no new sqlc query, and no extra HTTP request**.

2. **`FirstReleaseDate` is an opaque partial date.** MusicBrainz returns `""`, `"2020"`, `"2020-06"`, or `"2020-06-15"`. The package's standing doctrine (`ReleaseGroup`'s own doc comment, `Release.Date`'s, `earliestReleaseDate`'s) is: **never parse these into `time.Time`** — doing so either fails or invents a month/day that downstream logic then treats as real data. The gate must therefore compare strings, not times.

3. **`earliestReleaseDate` already establishes the `len < 4` malformed-date guard** (musicbrainz.go:578, added as WR-01 in 13-REVIEW.md): a date under 4 characters is malformed and is treated as absent. Mirror that threshold rather than inventing a new one.

4. **Every existing deluxe test already leaves `FirstReleaseDate` at its zero value.** Verified: `detector_test.go` contains exactly three `FirstReleaseDate` literals (lines 185, 186, 296), all in `new_release` tests; every `TestDetectMusicBrainz_DeluxeChange_*` fixture builds `musicbrainz.ReleaseGroup{MBID: ..., Title: "Album", PrimaryType: "Album"}` with no date. Under the "undated → still check" policy, **all of them keep passing with zero fixture edits.** If a pre-existing deluxe test starts failing, the undated policy has been implemented backwards — fix the policy, do not edit the fixture.

5. **`internal/poller/poller_test.go` is unaffected** — its comment at line 90-92 records that every release-group those tests fetch is brand-new within its own cycle, so the deluxe pass never calls `ReleasesByReleaseGroup` there at all.

6. **`go.mod` declares `go 1.26`**, so the `min` builtin and `time.DateOnly` are both available.
