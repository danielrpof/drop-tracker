<objective>
Implement the local half of CICD-10: a gitleaks pre-commit hook so secrets are caught on this
machine before they can ever become a commit object, and prove the existing history is clean.

CLAUDE.md states "gitleaks enforced in pre-commit and CI", but no `.pre-commit-config.yaml` exists
and `.git/hooks/` contains only Git's stock `.sample` files — the constraint is currently
unimplemented. This plan closes the pre-commit half. The CI half (CICD-02, the
`gitleaks/gitleaks-action` backstop) stays in Phase 07 and is deliberately out of scope here, as is
the golangci-lint hook that makes up the other half of CICD-10.

Second purpose: this repo has 86 commits, 39 of them not yet pushed to origin/main. Task 2 runs a
pinned gitleaks scan across the entire history as a failsafe before the session decides whether to
push.

Purpose: stop a leaked credential at the cheapest possible point (pre-commit), and get an
evidence-backed yes/no on whether the unpushed history is clean.
Output: `.pre-commit-config.yaml`, an installed and behaviourally-proven git hook, a zero-finding
full-history scan, and a `make hooks` + README path so a fresh clone reproduces it.

Infrastructure only — no application source code (`cmd/`, `internal/`, `queries/`) is touched.
</objective>

Wire the full path — config file, framework, git hook shim, real blocked commit — in one slice.

Write `.pre-commit-config.yaml` at the repo root with a single `repos` entry: repo
`https://github.com/gitleaks/gitleaks`, `rev` pinned to the v8.30.1 tag, one hook with
`id: gitleaks`. Do not add extra args, `exclude` patterns, or a `.gitleaksignore` — the stock hook
entry already carries `--redact --staged`, and any exclusion added before the baseline scan in
task 2 would hide exactly what that scan is supposed to find. Add a short header comment saying
this mirrors the Phase 07 CI gitleaks job (CICD-02) and that the golangci-lint hook (the other
half of CICD-10) is intentionally deferred to Phase 07, so a later reader does not read its
absence as an oversight.

Install the framework for the current user with `python -m pip install --user pre-commit`. Then
use the module form `python -m pre_commit ...` for every subsequent invocation rather than a bare
`pre-commit` — pip's `--user` scripts directory on this box
(`%APPDATA%\Python\Python314\Scripts`) is not guaranteed to be on PATH, and the module form
sidesteps that entirely. Record the resolved pre-commit version from
`python -m pre_commit --version` for the summary.

Install the hook with `python -m pre_commit install --install-hooks`. Use `--install-hooks` so the
golang hook environment (which compiles gitleaks from the pinned tag) is built now rather than
ambushing the next real commit with a multi-minute build.

Now prove it actually fires, which is the whole point of the slice. Generate a throwaway
AWS-access-key-shaped string at runtime — never write a complete secret-shaped literal into any
file that gets committed, including this plan, the config, or the SUMMARY:

  KEY=$(python -c "import secrets,string; print('AKIA'+''.join(secrets.choice(string.ascii_uppercase+string.digits) for _ in range(16)))")

Write it into `tmp-gitleaks-selftest.txt` as an `aws_access_key_id = "..."` assignment, `git add`
it, and attempt a real `git commit`. The commit MUST fail and `git rev-parse HEAD` MUST be
unchanged. Generating the value randomly at runtime matters: hard-coded documentation example keys
appear in gitleaks' own allowlists in some releases and would produce a false pass.

Then clean up completely — `git restore --staged tmp-gitleaks-selftest.txt`, delete the file, and
confirm `git status --porcelain` is empty. Note for your own peace of mind: `git add` did write an
unreachable blob into `.git/objects`, but no commit object references it, it is not in history, it
is never pushed, and normal git GC prunes it. `gitleaks git` scans commits, not dangling blobs, so
it will not show up in task 2. Do not run `git gc` — it is unnecessary churn.

Finally commit `.pre-commit-config.yaml` on its own. This commit passing is the other half of the
proof: the hook blocks secrets without blocking ordinary work.

Never paste the generated key value into a commit message, the SUMMARY, or any log you keep. The
hook's `--redact` flag already masks it in gitleaks' own output.
  </action>
  <verify>
    <automated>
set -e
BEFORE=$(git rev-parse HEAD)
test -f .pre-commit-config.yaml
grep -vE '^[[:space:]]*#' .pre-commit-config.yaml | grep -q 'v8.30.1'
grep -vE '^[[:space:]]*#' .pre-commit-config.yaml | grep -q 'id: gitleaks'
test -f .git/hooks/pre-commit
grep -qi 'pre.commit' .git/hooks/pre-commit
KEY=$(python -c "import secrets,string; print('AKIA'+''.join(secrets.choice(string.ascii_uppercase+string.digits) for _ in range(16)))")
printf 'aws_access_key_id = "%s"\n' "$KEY" > tmp-gitleaks-selftest.txt
git add tmp-gitleaks-selftest.txt
if git commit -m "chore: gitleaks selftest (must be blocked)"; then echo "FAIL: hook did not block a staged secret"; exit 1; fi
git restore --staged tmp-gitleaks-selftest.txt
rm -f tmp-gitleaks-selftest.txt
[ "$(git rev-parse HEAD)" = "$BEFORE" ] || { echo "FAIL: HEAD moved during a blocked commit"; exit 1; }
[ -z "$(git status --porcelain)" ] || { echo "FAIL: working tree dirty after cleanup"; exit 1; }
echo "PASS: staged secret blocked, HEAD unchanged, tree clean"
    </automated>
  </verify>

<task type="auto">
  <name>Task 2: Scan all 86 commits of history with pinned gitleaks — zero findings required</name>

  <action>
The pre-commit hook only ever sees *future* staged changes. Nothing so far has looked at what is
already in the 86 existing commits, 39 of which have not reached origin/main. This task is that
second failsafe, and it must run before any push decision.

Install the pinned scanner: `go install github.com/zricethezav/gitleaks/v8@v8.30.1`. Use the
`zricethezav` module path, not `gitleaks/gitleaks` — the latter fails with a module-path-mismatch
error even though the repository now lives under the `gitleaks` org. Installing a versioned
`module@version` argument does not touch this project's go.mod or go.sum; assert that rather than
assume it. The binary lands at `C:\Users\danie\go\bin\gitleaks.exe`; invoke it by absolute path
built from `go env GOPATH` instead of relying on PATH.

Assert the installed version reports 8.30.1 before trusting any result — a scan from an unexpected
version tells you nothing about the pinned ruleset.

Run `gitleaks git --no-banner --redact -v .` from the repo root. The `git` subcommand walks the
full commit log by default; do not narrow it with `--log-opts`. Keep `--redact` so any finding is
masked in the output. Exit code 0 means no leaks; 1 means leaks *or* an error, so read the output,
do not just trust the code.

Do not use `gitleaks dir` here. It scans the working tree including gitignored files, so a
legitimately-local, never-committed `.env` would surface as a finding and muddy the signal. The
question this task answers is specifically "is the committed history clean".

**If there are any findings, STOP.** Report them (redacted — never paste a matched value into the
SUMMARY or a commit message) and do not push. Explicitly do NOT create a `.gitleaksignore`, a
`--baseline-path` file, or an `exclude` rule to make the scan green. A finding here is precisely
the signal this task exists to produce; suppressing it silently defeats the entire exercise and
would also blind the Phase 07 CI job that will run the same scan.

Record the scanned commit count and the clean result for the SUMMARY. There are no file changes in
this task, so there is nothing to commit.
  </action>

    <automated>

"$GITLEAKS" git --no-banner --redact -v .

echo "PASS: full history scanned by pinned gitleaks with zero findings; go.mod/go.sum untouched"
