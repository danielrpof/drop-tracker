# Phase 26 post-discuss grill decisions (2026-10-11)

Source: a grill-with-docs session after `/gsd-discuss-phase 26` and `/gsd-ui-phase 26`. These decisions are locked. They override 26-CONTEXT.md and 26-UI-SPEC.md where the two differ (grill overrides discuss). Amend the docs; don't rewrite them wholesale.

| # | Decision | Doc impact |
|---|----------|------------|
| Q1 | **Derived selection.** Keep `selectedIds` intact. The effective selection is `selected ∩ visible`, where visible is the same `selectVisible(entries, {...view, q: query}, stickyIds)` the list renders. A selected artist hidden by a filter stays selected but is inert until shown again. Any bulk action, and Clear, empty the entire selection, hidden artists included. Reason: `visible` changes per keystroke (`query` local state), so destructive pruning would drop selections while typing. | Rework D-11 and the UI-SPEC "Selection model" Pruning bullet ("a pruned artist does not come back" is gone). The announcement says "{k} selected" over the effective selection. Update the UI Considerations rows that mention pruning. The bar count and select-all state use the effective selection. |
| Q2 | Bulk endpoints return the **outcome only**: `{applied: number[], skipped: {id, name?, reason: "cap"\|"gone"}[]}`, plus the carried count for remove-tag. The client **always** calls `refresh()` after a bulk success and re-derives from it. No `entries` in the response. Reason: avoids a third copy of the heavy ListWatchlist projection, and keeps `tags` from importing `watchlist`. | D-04 and the UI-SPEC Data Contract drop `entries`. The interaction steps change "merged from the response's entries" to "refresh(); mark applied ids sticky". `refresh()` is no longer conditional on `gone`. |
| Q3 | **Bulk add-tag mechanism**, one transaction: (1) GetOrCreateTag; (2) `SELECT id FROM artists WHERE id = ANY(...) ORDER BY id FOR NO KEY UPDATE`, which takes the trigger's lock early and in a fixed order, so no snapshot race and no deadlock; (3) count links per artist and insert only where count < 10 or the link already exists, `ON CONFLICT DO NOTHING`; the ADR 0004 trigger stays as the backstop. If **zero** links were inserted, **roll back**, so the tag created on the fly doesn't become an orphan (honours 24 D-29). Tests: concurrent overlapping bulk attaches don't deadlock; a new tag with every artist at the cap leaves no tag row. Amend ADR 0004 (ordered pre-lock for bulk insert) during implementation. | Pin it in D-01. Add the tests to the D-01 text or a new decision. Note the ADR 0004 amendment as an implementation task. |
| Q4 | Removing an artist **does not** withdraw its pending events. Already-detected alerts are still delivered, by real-time flush or the next digest. The outbox (`ListPendingEvents`) has no watchlist join. Phase 26 keeps this behaviour and discloses it. | D-17 and the UI-SPEC remove-confirmation description add a clause stating that alerts already found for them may still be sent. Add a deferred idea: withdraw pending events on remove (single and bulk). Also create a pending todo under `.planning/todos/pending/` in the existing todo format. |
| Q5 | A new narrow `httpserver.WatchlistBulkStore` interface, implemented by `*watchlist.Service` and wired by a `WithWatchlistBulk` option (503 when absent, like `WithTags`/`WithSettings`). Bulk tag add/remove are methods on `tags.Service` and are exposed through `TagStore`. `watchlist.Store` is **not** extended, so the poller and handler stubs stay untouched. | Add as a new decision in CONTEXT (Implementation Decisions / Integration Points). |
| Q6 | Bulk remove = **one** `DELETE FROM watchlist WHERE id = ANY($1) RETURNING id`, with **no** explicit transaction. Nothing references `watchlist` by foreign key, so the single statement is all-or-nothing. Requested ids that aren't returned are `already_gone`. | Reword D-03's "rolls back the whole transaction" to the single atomic statement. Note: do not add a transaction "for safety". |
| Q7 | Drop D-04's "Phase 27 reuses this shape" commitment. Phase 27 confirms by external id and has different skip reasons, and it may choose to reuse the shape. The ROADMAP Phase 27 "Depends on" line was **already amended**. | Edit the D-04 sentence and the UI-SPEC Data Contract comment "Phase 27's confirm step reuses the shape". |
| Q8 | **Preferences delta** = one set-based statement: a CTE that locks the target ids `FOR UPDATE`, then updates only rows whose arrays actually change (`IS DISTINCT FROM`). applied = every locked (existing) id; gone = requested minus locked. Each axis is rebuilt in **canonical order** (the `ReleaseTypes`/`EventTypes` order that `normalizeSet` uses), as current ∪ set minus unset. **400** when a type is in both set and unset on one axis, when a type is unknown, or when all four lists are empty (mirrors `ErrNoPreferencesSupplied`). | Extend D-05/D-08. |
| Q9 | Unchecking "Select all visible" clears **only the visible selected** artists; hidden selections stay. Clear and every bulk action empty everything (Q1). | UI-SPEC "Select all visible" bullet and the Clear bullet. |
| Q10 | Bulk remove-tag targets a **tag id**. A tag that doesn't exist (concurrently deleted or merged) → **404** `tag not found` → failure toast + `refresh()`. | Settles the CONTEXT "Claude's Discretion" bullet on id vs name. Add the 404 case to the UI-SPEC bulk remove-tag flow. |
| — | The id-count `{max}` cannot be a constant shared between Go and TS. The server's 4xx response is the source of truth; the client may mirror the number but must not rely on it. | UI-SPEC Data Contract `limits.ts` bullet. |

Also already done in this session (do not redo): CONTEXT.md glossary gained **Selection** and a Pending-event sentence; ROADMAP Phase 27 Depends-on was amended.
