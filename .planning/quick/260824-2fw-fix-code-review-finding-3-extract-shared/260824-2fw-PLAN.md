<planning_findings>
Verified during planning by reading `internal/httpserver/watchlist.go` in full and `internal/httpserver/watchlist_test.go`'s tests and stub types -- the executor should act on these, not re-derive them:

- **The five call sites are not textually identical in structure.** mbid and name are trimmed together, then a single combined blank check (`if mbid == "" || name == ""`) fires before either field's own length check runs; only after that does each field get its own `utf8.RuneCountInString(...) > maxNRunes` check and its own `writeError` call. The three optional fields (`req.DeezerID`, `req.Disambiguation`, `req.ImageURL`) are each guarded by `if req.Field != nil`, trim the dereferenced value, length-check it, `writeError` and return on violation, and on success reassign the pointer to the trimmed value's address. The shared mechanics across all five is exactly: trim, then report whether the trimmed value's rune count is within a caller-supplied max. Everything else (the blank check, which error message, which status code, whether the field is a plain string or an optional pointer) stays caller-side.
- **Helper shape:** `func trimAndCap(v string, maxRunes int) (trimmed string, withinLimit bool)` -- trims `v`, returns the trimmed value plus whether its rune count is `<= maxRunes`. This shape lets the mbid/name call site get both the trimmed value (needed for the blank check, which must still run before either length check, unchanged) and the bounds bool in one call, and lets each optional-field call site do `v, ok := trimAndCap(*req.Field, maxFieldRunes)` and reassign `req.Field = &v` only on the `ok` branch -- both call shapes stay a two-line change, no awkward multi-return unpacking or a pointer-mutating signature.
- **Ordering must not change.** Today mbid/name are trimmed and blank-checked *before* either field's length check runs. Calling `trimAndCap` for both fields first (to get their trimmed values for the blank check) and only branching on the returned `withinLimit` bools afterward, in the same mbid-then-name order the length checks already run in, reproduces this exactly -- `trimAndCap` itself never writes a response or returns early, so computing both bools before the blank check is a no-op change in observable behavior.
- **`internal/httpserver/watchlist_test.go` never reaches into any unexported symbol this refactor touches.** It exercises `handleAddWatchlist` only through real HTTP requests against `httpserver.New(...)`'s router (`stubStore`/`noopPinger` are the test's own file-local doubles for the exported `watchlist.Store`/`httpserver.Pinger` interfaces, not touched by this refactor) and asserts on status codes, response JSON bodies, and a `called bool` flag on the stub store's `addFunc`. No test references `trimAndCap`, `maxMBIDRunes`, or any other symbol by name. The file needs zero edits.
- **`handleUpdateWatchlist` does not share this idiom.** Reading it directly: it decodes the PATCH body into `updateWatchlistRequest` and forwards straight to `s.watchlist.UpdatePreferences` -- no trim, no rune count, no length cap anywhere in that handler. It is out of scope for this refactor and must not be touched.
- Module path is `github.com/danielrpof/drop-tracker`; no new imports needed (`strings` and `unicode/utf8` are already imported), no `go.mod` changes, no new files. This is a same-file, same-package, behavior-preserving refactor confined to `internal/httpserver/watchlist.go`.
</planning_findings>
