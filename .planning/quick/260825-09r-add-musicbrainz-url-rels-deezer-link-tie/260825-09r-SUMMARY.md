# Quick Task 260825-09r: MusicBrainz url-rels Deezer Link (Tier 0) and Alias Retry (Tier 1) Summary

**`artistart.Matcher.Match` now resolves a watchlisted artist's curated MusicBrainz->Deezer link before any name search (Tier 0), and retries the unchanged strict name-match pipeline over MusicBrainz aliases when the primary name finds nothing (Tier 1) -- both wired into production via a new `WithArtistLinks` option.**

- **Tasks:** 3
- **Files modified:** 7 (4 created, 3 modified)

## Accomplishments
- `musicbrainz.Client.LookupArtist` fetches an artist's curated `url-rels` and `aliases` in a single `inc=url-rels+aliases` round trip, so Tier 1's alias retry never costs a second MusicBrainz request
- `deezer.Client.ArtistByID` confirms a single Deezer artist by id, routing through the existing `decodeChecked` helper so a pulled/renumbered artist page (Deezer's HTTP-200 in-body error) surfaces as a real `*APIError` instead of a zero-valued success
- `artistart.Matcher.Match` gained Tier 0 (a curated `free streaming`/`streaming` url-rel to a `deezer.com` artist page resolves without any Deezer name search) and Tier 1 (the identical strict pipeline retried over prioritized, deduped, bounded MusicBrainz aliases when the primary name finds zero candidates)
- `NewMatcher` widened with a trailing `opts ...Option` parameter (`WithArtistLinks`, `WithLogger`) so all 25 pre-existing call sites compile and pass unchanged; `cmd/server/main.go` is the one production site now passing `WithArtistLinks(mbClient, dzClient)`
- Every absorbed failure path (MusicBrainz lookup error, Deezer confirm error, per-alias search error) degrades to the pre-existing behavior and is logged at debug level -- none of them can turn a clean fail-closed into a `Backfill` `Errored` outcome (D-12's cooldown stays intact)
