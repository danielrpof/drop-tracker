<objective>
Add two new matching tiers inside `artistart.Matcher.Match`, ahead of and behind the
existing strict name-equality rule, without changing that rule or the method's
signature.

- **Tier 0 (before the Deezer name search):** read MusicBrainz's curated
  `url-rels` for the artist; if a `free streaming`/`streaming` relation points at a
  `deezer.com` artist page, take that Deezer artist id as an authoritative identity
  claim, confirm it still resolves via Deezer, and return it.
- **Tier 1 (after the name search finds zero candidates):** re-run the *identical*
  strict pipeline against the artist's MusicBrainz aliases before falling closed.

Purpose: today `Match` only ever asks Deezer "who is named this?", so any artist whose
Deezer display name differs from their MusicBrainz name falls closed forever and their
`artists.image_url` stays NULL. MusicBrainz already stores a human-curated link to the
exact Deezer artist page for many artists; not reading it is the single largest
avoidable source of D-09 fail-closed outcomes.

Output: two new external-client methods, two new consumer-declared seams on `Matcher`,
and the retiered `Match` -- with `Match(ctx, mbid, name) (Result, error)` and both call
sites (`watchlist.Service.Add`, `artistart.Backfill`) untouched.

Explicitly NOT in this plan: Tier 2 (fuzzy/corroborated matching), any change to
`normalizeArtistName`/`titlesMatch`/`tieBreak`/the fail-closed default, any DB schema or
migration change, any new Go module.
</objective>

<design_decisions>
Three judgment calls the brief left open, decided here so the executor does not re-derive them:

**DD-1 -- Confirming Deezer call: YES (brief item 4).** Tier 0 makes the confirming
`GET /artist/{id}` call. Without it, a Tier 0 hit would return `Matched: true` with
`DeezerID` set and `ImageURL` nil, which is a *bad steady state*: `Backfill` would write
the row, record the attempt, and `ListArtistsMissingImage` (predicate `image_url IS NULL`)
would keep re-selecting that artist every 24h forever, each sweep re-walking Tier 0 and
again producing no image. The confirming call is also the only way to notice a
pulled/renumbered Deezer artist page, which Deezer signals as an HTTP-200 in-body error
that `decodeChecked` already surfaces. Cost is one extra rate-limited Deezer request on
the Tier 0 path only, which *replaces* the `SearchArtists` request that path skips -- net
zero.

**DD-2 -- Wiring via variadic options, not a wider constructor.** `NewMatcher` has 25
existing call sites (1 production + 24 test). Widening it positionally would churn all of
them and force every existing test to be edited, which directly conflicts with the brief's
"confirm existing test cases still pass unchanged." A trailing `opts ...Option` parameter
keeps every existing call compiling and running byte-identically (both tiers no-op when the
seams are nil), and confines the production change to one line in `main.go`. The tradeoff
is real and must be mitigated: an unwired production path would make this whole plan a
silent no-op with a fully green test suite. That is why the `main.go` wiring has its own
grep gate in `<verification>` and is called out as this plan's key link.

**DD-3 -- Alias retry fires ONLY on zero strict candidates, never on an ambiguous tie.**
The brief specifies the zero-candidate case. An *ambiguous* tie (2+ same-normalized-name
Deezer artists that the tie-break could not resolve) is a deliberate D-09 stop, not a
"we found nothing" -- retrying under a different name string there would quietly convert a
considered fail-closed into a second guess. So `matchNameStrict` returns the strict
candidate count alongside the `Result`, and alias retry is gated on `count == 0`.
</design_decisions>
