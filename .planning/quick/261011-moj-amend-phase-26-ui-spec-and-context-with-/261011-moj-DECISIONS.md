# Phase 26 UI review amendments (2026-10-11)

Source: a `ui-ux-pro-max` review of `26-UI-SPEC.md` and `26-CONTEXT.md` (risks R1, R2, R4, R8). The user accepted alternatives 1–3. These decisions are locked. They amend 26-UI-SPEC.md, and 26-CONTEXT.md where noted, wherever the docs differ. Amend in place; don't rewrite the docs wholesale. Keep the existing grill amendments (Q1–Q10) intact.

| # | Decision | Doc impact |
|---|----------|------------|
| U1 | **Surface lifecycle and focus ordering.** `ConfirmDialog` for bulk remove is rendered by `web/app/routes/watchlist.tsx` (route level), **not** inside `BulkActionBar`. The bar's `Remove` only opens it, and the route passes a ref to the bar's `Remove` button. On every bulk success the order is: (1) the surface closes (dialog `onOpenChange(false)`, popover closed, or inline mode exited); (2) then `selectedIds` is emptied, which unmounts the bar; (3) then focus moves to the fallback-chain target in an effect that runs after the bar has unmounted (e.g. a `pendingFocus` flag consumed by `useEffect`). Never clear the selection inside `onConfirm` before the dialog has closed. On failure, `ConfirmDialog`'s `finalFocus` is the bar's `Remove`; on success it is the fallback target. Pick the ref when the dialog closes, not when it first renders. Reason: `ConfirmDialog.handleConfirm` calls `onOpenChange(false)` only after `onConfirm` resolves, so a dialog inside the bar unmounts first and focus lands on `<body>`. | UI-SPEC: Inventory row for `ConfirmDialog` (route-level host), the Bulk remove flow, the Focus management table and fallback-chain paragraph, and the Bulk add tag and Preferences success steps (same close → clear → focus order). The scope bullet that says the bar "hosts … the Remove trigger for ConfirmDialog" now says the bar hosts the trigger and the route hosts the dialog. CONTEXT: one sentence under D-16 that the dialog is hosted at route level. |
| U2 | **Focus is never hidden by the bar (WCAG 2.4.11).** While the bar is mounted, `html` gets `scroll-padding-bottom: var(--bulk-bar-clearance, 0px)`. Declare it once in `web/app/app.css` on `html`; with the variable unset it resolves to 0, so other pages are unaffected. Keyboard focus moved to a card checkbox near the bottom of the viewport then scrolls clear of the bar. | UI-SPEC: Spacing "Page bottom clearance" exception and the Layout section. Add a UI Considerations row (overflow/focus, B1/B3, ✅ covered) and a UAT verification item: "Tab through card checkboxes with the bar visible: the focused checkbox is never behind the bar." |
| U3 | **One-row phone action bar.** Below `sm` the bar is a single row: `[{N} selected] [TagPlus] [TagX] [Sliders] [Trash2] [X]`. The count is `min-w-0 flex-1` (visible text `{N} selected`, `tabular-nums`). The five controls are icon-only `size-11` (44px) ghost buttons, with `gap-1` between items below `sm`. Clear becomes icon-only `X` below `sm`, with `<span class="sr-only sm:not-sr-only">Clear</span>`, `aria-label="Clear selection"` unchanged, and `title="Clear selection"`. Clear keeps its visible text at `sm` and up. To make it fit, the phone wrapper inset shrinks from `bottom-4 px-4` to `bottom-2 px-2`; it stays `sm:bottom-6 sm:px-8`. Width check at 375px: bar 359, minus `p-2` = 343 inner; 5 × 44 + 5 × 4 gaps = 240, which leaves 103px for the count (fits `1000 selected`). **Inline mode below `sm`:** the four action icons hide and the picker row `[input flex-1] [Cancel]` renders as a second row under `[count … Clear]`; the bar returns to one row when inline mode exits. Desktop (≥ 640px) layout is unchanged. Reason: the two-row bar used ~130px (~20%) of a 667px phone viewport; one row uses about 60px. | UI-SPEC: Spacing table (`sm` gap and inset rows, the 8px bar inset below `sm`), Control sizes, the Action bar "Phone" block (replace the two-row diagram), Wrapper classes, Inline mode paragraph, the copy row "Clear (visible / aria-label)", the B3 375px backstop row (now one row, 4-digit count fits), and the B3 populated row. CONTEXT D-10: append "one row at phone width (icon-only actions)". |
| U4 | **Undo on the bulk remove-tag success toast.** The `Removed “{tag}” from {n} artist{s}.` toast gains an `Undo` action (sonner `action`), and its duration rises to 8000ms. Undo sends **one** bulk add-tag request with the tag's **name** and the remove response's `applied` ids, through the same bulk add-tag endpoint (normalization, get-or-create, cap rule D-01). Undo does not touch the current selection (a new selection may exist) and does not mount the bar. While it is in flight there is no extra UI; on success `refresh()` runs, the restored ids are marked sticky, and a toast `Restored “{tag}” on {n} artist{s}.` fires (`toast.success`). Cap skips (only possible if the user added other tags in between) reuse the add-tag partial copy: `toast.warning`, 8000ms, description `{k} already {has/have} 10 tags: {names}.`. On failure: `toast.error` `Couldn't restore “{tag}” — try again.`. Undo is offered only when `applied` is non-empty. Bulk remove of artists keeps D-15 (no Undo). Reason: the selection clears after the action (D-14), so "reversible" otherwise means rebuilding the selection by hand. | UI-SPEC: Bulk remove tag flow (add an Undo step), Toasts table (amend the remove-tag row; add the restore success, partial and failure rows), the "Deliberately NOT used" Undo bullet (clarify that it applies to artist removal only), and a UI Considerations row (B8 undo, ✅ covered). Data Contract: note that the remove-tag response's `applied` is reused for Undo. CONTEXT: under D-15, add "Bulk remove-tag offers Undo (re-add by name to `applied` via bulk add-tag); this does not reverse D-15, which covers artist removal only." |
