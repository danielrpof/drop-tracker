Add `csrfHeaderName` and `csrfHeaderValue` constants to `internal/authgate/gate.go` holding exactly
the header name and value that `web/app/lib/api.ts` sends. Add a comment recording that these two
literals are a contract with the client and that changing one without the other silently breaks every
state-changing request.

Add `RequireCSRFHeader` as a method on `*Manager` returning a `func(http.Handler) http.Handler`
closure shaped like `Authenticate`. It passes straight through for the safe methods — GET, HEAD and
OPTIONS — and for every other method requires the custom header to be present with the expected
value, rejecting otherwise with 403 and the fixed body naming a missing required header. Use the
existing `writeJSONError` helper so the shape matches everything else the package returns. Document
why this works: a cross-site attacker can trigger a form POST but cannot set a custom request header
without a CORS preflight, and this server sends no CORS headers at all, so the preflight is denied —
`SameSite=Lax` and this header are two independent controls covering each other (D-15).

Register it inside the protected group in `internal/httpserver/server.go` with a second `pr.Use`
placed after the `Authenticate` registration, so a request is authenticated before it is judged on
the header and an unauthenticated request still gets 401 rather than 403. Both registrations live
inside the same conditional branch, so the inert path installs neither.

Apply the same check at the top of `HandleLogin`, before the throttle, before the body is read, and
before any comparison — this closes login-CSRF, which is the case `SameSite=Lax` alone does not cover
because a login POST is exactly what an attacker wants to force. A rejection here must not increment
the global failure counter and must not consume a token from the per-IP limiter. `HandleLogout` gets
the same check for symmetry.

Add the Referrer-Policy response header. Set it once for every response rather than only on the
session routes: a small middleware registered on the root router alongside the existing four, or a
header set inside `echoRequestID`'s existing closure — choose the one that keeps the existing four
`r.Use` lines byte-for-byte unchanged, and state which you chose and why in the SUMMARY. The value is
the no-referrer policy. This prevents a passphrase-bearing URL from ever leaking through a Referer
header, which is defence in depth given the passphrase already never enters a URL.

Write the tests first. In `internal/authgate/gate_test.go` cover a gated POST, PATCH and DELETE with
and without the header, a gated GET without it, and a HEAD or OPTIONS without it. In `login_test.go`
cover `POST /session` without the header returning 403, asserting with a fake Alerter and a shrunk
threshold that the global counter did not move, and `POST /session` with the header still working. In
`internal/httpserver/server_test.go` add an inert-path case asserting no route returns 403 for a
missing header, and a case asserting the Referrer-Policy header is present on a gated response and on
an inert response alike.

  <behavior>
    - An empty string returns not-weak: unset means the gate is disabled, which is a configuration state rather than a weak passphrase.
    - A value shorter than 16 runes returns weak with a reason naming the length.
    - A value of 16 runes or longer that is not on the denylist returns not-weak.
    - A denylist match returns weak with a reason naming a known default, and the comparison is case-insensitive and ignores surrounding whitespace.
    - The `.env.example` placeholder value is on the denylist and therefore returns weak.
    - Rune counting, not byte counting, decides length, so a 16-character multi-byte value is not reported as short.
    - The returned reason never contains the input value or any substring of it.
    - Booting with a weak passphrase logs exactly one WARN line and the process continues to the next boot step.
    - Booting with a strong passphrase logs no such line.
    - Booting with no passphrase logs no such line.
  </behavior>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Hostile third-party page → gated state-changing routes | A cross-site form POST rides the user's cookie; only a header the attacker cannot set distinguishes it from the real SPA. |
| Hostile third-party page → `POST /session` | Login-CSRF: forcing a victim's browser to authenticate as the attacker's chosen session. |
| Browser → outbound Referer header | Any URL the app is reached at may be forwarded to a third-party origin. |
| Operator environment → running process | A weak or copied-from-example passphrase makes every other control in this phase moot. |
| Repository → public git history | `.env.example` is committed and scanned; a real value here is a permanent leak. |
