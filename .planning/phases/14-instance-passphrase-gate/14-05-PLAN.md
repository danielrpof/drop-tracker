## Compose semantics — already verified empirically, do not re-derive

The planner ran a throwaway fixture probe against this machine's Docker Compose v2.40.3 (fake values only, no repo secrets involved) to settle the precedence question this plan depends on. Findings, treat as established fact:

1. `environment:` beats `env_file:` on key collision. A key present in both wins from `environment:`.
2. `${VAR:-}` in `environment:` resolves from the host shell first, then the project `.env`, then the default. Because this repo's `env_file` IS the project `.env`, a value the operator adds there is found by interpolation and rendered correctly — it is NOT clobbered.
3. The one clobber case: a host shell that exports the variable as an EMPTY string shadows `.env`, and `:-` then yields the default. Narrow, and the boot log line added in Task 2 makes it immediately visible. Document it; do not attempt to engineer around it.
4. `docker compose config` inlines `env_file` contents into its rendered `environment:` output. Running it against this repo prints the real `DISCORD_WEBHOOK_URL` and `INSTANCE_PASSPHRASE` to stdout. It must not be used as a verification step anywhere in this plan, and the operator runbook must warn against it.

## Constraints

- Do NOT weaken or remove the GATE-07 inert path. Empty passphrase means no gate; that is intentional, is what Test 3 passed on, and stays.
- Do NOT add a YAML parsing dependency. `internal/config/config_test.go` already inspects repo-root files with a `bufio.Scanner` line scanner (`envExampleKeys`, `TestDotEnvIsNotTracked`). Follow that idiom.
