<objective>
Close **G-14-3**. On a gated instance, a browser that already holds a valid `dt_session` cookie and
opens a fresh session — no `dt_gate_active` entry, no 401, no typed passphrase — never renders the
**Log out** control, because the SPA has no way to discover the instance is gated except a 401 or a
completed login. `authed` is optimistically `true` (**D-16**, no boot-time `GET /session`), every
gated fetch returns 200, and `gate.Authenticate` attaches nothing to a successful response, so a
gated 2xx is shape-identical to an ungated instance's. `gateActive` stays `false` all session and
`{gateActive && <LogoutButton />}` never mounts.

Plan 14-06 (seed `gateActive` from `sessionStorage`) narrowed but did not close this: it only helps
*after* a 401 or a login has recorded the flag once in the session. The deeper gap, present since
14-03, is the absence of any gated-load signal at all.

The fix is one thin vertical slice: **the server marks every response that passes the gate, and the
client latches that marker.** `gate.Authenticate` sets a fixed response header on its proven-valid-
cookie path; `apiFetch` — already the single funnel every request goes through, and already the home
of the D-16 401 interceptor and the D-15 CSRF header — reads it and calls a new
`authStore.markGateActive()`. No new endpoint, no extra round trip, no boot-time probe, no change to
`root.tsx`.

This does not weaken **D-18**; it implements its purpose more faithfully. D-18's rule is that the
Log out control renders only when the instance is gated, "so an ungated instance never shows a
control that would call a route that does not exist." Its enumeration of triggers (a 401, or a
completed login) was the implementation available in 14-03, not the point. After this plan the
signal comes from a middleware that is *only registered when the gate exists*, so the ungated
guarantee holds structurally rather than reactively. Record that extension in the SUMMARY; do not
edit 14-CONTEXT.md.

Purpose: restore GATE-06's user-facing half — a logged-in user can always find the control that ends
their session — without giving the client any new authority. `gateActive` stays presentation-only and
the server 401 remains the sole enforcement.

Output:
- A self-identifying gated response (`internal/authgate/gate.go`), proven by a Go test that an
  ungated instance and a gated 401 both carry nothing.
- A client latch (`api.ts` + `authStore.markGateActive`) that never touches `authed` and never
  clears.
- The one-line WR-01 storage-guard hardening carried by 14-VERIFICATION as a residual, now with an
  automated test that removes a standing human-verification item.
- A 14-UAT.md Test 5 precondition that actually reproduces G-14-3, so the operator's re-run cannot
  accidentally pass by typing the passphrase.

Sizing note: four tasks, but the entire production diff is under 40 lines across four files
(a two-const block plus one `Header().Set` in Go; one method on the store; one `if` in `apiFetch`;
two lines moved inside an existing `try`). Tasks 3 and 4 are severable single-concern commits.
Splitting this into two plan files would cost more orchestration than the work itself, and the
context budget is dominated by reads of files that all four tasks share.
</objective>

## Deliberate scoping decisions

Recorded here so the choices are visible rather than silent:

1. **Header on the success path only, not at the top of `Authenticate`.** Setting it unconditionally
   would also mark the 401, which is semantically defensible but strictly larger: the 401 already
   drives `markUnauthenticated()`, which already sets `gateActive`. Restricting the write to the
   proven-valid-cookie path keeps the marker's meaning exact — *this response passed the gate* — so
   it can never be emitted by a path that is not behind the gate. The consequence is that its absence
   proves nothing (exempt routes carry none on a gated instance), which is precisely why the client
   latch is one-way and never clears.

2. **WR-01 folded in as a severable task (Task 3), not deferred.** 14-VERIFICATION routed it to a
   follow-up quick task on the assumption that a throwing storage *accessor* is not reproducible in
   jsdom. It is — a `configurable` accessor property redefined on the global with a throwing getter
   makes even `typeof sessionStorage` throw. Folding it in costs two moved lines plus one test in a
   file this plan already opens, and it retires a standing human-verification item rather than
   carrying it into the next round. It lands as its own `fix` commit so reverting it does not touch
   the G-14-3 closure, and it is NOT listed in `gap_ids` — it is a review residual, not a gap.

3. **No re-probe across all seven GATE requirements.** Phase 14 verified 8/8 and Tests 1–4 pass. As
   in 14-06, `must_haves` here are derived from G-14-3, its operator-confirmed root cause, the debug
   session, and decisions D-15/D-16/D-18 — not from a fresh phase-wide probe. Re-probing a verified
   phase to fix one hidden button would be cost with no new information.

4. **External-API coverage: not applicable.** This plan integrates nothing. It adds one response
   header to an existing in-process middleware and one header read to an existing fetch wrapper. No
   HTTP client, SDK, service, or credential is introduced; `COVERAGE.md`'s "No external API
   integration" record for the phase needs no amendment.

5. **Reversibility: `reversible`.** One Go middleware line plus two small client edits. No wire
   contract that anything outside this repo depends on, no schema, no migration, no env var, no route
   table change. Reverting the Task 2 commit restores exactly today's behaviour. No
   `checkpoint:decision`.

6. **The committed `internal/webassets/build/client/` tree is deliberately not regenerated** —
   unchanged carry-forward from 14-06 scoping decision 3. The `Dockerfile` builds `web/` itself in a
   `node:26-alpine` stage and overwrites that tree, so `docker compose up --build` (the path the
   operator uses for UAT) picks this fix up from source.

| server response headers → SPA module state | This plan opens a new channel across an existing boundary. Anything crossing it is a presentation hint only; no authorization decision may be derived from it. |
| server 401 → client presentation | The only real authorization boundary in this phase. This plan adds state on the client side of it and moves no decision across it. |
