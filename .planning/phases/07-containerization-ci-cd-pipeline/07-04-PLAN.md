> Every push is automatically linted, tested, and security-scanned, and every merge to main produces a versioned, non-root, single-image build published to a container registry — with the full stack (API, scheduler, notifier, embedded SPA) also runnable locally via docker-compose.

<objective>

Purpose: plan 07-03 stops deliberately at "built and scanned, never published". This plan adds publishing on the one trigger that is never attacker-controlled, in a separate job so the elevated `packages: write` / `contents: write` token is unreachable from any pull request. It closes the phase's last three requirements and ends with the only verification that can honestly close them — a real pull request and a real merge.

Output: a `release` job in `.github/workflows/full-pipeline.yml`, and the seeded `v0.1.0` git tag.
</objective>

  </read_first>
  <files>.github/workflows/full-pipeline.yml</files>
  <action>
    Add a `release` job. Do not fold these steps into `build-scan`: `build-scan` runs on pull requests and therefore builds pull-request-authored code, and a job-level `permissions:` block applies to every event that reaches the job. A separate job is what keeps the elevated token structurally unreachable from a pull request.

    The job declares `needs: [build-scan]` and `if: github.event_name == 'push' && github.ref == 'refs/heads/main'`. It runs on `ubuntu-latest` with a job-scoped `permissions:` block granting exactly `contents: write` (to push the tag) and `packages: write` (to push the image). `needs:` is what makes the scan gate structural: a red Trivy result fails `build-scan`, `release` never starts, and no login, push, SBOM or tag can occur.

    Steps, in this exact order:

    1. `actions/checkout` (pinned SHA `3d3c42e5aac5ba805825da76410c181273ba90b1`, v7.0.1) with `fetch-depth: 0`. The default shallow clone makes svu unable to see prior tags or walk commit history, and its failure mode is a wrong version rather than an error.
    2. `actions/setup-go` (pinned SHA `b7ad1dad31e06c5925ef5d2fc7ad053ef454303e`, v7.0.0) with `go-version-file: go.mod`.
    3. A `run` step installing svu with `go install github.com/caarlos0/svu/v3@v3.4.1`, computing `svu next` into a shell variable, and comparing it against `svu current`. If the two are equal, fail the step with an explicit message stating that no recognized conventional-commit prefix was found in the merged history so no version bump could be computed, and pointing at the `pr-title` job as the gate that normally prevents this. This is the deliberate, documented behaviour for an unrecognized prefix: a loud failure, never a silent no-op and never an accidental bump. Only on success write the value to `$GITHUB_ENV` as `VERSION`.
    4. `docker/setup-buildx-action` (pinned SHA `bb05f3f5519dd87d3ba754cc423b652a5edd6d2c`, v4.2.0).
    5. `docker/login-action` (pinned SHA `dbcb813823bdd20940b903addbd779551569679f`, v4.6.0) with `registry: ghcr.io`, `username: ${{ github.actor }}`, `password: ${{ secrets.GITHUB_TOKEN }}`. The ambient token already carries `packages: write` from the job's own permissions block, so no additional registry secret is needed.
    6. `docker/build-push-action` (pinned SHA `53b7df96c91f9c12dcc8a07bcb9ccacbed38856a`, v7.3.0) with `context: .`, `push: true`, `tags: ghcr.io/danielrpof/drop-tracker:${{ env.VERSION }}`, `cache-from: type=gha` and `cache-to: type=gha,mode=max`. The cache was populated by `build-scan`'s identical build of the identical Dockerfile, so this resolves almost entirely from cache rather than rebuilding. Publish exactly one tag — the semantic version. Do not additionally publish `:latest` or any other mutable rolling tag: a mutable tag can be made to point at an artifact whose provenance a consumer cannot reconstruct, which is precisely the guarantee this pipeline exists to demonstrate.
    7. `anchore/sbom-action` (pinned SHA `e22c389904149dbc22b58101806040fa8d37a610`, v0.24.0) with `image: ghcr.io/danielrpof/drop-tracker:${{ env.VERSION }}` and `format: spdx-json`. spdx-json is the format CLAUDE.md's Technology Stack names as most broadly tooling-compatible, and research surfaced no reason to deviate. The SBOM is generated against the pushed reference so it describes exactly the artifact a consumer will pull.
    8. A final `run` step creating and pushing the git tag: `git tag "$VERSION"` then `git push origin "$VERSION"`. This is last on purpose. Tagging before the push would leave a version tag with no corresponding image whenever the push fails; ordering it after means a failed push fails the whole job before any tag exists, so a tag never outlives a failed publish.

    The ghcr.io package inherits public visibility from the already-public repository (D-05), so no manual visibility step is needed.

    Re-verify every SHA against the live remote with `git ls-remote` before writing it, exactly as in plan 07-03.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| workflow job -> ghcr.io registry | The publish credential is the ambient `GITHUB_TOKEN`; whichever job holds it can write packages |
| workflow job -> git refs on origin | `contents: write` allows creating tags, which are the version line consumers rely on |
| ghcr.io -> anonymous puller | The package is public (D-05); anything in the image is world-readable |
| conventional-commit message -> computed version | An unvalidated commit message silently drives the published version number |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-07-17 | Elevation of Privilege | ghcr.io push credentials | high | mitigate | `packages: write` and `contents: write` live in the `release` job's own `permissions:` block; that job is guarded by `github.event_name == 'push' && github.ref == 'refs/heads/main'` and is therefore unreachable from any pull-request event. Enforced by the "appears exactly once" acceptance gate |
| T-07-18 | Tampering | unscanned artifact reaching the registry | high | mitigate | `release` declares `needs: [build-scan]`; a red Trivy step fails `build-scan`, so login, push, SBOM and tag never execute. There is no alternate code path to the registry in the workflow |
| T-07-19 | Repudiation | version tag with no corresponding image | medium | mitigate | The `git tag` / `git push origin` step is ordered last, after a successful image push and SBOM generation, so a failed push fails the job before any tag exists |
| T-07-20 | Tampering | mutable published tag | medium | mitigate | Exactly one immutable semantic-version tag is published; no rolling tag is created, so a consumer's pulled digest always maps to one scanned build. Gated by the zero-count acceptance check |
| T-07-21 | Spoofing | unvalidated commit message driving the version | medium | mitigate | D-06's `pr-title` job validates the squash-merge message that actually feeds svu; the version-compute step additionally fails loudly when no bump can be computed rather than proceeding with a wrong or unchanged version |
| T-07-22 | Information Disclosure | public image contents | low | accept | The image contains only compiled output of an already-public repository, and plan 07-01's `.dockerignore` plus the no-`ENV` gate keep secrets out of every layer (T-07-01). Public visibility is the explicit intent of D-05 — a reviewer can pull without authenticating |
</threat_model>
