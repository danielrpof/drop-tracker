<objective>
Close G-11-1: `internal/db/pool.go`'s `PoolConfig` never sets `pgxpool.Config.MaxConns`, so the pool inherits pgxpool's own `max(4, runtime.NumCPU())` default — which is below the `MusicBrainzPollWorkers + DeezerPollWorkers` ceiling (default 3 + 5 = 8) on any host with fewer than 8 vCPUs, including the small VPS this project targets.

Purpose: size the pool against the concurrency it must actually serve rather than against the deploy host's CPU count, while leaving an operator's explicit `pool_max_conns` authoritative.
Output: a `PoolConfig`/`NewPool` pair that take the poll-worker ceiling as an argument, a computed `MaxConns` default with documented headroom, and tests pinning both the computed default and the operator-override path.
</objective>

<upstream_facts>
These were verified directly against `github.com/jackc/pgx/v5@v5.10.0` in the module cache during planning. Do not re-derive them; do not assume the `ConnectTimeout` pattern in `PoolConfig` transfers.

1. `pgxpool.ParseConfig` (pgxpool/pool.go:370-385) ALWAYS populates `config.MaxConns`. When the DSN carries `pool_max_conns` it parses that value AND deletes the key from `connConfig.Config.RuntimeParams`; otherwise it assigns `max(4, runtime.NumCPU())`. `config.ConnConfig` and that `connConfig` are the same pointer, so the deletion is visible on the returned config.

   Consequence: the sentinel technique at pool.go:98 (`if cfg.ConnConfig.ConnectTimeout == 0`) has NO analog for `MaxConns`. After `pgxpool.ParseConfig` returns, an operator-set `pool_max_conns=6` and an incidental 6-vCPU default are indistinguishable. Any "is it still zero / is it still the default" check is wrong.

2. The only reliable operator-intent signal is a separate parse: `pgx.ParseConfig(dsn)` leaves `pool_max_conns` in `RuntimeParams`. `pgconn.ParseConfig` (pgconn/config.go:399-437) routes every setting NOT in its `notRuntimeParams` set into `RuntimeParams`, and `pool_max_conns` is not in that set. This works for both DSN forms this project may see (URL `postgres://…?pool_max_conns=10` and keyword/value `host=… pool_max_conns=10`) because pgx's own parser normalises both — which is exactly why hand-rolling DSN string matching is the wrong approach here.

3. `pgx.ConnConfig` embeds `pgconn.Config` anonymously (pgx/conn.go:22-23), so both `connCfg.RuntimeParams` and `connCfg.Config.RuntimeParams` compile.

4. `github.com/jackc/pgx/v5` is already a DIRECT require in go.mod at v5.10.0 (used by `internal/db/sqlc/db.go` and `internal/watchlist/service.go`). This plan adds no module dependency and runs no package-manager install.

5. Parsing the DSN twice inside this package is already precedented: `redactedTarget` (pool.go:112-118) re-parses on every error path.
</upstream_facts>
