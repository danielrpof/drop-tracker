# Phase 27 — UI Design Contract

> Visual and interaction contract for **Paste-a-List Bulk Add**. An `Add from list` button on the Watchlist
> opens a four-step dialog: **1 Paste · 2 Find matches · 3 Review · 4 Done**. Step 2 is a dedicated
> progress screen (sketch 002, variant B). Step 3 shows one status group at a time behind a segmented
> control (sketch 001, variant C). Step 4 is a result view that replaces the toast pattern.
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope of this phase's UI:**
- `web/app/routes/watchlist.tsx` gets an `Add from list` button beside `SearchBox`, and hosts the new dialog at route level, as it already does for `ManageTagsDialog` and `ConfirmDialog` (D-10).
- A new `web/app/components/watchlist/BulkAddDialog.tsx` holds the whole flow. The planner may split the step bodies into sibling files (`BulkAddPaste`, `BulkAddProgress`, `BulkAddReview`, `BulkAddResult`) and keep the row card as `BulkAddRow`.
- `web/app/components/common/ConfirmDialog.tsx` gains one optional prop, `cancelLabel` (default `Cancel`), for the discard prompt.
- `web/app/app.css` gains **one** theme token, `--color-status-error`.

There is no new route or nav entry. History, System, the search columns, the filter toolbar, and the Phase 26 bulk bar do not change.

**Upstream contract (read first):**
- `27-CONTEXT.md` decisions **D-01…D-20** are locked, as amended by the post-discuss grilling **G-27-1…10** (where they conflict, the amendment wins). The ones that change this spec are G-27-2 (concurrency 2, no rate promise), G-27-3 (High requires score ≥ 90), G-27-6 (outcome shape), G-27-7 (abort on unmount), G-27-8 (the re-add line moves to Review), and G-27-10 (one automatic retry before Error). This spec pins only what CONTEXT left to discretion: exact copy, the seed-mode wording, visual tokens, sizes, focus order, and announcements.
- The sketch winners are locked: `.planning/sketches/001-review-screen/` (C: segmented tabs, D-16 amended so the selected row wins) and `.planning/sketches/002-dialog-flow/` (B: progress screen, then review).
- `06-UI-SPEC.md` (tokens, type scale), `19-UI-SPEC.md` (status palette), `24-UI-SPEC.md` ([R6] one status region, the ConfirmDialog title override), and `26-UI-SPEC.md` (44px checkbox hit area, `border-muted-foreground` checkbox boundary, the seed-mode disclosure wording).
- ui-ux-pro-max rules applied: `color-not-only`, `touch-target-size`, `contextual-live-badge-updates`, `multi-step-progress`, `sheet-dismiss-confirm`, `error-placement`, `error-recovery`, `loading-buttons`, `focus-not-obscured`, `reduced-motion`, `horizontal-scroll`, `long-token-wrapping`, `primary-action`.

## Spacing Scale

This is the same Tailwind v4 default scale used since Phase 6, through default utilities. **There are no custom spacing tokens.**

| Token | Value | Usage in this phase |
|-------|-------|---------------------|
| xs | 4px | `gap-1` between a row's checkbox column and its body; icon-to-text inside badges and tallies (vendored `gap-1`); `gap-1` between step pills; `gap-1` between a row's text lines |
| sm | 8px | `gap-2` between footer buttons; between the textarea, its label, and its helper; between the `Add from list` button and `SearchBox`; between tally tiles; `py-2` on row cards and the tab strip |
| md | 16px | `p-4` on the dialog header, body, and footer; `px-4` on row cards and the tab strip; `gap-4` between tally items on the progress screen; `p-4` inside result tiles |
| lg | 24px | `gap-6` between result-view blocks (tiles, skipped list, failed list, note) |
| xl | 32px | `p-8` page gutter (unchanged) |
| 2xl | 48px | `py-12` above and below the progress-screen content block |
| 3xl | 64px | Not used |

**Control sizes (multiples of 4):** checkbox box `size-4` (16px) inside a `size-11` (44px) label; close button `size-11`; segmented tab strip `h-11`; footer, row-action, and Select controls `h-11` below 640px and vendored `h-9` / `h-8` at `sm` and up; progress track `h-3` (12px, vendored); badge `h-6` (24px); dialog `sm:max-w-2xl` (672px); progress block `max-w-90` (360px).

**Exceptions:**
- **44px touch rule below `sm`.** Every interactive control inside the dialog is at least 44px tall below 640px (ui-ux-pro-max `touch-target-size`). Footer buttons and the row `Retry search` / `Search line` buttons take `max-sm:h-11`. `SelectTrigger` needs `max-sm:data-[size=default]:h-11`, because its vendored `data-[size=default]:h-9` outranks a plain `max-sm:h-11`. At `sm` and up the vendored sizes stand, which meets WCAG 2.2's 24px minimum. The segmented tabs (`h-11`) and the checkbox labels (`size-11`) are 44px at every width.
- **The page-level `Add from list` button stays at the vendored `h-9`**, matching `Manage tags` and `SearchBox`'s `h-9` input on the same page.
- **Safe-area footer padding:** below `sm`, the footer takes `pb-[max(0.5rem,env(safe-area-inset-bottom))]`. This is computed, not a token.
- **Row text offset:** the row body takes `pt-3` (12px, which is on the 4px grid), so its first 21px line (14px × 1.5) sits centered against the 44px checkbox label: (44 − 21) / 2 ≈ 12. `items-center` on the `<li>` was rejected because it would center the checkbox against the whole multi-line body (pasted line, match, note, picker, action) instead of the first line.
- **Registry-internal paddings stay as shipped** (`Badge px-2`, `TabsList p-[3px]`, `TabsTrigger px-2`, `SelectItem py-2 pl-3 pr-8`, `Textarea px-3 py-3`), the same treatment Phases 20, 24, 25, and 26 gave vendored internals.

## Typography

This is unchanged from Phase 6: **exactly 4 sizes and exactly 2 weights**, set through the `text-display` / `text-heading` / `text-body` / `text-label` tokens.

| Role | Size | Weight | Line Height | Where used this phase |
|------|------|--------|-------------|------------------------|
| Display | 28px (1.75rem) | 600 | 1.2 | The progress count (`12`, with `of 40` at weight 400 in `text-muted-foreground`); the result-tile numbers |
| Heading | 20px (1.25rem) | 600 | 1.2 | `DialogTitle` on every step (vendored `text-heading font-semibold`); the `ConfirmDialog` title (already overridden in Phase 24) |
| Body | 16px (1rem) | 400 / 600 | 1.5 | The matched artist name on a row card (600); textarea text below `md` (vendored `text-base`, which avoids iOS zoom on focus) |
| Label | 14px (0.875rem) | 400 / 600 | 1.5 | Everything else: pasted line, disambiguation and country, row notes, badges (600), tab labels, step pills, helper and error lines, tallies, footer count (number at 600), result list items, list headings (600), buttons (vendored `text-sm`), textarea text at `md` and up (vendored `md:text-sm`) |

- **Badge override:** `Badge` ships `text-xs font-medium` (12px / 500). Every badge this phase renders adds `h-6 text-label font-semibold`. This phase introduces no 12px text.
- **Known third rendered weight: 500.** The vendored `Button` and `TabsTrigger` ship `font-medium` (500), so every button and segmented tab label in this dialog renders at 500. This is the same vendored-component exception Phases 6, 19, 24, 25, and 26 kept. It is not overridden to 600, because that would make this dialog's buttons differ from every other button in the app. Phase-authored text uses only 400 and 600.
- `tabular-nums` applies to the progress count, the tallies, the tab counts, the line numbers (`12.`), the footer `{N} selected`, and the result-tile numbers, so none of them jitter as they change (`number-tabular`).
- Pasted lines, artist names, disambiguations, and result names take `wrap-anywhere` (`long-token-wrapping`). None of them truncate, except the `SelectTrigger` value (see Layout).

### Step 1 — Paste

```
body: <div class="flex h-full flex-col gap-2 p-4">
  <label for="bulk-add-names" class="text-label font-semibold text-foreground">Artist names, one per line</label>
  <Textarea id="bulk-add-names" aria-describedby="bulk-add-help" aria-invalid={over}
            spellCheck={false} autoCapitalize="off" autoComplete="off"
            class="min-h-60 flex-1 field-sizing-fixed resize-none sm:h-80 sm:flex-none sm:resize-y" />
  <p id="bulk-add-help" aria-live="polite" class="text-label text-muted-foreground | over: flex items-center gap-1 text-status-error">…</p>
</div>
footer: [ (empty flex-1) ] [Find matches default]
```
- **No footer secondary on Paste.** The header's 44px Close button and Esc already dismiss this step, and they close with no prompt because no search has run yet (D-12). A second dismiss control would repeat Close and need a generic label.
- `field-sizing-fixed` replaces the vendored `field-sizing-content`, so 100 lines scroll inside the field and never push the footer off screen.
- The helper is recomputed 250ms after the last keystroke (`debounce-throttle`), so a long paste doesn't announce on every key. The visible text and the live region are the same node, which keeps D-10's single live helper.
- When over the cap, the helper gains `TriangleAlert` and the error copy, both in `text-status-error` (one status color for the whole line), the textarea gets `aria-invalid="true"` (vendored destructive border), and `Find matches` is disabled. The error sits directly below the field it describes (`error-placement`).

## Interaction Contract

### Step transitions

| From | Trigger | To | Notes |
|------|---------|----|-------|
| (closed) | `Add from list` | Paste | Opens empty. Any earlier session's state was dropped on close. |
| Paste | `Find matches` (enabled when 1 ≤ distinct names ≤ 100) | Resolving | Parsing (D-11): split on newlines, normalize (D-02), drop blank and duplicate lines, and keep the first occurrence's original text as the row's `line`. Row numbers `{n}` count from 1 in kept order. |
| Resolving | every search settles | Review | Automatic. |
| Resolving | `Stop and review` | Review | Aborts in-flight requests with the shared `AbortController`, drops the pending queue, and marks every unsettled line Not searched (D-13). Aborted requests are never reported as Error. |
| Review | `Edit list` | Paste | The textarea text is exactly what the user last ran (D-10). Every resolved row, pick, and selection is dropped. `Find matches` searches every line again. No confirm. |
| Review | `Add {N} artist{s}` | Result (on success) | One request with every selected row's `{mbid, name, disambiguation}` (D-06, D-07). No request is sent when N = 0, because the button is disabled. |
| Review | confirm fails (network, 4xx, 5xx) | Review | Stays on Review with every pick and selection intact. The confirm-failure line renders, `Add` re-enables, and focus stays on `Add`. Nothing was added. |
| Result | `Done`, Close, or Esc | (closed) | No discard prompt. |

### Search orchestration (UI-visible behavior only)

- Concurrency is **2** (G-27-2): one search in flight, one queued. The shared MB limiter decides the real pace, which runs from about 1 search a second when the poller is idle to about 0.4 a second during a poll cycle. The UI never promises a rate or a fixed duration.
- Each settled search classifies its row by D-01…D-04, using MusicBrainz results only. The Deezer column is ignored.
- **One automatic retry before Error** (G-27-10). A first failure is not shown: the line goes back to the end of the queue after about 2s, and its row stays in the "Searching" state (on Resolving, it rejoins "now searching" when it runs again). The Error badge, the Error tally, and the `Retry search` button appear only after the automatic retry also fails. `{done} of {total}` advances only when a line settles for the last time, so the bar never moves backwards. Manual retries get no extra automatic retry.
- Per-row `Retry search` / `Search line` and the banner's `Retry failed` go through the same queue and limiter. While any retry is in flight, `Add` stays enabled: selected rows can be confirmed while other rows retry, and a row that is still searching is simply not selected.
- A retried row **keeps its tab** (D-18). If it resolves High, it becomes selected (unless it is a duplicate or already watched). If it resolves Medium, it stays unselected. Not found and Error behave as they do on first resolve.

### Selection rules (D-05, D-15, D-16 amended, D-17)

- **Start of review:** High rows are selected and every other row is unselected (D-05). The derivation pass then runs, and group membership is frozen (D-18).
- **Derivation pass** (runs after every selection, pick, or retry change, over all rows in paste order):
  1. `onWatchlist` = the row's current pick `mbid` is in `entries`' mbids. Such a row is forced unselected.
  2. `dupOf` = the line number of another **selected** row with the same pick `mbid`, else none. The row that was already selected keeps its selection, and the other row is forced unselected and blocked.
  3. A row is `selectable` when it has a pick, is not searching, and has neither `onWatchlist` nor `dupOf`.
- **Checkbox toggle:** flips `selected` when selectable. Focus stays on the checkbox.
- **Picking a candidate** (D-15): sets the pick, then sets `selected = true`, then runs the derivation pass. A pick that is already watched or already held by another selected row lands unselected with its note. Focus returns to the Select trigger (base-ui default).
- **Unchecking a row frees its artist:** any row blocked as its duplicate becomes selectable again, but is not auto-selected.
- The confirm body never carries the same `mbid` twice. This follows from step 2, and the payload builder de-duplicates as a backstop.
- **Tab membership is frozen at review start** (D-18). Skipped = rows that were `onWatchlist` or `dupOf` at that moment, Ready = High, and Needs review = everything else. Later changes update badges, notes, checkboxes, and the footer count, never a row's tab or the tab counts.

### Closing and discard (D-12)

- The Close button, Esc, and an outside press on the overlay (at `sm` and up) all call `requestClose()` through `Dialog onOpenChange(false)`.
- `requestClose()` closes immediately when the step is Paste (no search has run yet) or Result. Otherwise it opens the discard `ConfirmDialog` and the main dialog stays open.
- While the confirm request is in flight, `requestClose()` does nothing. Close and Esc are blocked until the request settles, the same rule `ConfirmDialog` uses for its own pending state.
- **Discard list** aborts every in-flight search with the same `AbortController`, drops all state, and closes both dialogs. Nothing is added. **Keep list** closes only the prompt and leaves searches running.
- **Unmount aborts too** (G-27-7). The dialog's effect cleanup aborts the `AbortController` and drops the queue. When a session expires mid-resolve, `apiFetch`'s 401 handler unmounts the Watchlist, and the remaining searches must not keep firing. The pasted list is lost (no saved draft), and no discard prompt is shown.

### Watchlist refresh (SC5, D-08, D-20)

- When the confirm request succeeds, the dialog switches to Result **and** calls `refresh()` in the same tick. The list updates behind the dialog with no reload and no skeleton flash (existing `refresh()` behavior).
- After `refresh()` resolves, map each added `mbid` to its watchlist id and pass them to `markStickyMany`, so the new cards stay visible under an active filter (Phase 25 G4).
- New cards render with the existing no-art placeholder. There is no "resolving art" indicator and no client re-polling (D-08).

### Copy failed names

`Copy failed names` writes the failed names, one per line in paste order, to `navigator.clipboard.writeText`. On success the button reads `Copied` with `CopyCheck` for 2000ms, then reverts, and the status region announces the copy message. If the clipboard is unavailable or the write rejects, the button stays as it is and the status region announces the copy-failure message. The names stay on screen as selectable text.

## Data Contract (informational — the planner owns it)

This section records what the UI above needs from the confirm endpoint. The path, verb, and field names are CONTEXT discretion.

```ts
interface BulkAddItem { mbid: string; name: string; disambiguation: string | null } // no Deezer data (D-07)
interface BulkAddOutcome {
  added: string[]                                         // mbids
  skipped: { mbid: string; reason: "already_watched" | string }[]
  failed: { mbid: string; reason: string }[]              // refused as invalid before the transaction (G-27-4)
}
```
- The UI renders names from its own rows keyed by `mbid`, so name fields in the response are optional.
- An unknown skip `reason` renders as `{name} · skipped`, never as the raw string. A failure `reason` is never rendered; every failed row reads `{name} · couldn't be added`.
- Valid items go in one transaction (G-27-4), so a database error fails the whole request with nothing added. The UI shows the confirm-failure line, and partial success is never reported.
- The 100-item and body-size limits are enforced server-side (D-11). If the server rejects the request, the UI shows the confirm-failure line.
- After success the UI always calls `refresh()` and derives new watchlist ids from the refreshed `entries` for `markStickyMany`. The response doesn't need to carry entries.
