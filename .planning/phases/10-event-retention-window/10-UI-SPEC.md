## Copywriting Contract

| Element | Copy |
|---------|------|
| Empty state — History, retention-hidden (heading) | **"Older than your retention window"** |
| Empty state — History, retention-hidden (body) | **"There's release history for this view — it's just outside your retention window. Nothing was deleted."** |
| Empty state — History, no events at all (heading) — *unchanged, existing* | "No release activity yet" |
| Empty state — History, no events at all (body) — *unchanged, existing* | "Add an artist to your watchlist to start tracking new releases, features, and deluxe editions." |
| Empty state — History, filtered to zero results (heading) — *unchanged, existing* | "No matching events" |
| Empty state — History, filtered to zero results (body) — *unchanged, existing* | "Try a different artist or event type." |

No action/CTA on the new retention empty state — there is nothing the user can click to "undo" retention from the UI (the window is operator-configured via `EVENT_RETENTION_DAYS`, not a client-adjustable setting), so unlike the error states elsewhere in History, this empty state renders `EmptyState` with `action` omitted, exactly like the other two History empty states.

**Copy rationale (ties to 10-CONTEXT.md D-05):** must read as "your history isn't empty, it's just outside the window" — never implying the account/artist genuinely has no activity ("No release activity yet" would be false) and never implying the user applied a filter ("No matching events" would be false). The chosen copy states the true cause plainly and reassures the user nothing was deleted, without naming the raw env var (`EVENT_RETENTION_DAYS`) or a specific day count in the UI string, since the frontend has no guaranteed API-exposed source for the exact configured day count (10-RESEARCH.md D-06/Open Question 1 scopes the new API signal to a boolean only, not the day count) — inventing that exposure would be new scope beyond what CONTEXT.md locked.

**Trigger condition (interaction contract, not just copy):** `history.tsx`'s existing three-way empty-state branch (currently `isFiltered ? "No matching events" : "No release activity yet"`) becomes a three-way branch:

1. `events.length === 0 && hasOlderEvents === true` → **retention empty state** (new, takes priority)
2. `events.length === 0 && hasOlderEvents === false && isFiltered` → "No matching events" (unchanged)
3. `events.length === 0 && hasOlderEvents === false && !isFiltered` → "No release activity yet" (unchanged)

`hasOlderEvents` (wire name recommended by 10-RESEARCH.md Open Question 1 as `has_older_events`, snake_case matching the rest of the `/events` JSON envelope) must win over the `isFiltered` check when both could theoretically apply (e.g. a filtered view where every match happens to be retention-hidden) — the retention explanation is the more specific and more useful truth in that case, so it takes branch priority as ordered above. This is a UI/interaction contract this spec locks; the exact backend field name/shape itself remains 10-RESEARCH.md's/planner's discretion, but the frontend's branch-priority behavior described here does not change based on whatever name is chosen.
