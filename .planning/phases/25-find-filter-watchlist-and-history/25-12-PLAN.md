<objective>
Close UAT gap G-25-7 (major). Pressing History's Load more under a tag shows releases that are years old, which the user read as events
older than the retention edge.

Diagnosis (`.planning/debug/history-load-more-retention-leak.md`): this is not a leak. ListEvents applies `created_at >= cutoff` on every
page and filter variant, and live cursor walks returned 0 out-of-window rows. Retention counts from detection time (Phase 10 D-01), but
quick task 260825-g6i made the feed sort by release date, and EventCard shows only the release date. A newly watched artist's back
catalogue is inserted with a fresh `created_at`, so Load more pages back through years-old releases that retention correctly keeps.

User decision (2026-10-11, binding): keep D-01 and clarify the UI. Show the detection date on History event cards (or an end-of-feed
retention note), add a "detected recently, released long ago" regression test, and reword UAT test 7 and the verification check. The
rewording lives in 25-14 (shared doc files).

Discretion choice: a per-card `Detected {date}` line, not an end-of-feed note. 25-UI-SPEC "History Tag filter" says the UI needs no
retention logic of its own. An end-of-feed note would need the retention window length, which the History route doesn't have, and the
confusion shows up on every Load more page, not only at the end of the feed. `created_at` is already in the GET /events payload
(`EventItem.created_at`), so no API change is needed.

Purpose: HIST-02's "respecting event retention" becomes visible to the user.
Output: `formatDetectedDate`, the EventCard Detected line, and the Go regression test.

Commit discipline (CLAUDE.md): run `corepack pnpm --dir web exec prettier --write "**/*.{ts,tsx}"` before staging web files. Stage only
this plan's files (wave 1 runs in parallel). Comments are 1-3 lines and cite one design reference at most. Hooks stay on, and no AI
attribution trailer.
</objective>
