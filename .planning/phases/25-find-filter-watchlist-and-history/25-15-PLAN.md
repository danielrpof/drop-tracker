Root cause (25-VERIFICATION gap, 25-REVIEW WR-01): `handleTagsChange` calls the sticky clear as a sync-lane state write. React Router
7.18.2 applies the new location inside `React.startTransition` (`node_modules/react-router/dist/development/chunk-62JRHF6Z.mjs`
~6752). So the first commit renders the old filter without the sticky card, which unmounts it. The second commit mounts a new node.
`useScrollAnchor`'s captured chip is then disconnected, so no correction runs and focus falls to `<body>`.

Locked decisions (binding; they override CONTEXT/UI-SPEC ambiguity). Cite them as "user decision 2026-10-11 (gap planning)":
- WR-01 fix: make sticky invalidation part of the same render as the URL change. Key the sticky set to the filterKey it was created
  under and derive it during render (25-REVIEW WR-01 sketch). Drop the sync clear from `handleTagsChange`, `handleFlagChange`,
  `handleSortChange`, and the filterKey effect. Keep the q (local-state) path.
- WR-03: keep sticky cards across the route's own tag rewrites. A Manage tags merge or delete of a selected tag (`replaceSelectedTag`)
  and the canonicalization write (`settleTagIds`) carry the sticky set to the new filterKey. Only G4 user actions (and Back/Forward)
  clear it. Back must also show no post-paint flash.

Design choice (Claude's discretion, recorded): the reviewer's sketch derives `ids` only when `sticky.key === filterKey`. Done that way,
it brings sticky cards back when the user returns to an earlier filter key (toggle on, then off), which breaks G4. This plan resets the
state during render with React's "adjust state while rendering" pattern, so any key change is final. The carry target (`carryTo`) is
how the route's own rewrites opt out of that reset.

Carry lifetime (Claude's discretion, recorded; plan-checker iteration 1): a carry must apply only to the landing it was made for. If a
carry were cleared only on a filterKey change, a route-own rewrite followed in the same tick by a write back to the current key would
leave it pending, and a later G4 action onto the old target would keep stale ids. Clearing it on every render can't work either: the
router commits the location in a transition, so a render with the old location always runs between the write and its landing, and
that render would drop the carry before it lands. So the carry is tied to its write in three ways. The router location key (fresh
for every navigation) lets the first landing consume it. `useNavigationType()` limits it to a replace landing (every route-own rewrite
uses `{ replace: true }`, G4 writes push, and Back/Forward pops). And the write's starting filter key must equal the reconciled key,
so a write layered on an unlanded G4 change in the same tick never carries. The transitions live as pure functions in
`watchlistView.ts`, because same-tick write ordering can't be driven deterministically through the route in jsdom.
