  <action>
    Write the failing tests first, then make them pass.

    Extend `handleListEvents` to read four optional query params and build a populated `events.ListParams` from them. Parse in this order, rejecting before any store call:

    `artist_id` — absent or empty string means no filter. Otherwise `strconv.ParseInt` base 10, 64-bit; reject a parse failure or a value below 1 with `writeError(w, http.StatusBadRequest, "invalid artist_id")`. Ids are BIGSERIAL so zero and negatives are never valid, exactly as `parseWatchlistID` already reasons.

    `event_type` — absent or empty means no filter. Otherwise validate membership in `watchlist.EventTypes` using `slices.Contains`, the same allow-list `handleAddWatchlist` already checks against; reject with `writeError(w, http.StatusBadRequest, "invalid event type")`. Do not echo the submitted value back — unlike the watchlist handlers' sentinel path, this string is going into a message the handler composes itself, so keep it fixed.

    `cursor` — absent or empty means first page. Otherwise `strconv.ParseInt`, reject a parse failure or a value below 1 with `writeError(w, http.StatusBadRequest, "invalid cursor")`.

    `limit` — absent or empty means let the domain default apply. Otherwise `strconv.Atoi`, reject a parse failure or a value below 1 with `writeError(w, http.StatusBadRequest, "invalid limit")`. A value above the maximum is NOT an error: pass it through and let `events.Service.List`'s existing clamp reduce it to `MaxPageSize`. Clamping rather than rejecting means an over-large request still succeeds while never producing an unbounded scan.

    Add a small file-local helper for the shared "absent, or parse as a positive int64" logic so the three integer params do not each hand-roll it.

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-06 | Denial of Service | `limit` query param on `GET /events` | high | mitigate | Parsed then passed through to `events.Service.List`'s clamp at `MaxPageSize`; the clamp lives in the domain service so it cannot be bypassed. `TestHandleListEvents_Validation` asserts a `limit` of 100000 yields a requested page size no larger than the maximum |
| T-06-07 | Tampering | `event_type` query param | medium | mitigate | Membership-checked against `watchlist.EventTypes` with `slices.Contains` before the store call — the same Go-side allow-list that mirrors the DB CHECK constraint |
| T-06-08 | Tampering | `artist_id` and `cursor` query params | medium | mitigate | `strconv.ParseInt` with a reject-below-1 rule before the store call, mirroring `parseWatchlistID`; the values then travel only as sqlc-bound parameters |
| T-06-09 | Tampering | Stored XSS via event `title` / `artist_name` rendered in cards | high | mitigate | Rendered exclusively as plain JSX text nodes, which React escapes by default; a repo-wide negative grep in this task's acceptance criteria asserts React's raw-HTML injection prop appears nowhere under `web/app/` |
| T-06-10 | Information Disclosure | Validation error messages | medium | mitigate | Every 400 message is an operator-authored fixed string; the rejected value is not echoed back and no driver text reaches the body (V13) |
| T-06-11 | Spoofing | Untrusted `cover_art_url` loaded as an image source | low | accept | Browsers do not execute an image source as script, so the residual risk is a wrong or missing image, not code execution.
