<objective>
Give the operator a real management surface for their watchlist: see every tracked artist, tune each one's alert preferences inline, and remove one — all in the browser, none of it through curl.

**User story:** **As a** drop-tracker operator, **I want to** see and tune every artist I'm tracking from a web page **so that** I can control which releases reach my Discord without hand-writing PATCH bodies.

Purpose: UI-02 is the phase's management half. It also establishes the Watchlist tab and its loaded watchlist state, which plan 06-04's "Already watching" cross-reference depends on — `06-RESEARCH.md` Pitfall 3 is specifically about search results rendering before that state exists.

Output: A working Watchlist tab with inline, immediately-persisted preference editing and a forgiving remove flow.
</objective>

    Fill the two slots task 1 left in the row.

    **Preference toggles.** Create `web/app/components/watchlist/PreferenceToggles.tsx` exporting `PreferenceToggles`. Render two labelled groups of inline controls in the row itself — no modal, no separate save step per `D-12`:
    - release types: one checkbox per value in `album`, `single`, `ep`, `deluxe`, checked when the value is in the entry's `release_types`
    - muted event types: one control per value in `new_release`, `guest_feature`, `deluxe_change`, checked when the value is in the entry's `muted_event_types`

    Each toggle fires a PATCH immediately. Compute the next array for the toggled axis only and send exactly one axis in the request body. This matters: the API treats an absent key as "leave this axis untouched" and an explicitly empty array as "watch or mute nothing on this axis" — two distinct states. Sending both axes on every toggle would let a stale copy of the untouched axis overwrite a change made elsewhere, and unchecking the last box must send an empty array rather than omitting the key, because omitting it would leave the axis unchanged and the toggle would silently snap back.

    Apply the change optimistically so the control responds instantly, and keep the pre-toggle array in a local variable. Disable and dim the toggle between the click and the response so it cannot be re-clicked mid-flight. On any non-OK response or thrown error, restore the pre-toggle array into the parent's entry state and show the failure toast reading "Couldn't update preferences — try again." A rolled-back toggle must end up showing the server's true prior value, never the value the operator clicked — an optimistic control that stays visually "on" after a failed write is telling the operator their alerts are configured a way they are not.

    **Remove with undo.** Add the remove control to `WatchlistRow` and wire its handler in `web/app/routes/watchlist.tsx`. Per the UI-SPEC's destructive-confirmation policy there is no blocking dialog: the DELETE fires on click and the row disappears from the list immediately. Show a toast reading "Removed {artist name} from your watchlist." carrying an Undo action, auto-dismissing after 5 seconds. Undo calls `addWatchlist` with the artist's `mbid`, `name`, `deezer_id`, `disambiguation` and `image_url`, then refreshes the list.

    Label and describe the Undo honestly. The delete is a real hard delete and the removed row's custom preferences are not cached across the toast window, so Undo re-adds the artist with the API's default preferences — every release type enabled, nothing muted. Surface that in the Undo path's own user-visible copy rather than only in a code comment; an operator who had carefully muted deluxe alerts for an artist must not be led to believe those settings came back. The UI-SPEC flags this as a known limitation to document for the user, and the user-facing surface is where it has to be documented.

    On a failed DELETE show "Couldn't remove {artist name} — it may already be gone." and call the route's `refresh` so the list reflects the row's true server state rather than the optimistic removal — a 404 here means the entry really was already gone, and re-fetching is what makes the list honest either way.

    Give every icon-only control (remove button, toggles) at least a 44px hit area via padding around an on-scale icon, per the UI-SPEC's Spacing Scale exception, and an accessible label.

| Boundary | Description |
