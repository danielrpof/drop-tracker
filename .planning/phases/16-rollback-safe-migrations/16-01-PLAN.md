<objective>
Prove — and then make true — the single assumption the whole v1.3 rollback model rests on:
that the previously-released binary can boot against a schema newer than the migrations it
carries. RESEARCH Finding 1 executed the pinned `golang-migrate/migrate/v4 v4.19.1` and
refuted it: `Up()` returns a hard `no migration found for version N+1` error, which
`runMigrationsOnce` treats as fatal, which crash-loops the rolled-back image (Pitfall 9).

This is the phase's tracer slice: one thin path from the boot code through a real Postgres
and back, proving the rollback-safety model actually holds before any CI guard, static
scanner, or workflow job is built on top of it.

Purpose: MGRT-01 / SC #4. Nothing else in this phase is worth building if this fails.
Output: the `runMigrationsWithSource` seam, the `maxSourceVersion` helper, the
ahead-of-source no-op guard, the hermetic proof, and the `go run` HEAD-schema helper the
`n1-boot` job will invoke.
</objective>

<scope_note>
CONTEXT.md's Phase Boundary says "no change to the application's runtime **behavior** ...
plus one behaviour-preserving refactor". That line is **explicitly relaxed by the developer**
for this plan: RESEARCH Finding 1 was reviewed and the decision was to **absorb the fix into
Phase 16**. This plan therefore contains exactly ONE genuine runtime-behaviour change to the
boot path — the ahead-of-source no-op guard. It is inert on every forward boot (`cur <= smax`)
and fires only on a rollback. No other behaviour change is in scope.
</scope_note>
