<objective>
Build the static half of the SC #2 gate: a small, stdlib-only, unit-tested Go tool that reads
the migration SQL added on a branch and turns the build red — with a message that teaches the
expand/contract rule rather than reporting opaque DDL — when that SQL would break the
previously-released binary or hazard the forward deploy.

This is horizontal expansion from Plan 01's tracer: the boot path is now provably
rollback-tolerant, so the remaining work is catching the migrations that would break that
tolerance before they merge.

Purpose: MGRT-01 / SC #2, decisions D-05, D-06, D-07, D-08, D-19b.
Output: `cmd/migration-check` with its scan mode, the `allow-destructive` annotation contract,
and the two repo-config carve-outs a CI helper package needs.
</objective>

<task type="checkpoint:decision">
  <name>Checkpoint: lock the allow-destructive annotation grammar</name>

  <decision>
    What is the exact syntax and scope of the `migration-check:allow-destructive` annotation
    that a migration author writes to ship a deliberate contract-phase migration?
  </decision>

  <context>
    This is a **one-way door**. Migration files are immutable once released — Plan 03 will add
    a hard error for editing an already-shipped `*.up.sql`. The moment one released migration
    carries this annotation, the grammar is a published contract: changing it later would make
    the guard fail to parse a file that can no longer be edited, and there is no migration path
    out. D-07 fixed the two required keys (`expand-shipped-in`, `reason`) and D-13 fixed that
    the tag value is validated; the **shape** is still open (CONTEXT.md "Claude's Discretion").

    Whatever is chosen here is written into `internal/db/migrations/README.md` by Plan 05 and
    parsed by Task 3 below, so the answer must be settled before either.
  </context>

  <options>
    <option name="a">
      **File-scoped, single line, bare-token tag, trailing free-text reason** (recommended).
      One `--` comment anywhere in the `.up.sql` file:
      `-- migration-check:allow-destructive expand-shipped-in=v1.7.0 reason=events.old_col superseded by watched_artist_name`
      The literal prefix is matched after optional leading whitespace; `expand-shipped-in` takes
      a bare token; `reason` takes the remainder of the line. Suppresses every
      backward-incompatible and unsafe-forward finding **in that file**.
      Pros: simplest to author and to parse; no quoting rules to get wrong; a reason with commas
      or parentheses needs no escaping; one annotation covers a multi-statement contract
      migration. Cons: coarse — a file with two destructive statements is waved through by one
      annotation, so the reason must cover both.
    </option>
    <option name="b">
      **Statement-scoped** — the annotation must appear on the line immediately preceding the
      offending statement, and suppresses only that statement.
      Pros: precise; each destructive statement gets its own justification. Cons: the tokenizer
      strips comments before splitting statements, so comment-to-statement association needs a
      second offset-preserving pass; brittle when a statement spans lines; more to specify in
      the README and more ways for an author to get it subtly wrong.
    </option>
    <option name="c">
      **File-scoped with a quoted reason** —
      `-- migration-check:allow-destructive expand-shipped-in=v1.7.0 reason="…"`.
      Pros: `reason` is unambiguously delimited, so a future third key could be appended after
      it. Cons: introduces quoting/escaping rules into a contract that can never be revised;
      an author who forgets a closing quote gets a parse error on a file they cannot edit once
      released.
    </option>
  </options>

  <recommendation>
    Option **a**. It is the only shape with no escaping rules, and escaping rules are exactly
    the kind of detail you cannot fix later in an immutable file. The coarseness cost is real
    but bounded: a contract migration touching several objects is a single deliberate act, and
    the D-15 cross-reference in Plan 03 red-lines it anyway if any dropped object is still
    referenced by the previous release — the annotation cannot wave that through. Options b and
    c both spend one-way-door budget on precision this repo has never needed (zero destructive
    migrations in seven releases).
  </recommendation>

  <resume-signal>Reply "a", "b", or "c" to pick an option, or describe a different grammar. Record the chosen option verbatim in `16-02-SUMMARY.md` — Task 3 parses it and Plan 05 documents it.</resume-signal>
</task>
