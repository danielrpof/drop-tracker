<user_story>
**As a** drop-tracker operator, **I want to** be told when an album I already know about gets a
deluxe edition or reissue with extra tracks, **so that** I do not miss added material on a
release my tracker already recorded once.
</user_story>

<objective>
Deliver the deluxe/tracklist-change slice end-to-end: for release-groups already in the seen
store, fetch each release's per-medium track counts, compare the group's maximum total against a
persisted baseline, and record a `deluxe_change` event only when the count genuinely grew — with
the first-ever measurement establishing the baseline silently rather than firing a false alarm.

Purpose: this is the phase's highest-risk correctness gap (04-RESEARCH.md Pitfall #1); a naive
`COALESCE(MAX(track_count), 0)` baseline would fire a spurious alert for every release-group on
its first real comparison cycle.
Output: `internal/musicbrainz/releases.go`, the baseline queries, `detectDeluxeChanges`, and
tests proving both the true positive and the absence of the first-comparison false positive.
</objective>

<flagged_assumptions>
1. **The release-detail envelope is `[ASSUMED]`, not live-verified.** 04-RESEARCH.md Assumption A1
   reconstructs `{"release-count", "release-offset", "releases":[{"id","title","status","date",
   "media":[{"format","position","track-count"}]}]}` by analogy to the live-verified release-group
   browse envelope. A wrong field name would decode to zero values rather than erroring, making
   DTCT-02 silently never fire. That is why the two boundary truths above are marked `backstop`.
   Re-verify against one real response if MusicBrainz becomes reachable during execution.
2. **The baseline design resolves an open question, not a locked decision.** 04-RESEARCH.md Open
   Question 2 flagged this; plan 04-01's Task 1 checkpoint resolved it. Read `04-01-SUMMARY.md`
   for which option was chosen before writing the queries — both are handled concretely below.
3. **Per-cycle MusicBrainz request volume now scales with catalogue size.** For an artist with N
   already-seen release-groups, one MusicBrainz cycle issues 1 release-group browse + up to 10
   recording pages + N release-detail fetches, all serialised through the same limiter. D-01 and
   D-04 lock this shape (D-04 only removes the fetch for brand-new groups). The existing overlap
   guard absorbs a long cycle by skipping the next tick rather than stacking. Surfaced here, not
   reduced — a `detail_fetch_count` log attribute makes the cost observable.
</flagged_assumptions>

    **`internal/musicbrainz/releases.go`.** Mirror `releasegroups.go` and `recordings.go`
    structurally. Declare `releasePageSize = maxLimit` and `maxReleasePages = 10`. Declare
    exported `Medium` with `Format` (`json:"format"`), `Position` (`json:"position"`) and
    `TrackCount` (`json:"track-count"`); exported `Release` with `MBID` (`json:"id"`), `Title`
    (`json:"title"`), `Status` (`json:"status"`), `Date` (`json:"date"`) kept as the opaque
    partial-date string MusicBrainz returns — same rationale as `ReleaseGroup.FirstReleaseDate` —
    and `Media []Medium` (`json:"media"`); and unexported `releaseEnvelope` with `Releases`
    (`json:"releases"`), `Count` (`json:"release-count"`) and `Offset`
    (`json:"release-offset"`). Head the type block with a comment marking these names as
    04-RESEARCH.md Assumption A1, reconstructed by analogy and not confirmed against a live
    response.

    Add method `func (r Release) TrackCount() int` summing every medium's track count by range.
    Summing rather than reading one medium is required: D-02 compares a release's TOTAL count,
    and a two-disc deluxe edition would otherwise read as smaller than the single-disc original.

    `ReleasesByReleaseGroup(ctx context.Context, groupMBID string) ([]Release, error)` trims and
    rejects an empty MBID with the existing `ErrEmptyMBID` sentinel, checks `ctx.Err()` before and
    inside the loop, and runs the bounded pagination loop terminating on an empty page or on
    count-reached, advancing the offset by the number of entries actually returned.
    `fetchReleasePage` builds `GET /release` with `release-group`, `inc=media`, `fmt=json`,
    `limit` and `offset` params and issues it through `c.doRequest(ctx, req)` — the shared helper
    is what performs the limiter wait and sets the identifying User-Agent, so a page request that
    reached the network any other way would be both unpaced and unidentified. Non-200 responses
    error with the status code only, never body text.

    **Baseline queries.** Add to `queries/events.sql`, naming them identically under either
    resolution so the Go call sites do not branch:

    Under option-a (`track_count` on `events`): `-- name: GroupTrackCountBaseline :one` selecting
    `COALESCE(MAX(track_count), 0)::int AS baseline` and `COUNT(track_count) > 0 AS has_baseline`
    from `events` where `source = 'musicbrainz' AND release_group_mbid = $1`; and
    `-- name: SetGroupTrackCountBaseline :execrows` updating `events SET track_count = $2` where
    `event_type = 'new_release' AND source = 'musicbrainz' AND external_id = $1`. Mutating
    `track_count` on an existing row is not a D-20 violation: D-20's stated scope is the display
    snapshot (title, cover art URL, release date, artist name), preserved so the historical record
    keeps what was first detected. `track_count` is operational baseline state, not display data,
    and no snapshot column is ever written twice.

    Under option-b (`release_group_baselines` table): `-- name: GroupTrackCountBaseline :one`
    selecting `track_count` from `release_group_baselines` where `release_group_mbid = $1`; and
    `-- name: SetGroupTrackCountBaseline :exec` inserting `(release_group_mbid, track_count)` with
    `ON CONFLICT (release_group_mbid) DO UPDATE SET track_count = GREATEST(...), updated_at =
    now()`.

    Regenerate with `make sqlc` and commit the output.

    **Detector helpers.** In `detector.go` add `groupBaseline(ctx, groupMBID string) (int, bool,
    error)` returning the recorded baseline and whether one exists at all, and
    `setGroupBaseline(ctx, groupMBID string, count int) error`. Under option-b, treat
    `pgx.ErrNoRows` as `(0, false, nil)` — not an error. Distinguishing "no baseline recorded yet"

    positive; a helper that collapses both to zero reintroduces Pitfall #1.

    Declare `type ReleaseDetailSource interface { ReleasesByReleaseGroup(ctx context.Context,
    groupMBID string) ([]musicbrainz.Release, error) }`, add a `releases ReleaseDetailSource`
    field to `Detector`, widen `New` to `New(q sqlc.Querier, recordings RecordingSource, releases
    ReleaseDetailSource) *Detector`, and update the `cmd/server/main.go` call site to pass
    `mbClient` for both.

    **Pass ordering, and the D-04 guarantee.** `DetectMusicBrainz` must compute the seen
    release-group set ONCE, at the top of the function, before the new_release pass inserts
    anything, and hand that pre-cycle snapshot to the deluxe pass. Re-querying the seen set after
    the new_release pass would include groups discovered moments earlier in the same cycle, so a
    brand-new group would get a release-detail fetch on its discovery cycle — exactly what D-04
    forbids.

    **`detectDeluxeChanges(ctx, logger, entry, freshGroups, preCycleSeen)`.** Return nil
    immediately when `deluxeDetectionEnabled(entry)` is false — the `deluxe` value in
    `release_types` is a boolean gate on whether this detection runs for the artist at all, never
    a value matched against a MusicBrainz primary-type field (Pitfall #7). Return nil as well when
    `eventTypeMuted(entry, "deluxe_change")` is true. Both checks precede any fetch, so a
    non-participating artist costs zero requests.

    For each fresh group whose MBID is in `preCycleSeen`: call
    `d.releases.ReleasesByReleaseGroup(ctx, groupMBID)`; compute the maximum `TrackCount()` across
    the returned releases along with the release that carries it; skip the group entirely when the
    maximum is 0, leaving the baseline untouched — a zero total means the response carried no
    usable media data, not that the release has no tracks. Then load the baseline:

    - No baseline recorded: call `setGroupBaseline`, fire no event, and log
      `baseline_established` with the count. A first measurement is a baseline, not an increase.
    - Baseline exists and the fresh maximum is greater: insert a `deluxe_change` event with
      `external_id` set to the winning release's MBID (D-10), `release_group_mbid` set to the
      parent group, `title` from that release's title, `artist_name` from `entry.Name`,
      `release_date` from that release's date through `nullableString`, `cover_art_url` from
      `coverArtURLForReleaseGroup(groupMBID)`, `track_count` set to the fresh maximum, and the
      cycle's seed-mode `notified_at`. Then call `setGroupBaseline` with the new maximum.
    - Baseline exists and the fresh maximum is equal or lower: no event, no baseline change. D-02
      counts increases only; a lower count is an upstream data correction, and lowering the
      baseline would let the same tracklist re-fire later.

    Log one `detection result` line for the deluxe pass carrying `event_type`,
    `detail_fetch_count`, `baseline_established_count` and `inserted_count`, using the caller's
    logger so `cycle_id` correlation survives. A per-group fetch error is logged and that group is
    skipped; the pass continues to the next group and returns nil, so one unreachable group never
    discards the cycle's other events.
