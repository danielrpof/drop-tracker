# Phase 24 — UI Design Contract

> Visual and interaction contract for **tag chips, the tag autocomplete, and the plain-text note**
> on each Watchlist card, plus the global **Manage tags** dialog (rename, merge, delete).
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope of this phase's UI:** `WatchlistRow`'s name column gains a chip row (`TagChips`) and a
note block (`ArtistNote`). The Watchlist header gains a **Manage tags** button that opens a
`ManageTagsDialog`. A reusable `ConfirmDialog` built on AlertDialog covers merge and delete, and
Phase 26's bulk remove reuses it (D-16). No new route, no new nav entry, no change to History,
System, or the search columns. `PreferenceToggles` and the remove-artist button stay where they
are (D-01).

**Design system is already locked.** Tokens, theme, fonts, and the component library come from
`06-UI-SPEC.md` (founding spec, `web/app/app.css`), extended by `19-UI-SPEC.md` (status palette)
and `20-UI-SPEC.md` (`select`). This phase adds **zero** new theme tokens and **zero** new npm
packages (STACK.md). It vendors four official shadcn `base-maia` components: `dialog`,
`alert-dialog`, `combobox` (which pulls `input-group`), and `textarea`. All of them wrap the
already-installed `@base-ui/react`.

### Deliberately NOT used

- **`ComboboxChips` / `ComboboxChip` / `multiple` mode.** STACK.md suggested `multiple` with chips.
  D-01, D-02, and D-04 lock a different shape: chips are always-visible plain labels under the
  name, and the input appears only on demand behind "+ tag". In base-ui, chips live inside the
  combobox's input container, so they would only render while the editor is open. They would also
  tie remove-a-tag to combobox value state, when it is a plain optimistic API call (D-03).
  Chips are therefore a `Badge`-based `TagChip`, and the combobox picks **one** tag at a time.
  Phase 25's filter bar can still use `multiple` mode.
- `Popover` / `Tooltip`. The full name of a truncated chip is exposed without a tooltip (see [R4]).
- `Card`. The Watchlist row stays `li.rounded-md.bg-card`, unchanged.
- `--color-event-*`, `--color-status-*`, and the `default` Badge variant must never style a tag chip ([R1]).

## Spacing Scale

Same as Phase 6, 19, and 20: Tailwind v4's default scale through default utilities. **No custom spacing tokens.**

| Token | Value | Usage in this phase |
|-------|-------|----------------------|
| xs | 4px | Gap between the name-column lines (existing `gap-1`); icon-to-text gap inside "+ tag" / "add note"; gap between note text and the pencil button |
| sm | 8px | `gap-2` between chips in both axes (8px between adjacent 24px targets, per ui-ux-pro-max "Touch Spacing"); `mt-1` above the chip row and above the note block, which adds to the column's `gap-1` for 8px total; gap between Cancel and Save; `py-2` on Manage tags rows |
| md | 16px | Existing card padding `p-4`; `gap-4` between a Manage tags row's name block and its actions |
| lg | 24px | Dialog / AlertDialog built-in `p-6` and `gap-6` (unchanged registry defaults); 24px chip and small-button height (`h-6`) |
| xl | 32px | `p-8` page gutter, unchanged |
| 2xl | 48px | Not used this phase |
| 3xl | 64px | `EmptyState`'s built-in `py-16` (empty vocabulary inside the dialog) |

**Exceptions:**
- **24px target floor for dense chip-row controls [R3].** `06-UI-SPEC.md` set a 44px minimum hit area
  for icon-only targets. The chip ×, the "+ tag" button, and the edit-note pencil are the documented
  exception: they use a **24×24 CSS px** minimum, which meets WCAG 2.2 AA 2.5.8 Target Size. A 44px target on each ×
  would force every chip row to 44px, or make adjacent targets overlap if extended with a
  pseudo-element. Either would break the compact `h-6` chip row D-01 asks for. Every other target keeps
  its existing size: the remove-artist × stays 44px (`h-11 w-11`) and the preference checkboxes stay `min-h-11`.
- Layout caps that are not spacing tokens: the dialog list `max-h-[min(60vh,28rem)]`, the textarea
  `max-h-40` (160px), and the combobox input `max-w-60` (240px). All are multiples of 4.

### Tag chip treatment and why it cannot be mistaken for a status or event badge [R1]

**Chip markup (locked):**
`<Badge variant="secondary" className="h-6 max-w-full gap-1 pr-0 pl-2 text-label font-normal">`
It contains a `<span class="min-w-0 truncate">{tag name}</span>`, followed by the × `<Button variant="ghost" size="icon-xs">` holding lucide `X` at `size-3`.

**Why `secondary` rather than `outline`:** `outline` is `border-border bg-input/30`, the same
translucent border-and-fill recipe as `Input` and `Button variant="outline"`. A row of outline
pills would read as a row of empty input fields or buttons, which fights D-04's "chips are plain
labels". `secondary` is an opaque, hue-free zinc-800 fill with near-white text. It reads as a
static label, and its text contrast is higher (see the contrast table).

**Visual distinctness from the app's other badge families.** Three badge families now exist, and each owns a separate visual signature:

| Family | Where | Signature |
|--------|-------|-----------|
| Event-type badge (`06-UI-SPEC.md`) | History event cards only | **Hue**: green, yellow, or fuchsia `--color-event-*`, plus an emoji. It signals *what kind of release happened*. |
| Run-outcome status badge (`19-UI-SPEC.md`) | System view only | **Tinted hue**: a `/15` fill of `--color-status-ok`, `--color-status-warn`, or `--destructive`, with same-hue text. It signals *health*. |
| **Tag chip (this phase)** | Watchlist cards (Phase 25 adds History filters) | **No hue at all**: an opaque neutral zinc-800 fill, near-white 14px regular text, a **trailing × control**, and `h-6` (the other two are `h-5` with 12px medium text). It signals *a user-authored label*. |

A tag chip never takes a tinted fill, never takes colored text, and always carries an ×. That
leaves the user nothing to mistake for a status or event signal. The two colored families mean
something the system decided, while a grey pill with an × is something the user wrote and can
take off again. System's grey `secondary` fallback badge for an unrecognised outcome shares the
fill, but it has no ×, uses 12px medium text, and only renders in the System table, which never
co-renders with Watchlist cards. **Future work:** tag chips must keep this neutral treatment when
Phase 25 puts them on History next to event badges, and "Tag colors" stays a deferred Future
Requirement (REQUIREMENTS.md).

### Contrast pairs to verify [R8]

Computed from the token values in `app.css`. The executor re-measures them in the running app (Checker Sign-Off item).

| Element | Foreground | Background | Required | Computed |
|---------|------------|------------|----------|----------|
| Chip text | `--secondary-foreground` oklch(0.985 0 0) ≈ `#fafafa` | chip fill `#27272a` | ≥ 4.5:1 (text) | ≈ 14.2:1 |
| Chip × glyph (rest) | `text-muted-foreground` oklch(0.705 0.015 286) ≈ `#a1a1aa` | chip fill `#27272a` | ≥ 3:1 (non-text) | ≈ 5.8:1 |
| Chip × glyph (hover/focus) | `text-foreground` ≈ `#fafafa` | chip fill `#27272a` | ≥ 3:1 | ≈ 14.2:1 |
| "+ tag" / "add note" / "max 10 tags" / note text / counters | `text-muted-foreground` ≈ `#a1a1aa` | `--card` `#18181b` | ≥ 4.5:1 | ≈ 6.9:1 |
| Note-save error | `--destructive` `#dc2626` | `--card` `#18181b` | ≥ 4.5:1 | ≈ 3.7:1. **Flag.** This is the same pair Phase 19 and Phase 20 already ship for inline error lines (`refreshError`, the digest save failure). This phase does **not** add a token, so it follows the existing `text-label text-destructive` convention. If the measurement confirms the value is below 4.5:1, the fix is **project-wide**, for example a lighter destructive text value such as red-500 `#ef4444` at ≈ 4.7:1. **The chip fill does not need 3:1 against `--card`.** Its boundary is ≈ 1.3:1, but the chip is a

glyph would risk failing 3:1.

not primary: the page's primary action is still "Add to Watchlist" in search results.

### Watchlist card name column (D-01, D-05)

The existing column `flex min-w-0 flex-1 flex-col gap-1` gains two blocks after the disambiguation line:

```
[artist name — text-heading, truncate]                       (unchanged)
[disambiguation — text-label muted, truncate]                (unchanged, omitted when null)
[chip row]      mt-1  flex flex-wrap items-center gap-2
   [chip ×] [chip ×] … [+ tag] | [combobox input] | "max 10 tags"
[note block]    mt-1
   note present:  <p line-clamp-2> … </p> [pencil]   then  [more|less] when truncated
   note empty:    [add note]
   editing:       <Textarea/>  then  [counter …… Cancel Save]  then  [error line]
```

- **Chip row trailing slot**, exactly one of three:
  1. `+ tag`: `Button ghost xs`, `h-6 text-label text-muted-foreground hover:text-foreground`, leading `Plus` (`size-3`, `aria-hidden`). Shown when the artist has fewer than 10 tags (counting optimistic chips).
  2. The **combobox input**, in place of "+ tag" while the editor is open (D-02): `h-8 w-full max-w-60 text-label`. The row grows by 8px only while the editor is open.
  3. `max 10 tags`: plain `<span class="text-label text-muted-foreground">`, shown when there are exactly 10 tags (D-14). It is not a control.
- Zero tags: the chip row holds only "+ tag". It never renders an empty-row gap.

**Row height at the extreme (10 tags × 32 characters) [R4]:** accept **unbounded flex-wrap**, with no "+n more" disclosure. Reasons:
(a) the 10-tag cap (TAG-04) bounds the worst case. With one chip per line in a narrow column that is 10 × 24px + 9 × 8px = **312px**, and a typical row is 1–2 lines.
(b) A disclosure hides values and adds a control per card, and Phase 25's tag filtering is more useful when every tag on every card is visible.
(c) D-01 already says chips wrap in the name column.
The chip-row container therefore never gets `overflow-hidden`, `max-h-*`, or `line-clamp`. Nothing is ever clipped.

**Single chip wider than the column [R4]:** chip labels stay on one line (`whitespace-nowrap`, from Badge). Only a chip whose label is wider than the column truncates, through the inner `min-w-0 truncate` span with the chip at `max-w-full`. The full name stays reachable for everyone:
- **Pointer:** `title={name}` on the label span.
- **Screen reader:** the × accessible name `Remove tag {name} from {artist}` carries the full name.
- **Sighted keyboard:** while the chip's × has focus (`group-focus-within/chip`), the label switches to `whitespace-normal break-all` and the chip to `h-auto min-h-6 py-0.5`, so the full name wraps visibly for as long as focus stays there. A title attribute alone is never the only way to recover the name.

**Note block (D-05):**
- **Present:** `<div class="flex items-start gap-1">` holds `<div class="min-w-0 flex-1">`, with `<p id="note-{id}" class="text-label text-muted-foreground whitespace-pre-line break-words line-clamp-2">` and then the "more"/"less" toggle. The pencil `Button ghost icon-xs` (lucide `Pencil`, `size-3`) sits after that div.
  - **"more"/"less"** is a native `<button type="button" class="text-label text-muted-foreground underline underline-offset-4 hover:text-foreground focus-visible:ring-[3px] focus-visible:ring-ring/50 rounded-sm">` with `aria-expanded` and `aria-controls="note-{id}"`. It renders **only when the clamped text actually overflows** (`scrollHeight > clientHeight`, re-measured on resize). Expanded, the `<p>` drops `line-clamp-2`. jsdom cannot measure layout, so tests stub the measurement.
- **Empty:** only the "add note" button (`Button ghost xs`, `h-6 text-label text-muted-foreground hover:text-foreground`, leading `NotebookPen` at `size-3`, `aria-hidden`).
- **Editing (D-06):** in place of the note block: the `Textarea` (`text-label`-sized text at `md`+, `max-h-40`), then a row `flex items-center justify-between gap-2` holding the counter on the left and `Cancel` + `Save` on the right, then the always-mounted error region.

### Manage tags dialog (D-07, D-08, [R7])

```
DialogContent  sm:max-w-lg  max-h-[calc(100dvh-2rem)]  grid-rows-[auto_1fr]
  DialogHeader:  DialogTitle "Manage tags" (text-heading font-semibold)
                 DialogDescription (text-label muted)
```

- **Deferred:** in-dialog search/filter over the vocabulary. The vocabulary can grow without bound (D-12), so filtering will eventually be needed, but it is **not in scope** for Phase 24. Record it as a future need.

## Interaction Contract

### Tag autocomplete (TAG-01, TAG-03, D-02, D-15)

- **Mode:** base-ui Combobox in **single-value** mode with a controlled `value={null}`. It resets after every pick, so each pick is one attach.
- **Items:** the global vocabulary (D-13, which includes tags carried only by removed artists) **minus** tags already on this artist. Sorted by name. Filtered with a case-insensitive, whitespace-collapsed *contains* match on the input.
- **Ordering rule (deterministic Enter):** let `q` be the input after trimming and collapsing whitespace.
  1. If `q` matches a vocabulary tag after lower-casing (TAG-03), **that tag is pinned first**, shown in its stored casing. No create row appears. So `Reggaeton ` pins `reggaeton`.
  2. Otherwise, if `q` is non-empty, **`Create “{q}”`** (leading `Plus` icon) is pinned first.
  3. The remaining partial matches follow, sorted by name.
  `autoHighlight` is on, so **Enter always commits what was typed**, whether that is the existing tag or a new one. Arrow keys reach the other suggestions.
- **Already on this artist:** if `q` matches a tag already on the card, the list shows the non-selectable `ComboboxEmpty` line `“{name}” is already on this artist` and Enter does nothing.
- **Empty vocabulary and empty input:** `ComboboxEmpty` shows `Type a name to create a tag`.
- **Input:** `maxLength={32}` (D-15 hard stop), placeholder `Tag name`, `aria-label="Add tag to {artist}"`, and `aria-describedby` pointing at the counter.
- **Counter (D-15):** appears once `q.length ≥ 25` (7 characters left). It reads `{n}/32` in `text-label text-muted-foreground tabular-nums` inline after the input, and switches to `text-foreground` at 32. Hitting the cap is not an error, so the counter never turns red.
- **Commit (D-03, optimistic):**
  1. The chip appears immediately at the end of the row with the typed or picked display text.
  2. Its × is `disabled` until the request settles, so a tag cannot be removed before it exists.
  3. On success the chip label updates to the server's stored casing (TAG-03, first-entered casing wins), and a newly created tag joins the route's vocabulary, so other rows and Manage tags see it with no reload.
  4. On failure the chip is removed and the matching error toast fires.
- **After a successful pick:** the input **stays open, cleared, with focus kept in it**, so several tags can be added in a row. The exception is the pick that brings the artist to 10: the editor closes and focus moves to **the new chip's ×** (see Focus management).
- **Close:** **Esc** closes the popup and the editor together in one press. **Blur** (focus leaves both input and popup) also closes the editor. Uncommitted text is discarded, never auto-attached.
- **Chip clicks:** the chip label does nothing (D-04). It gets no hover style, no pointer cursor, and no role.

### Chip remove (TAG-02, D-03)

The × is `Button ghost size="icon-xs"` (24×24), `-ml-1`, `text-muted-foreground hover:text-foreground`, with `aria-label="Remove tag {name} from {artist}"`. The × is not red on hover: removing a tag is low-stakes and easy to redo, unlike removing an artist.
- **Optimistic:** the chip disappears at once, and on failure it is restored in its original position with a toast.
- **Cap freed:** removing a chip from a 10-tag artist restores "+ tag" in place of the hint (D-14).

### Note editor (NOTE-01, D-05, D-06, [R2])

- **Open:** "add note" or the pencil. The textarea mounts pre-filled with the current note (or empty), **with focus in it** and the caret at the end.
- **Attributes:** `maxLength={500}`, `aria-label="Note for {artist}"`, placeholder `Add a note about this artist`, and `aria-describedby` pointing at the counter.
- **Counter:** **always visible while editing**, reading `{n}/500` (`text-label tabular-nums`, `text-muted-foreground`). It switches to `text-foreground` at ≥ 450.
- **Keys:** Enter inserts a newline. **Ctrl+Enter / Cmd+Enter saves.** **Esc cancels** (D-06), discarding edits with no confirmation.
- **Save enablement:** Save is `disabled` while the trimmed text equals the current note.
- **Saving normalization:** the text is trimmed. Empty or whitespace-only text **saves as a cleared note** (`null`, D-06).
- **In flight:**
  - Save becomes `disabled` and reads **`Saving…`** at the same width. The button carries `min-w-20` so there is no layout shift.
  - The textarea becomes **`readOnly` (not `disabled`)**, so focus stays put and the text keeps full contrast. It also gets `aria-busy="true"`.
  - Cancel is `disabled` and Esc is ignored.
- **Save success:** the editor closes and the note renders (or "add note" returns if cleared). Focus goes to the new trigger (see Focus management).
- **Save failure [R2]:** **the textarea stays open with the user's text intact.** The always-mounted `<p aria-live="polite" class="text-label text-destructive">` below the controls shows the error copy. `readOnly` is lifted and Save re-enables for retry. The error clears on the next Save attempt or on Cancel. **This deliberately does not reuse the chip pattern of optimistic rollback plus toast (D-03).** Losing typed prose costs more than losing one discrete toggle. The precedents are the keep-stale-and-inform posture of `14-UI-SPEC` (passphrase kept on error) and `19-UI-SPEC` D-12 (refresh failure keeps data).

### Manage tags: rename, merge, delete (TAG-05, TAG-06, D-09, D-11, D-16, D-17)

**Data and loading**
- **Open:** the dialog **re-fetches the vocabulary with counts on every open**, because counts go stale when cards change.
- **Loading:** 3 `Skeleton` rows (`h-10`) inside the list region.
- **Failure:** `EmptyState` with a `secondary` Retry button, inside the dialog.

**Rename**
- **Keys:** Enter saves and Esc cancels **the rename only**. Esc in the rename input is handled there and does **not** close the dialog.
- **Save enablement:** Save is disabled when the trimmed name is empty or identical, casing included, to the current name.
- **Plain rename:** a case-only change (`Latin` → `latin`) is a plain rename, never a merge (D-09).
- **In flight:** Save reads `Saving…` and the input is `readOnly`.
- **Collision:** when the normalized new name belongs to a *different* tag, the merge ConfirmDialog opens, stacked over the Manage tags dialog. Nothing merges without its confirmation.
- **Failure:** the input stays open with its text and a toast fires.

**Merge ConfirmDialog**
- **Actions:** Cancel, and the primary **Merge tags** button.
- **In flight:** the action reads `Merging…` and both buttons are disabled.
- **Success:** the ConfirmDialog closes, the source row disappears, and the target row shows its new count. A toast fires and the Watchlist cards update with no reload (D-17).
- **Cancel:** returns to the still-open rename input with the typed text intact.

**Delete**
- The row's **Delete** opens the delete ConfirmDialog (Cancel, and the destructive **Delete tag** button).
- **In flight:** the action reads `Deleting…`.
- **Success:** the row is removed, a toast fires, and cards update with no reload (D-17). There is no undo.
- **Count:** it includes watched artists only (D-11), while links to removed artists are still deleted.

**Failure on either confirm:** the ConfirmDialog closes, the matching toast fires, and focus returns per the focus table.

### Focus management [R5]

| Surface | Event | Focus goes to |
|---------|-------|---------------|
| (a) Chip row | "+ tag" activated | the combobox input |
| (a) | Esc, or blur closing the editor | the "+ tag" button. If the editor closed by blur, focus is already wherever the user moved it, so it is not pulled back. |
| (a) | Successful pick with the count still < 10 | stays in the input, now cleared |
| (a) | Pick that reaches 10 tags | the new chip's × (the "+ tag" button no longer exists) |
| (a) | That 10th attach then fails and rolls back | the restored "+ tag" button |
| (b) Chip × | Chip removed | the **next chip's ×**, else the **previous chip's ×**, else "+ tag" |
| (b) | Removal fails and the chip is restored | stays wherever focus had moved (the toast reports the failure) |
| (c) Note | "add note" or pencil activated | the textarea, caret at the end |
| (c) | Esc or Cancel | the trigger that opened the editor ("add note" or pencil) |
| (c) | Save success | the note's **current** trigger: the pencil if the saved note is non-empty, "add note" if it was cleared |
| (c) | Save failure | stays in the textarea |
| (d) Manage tags | Dialog opens | the first actionable element: row 1's **Rename**. With an empty vocabulary or an error, the dialog's close button or Retry. |
| (d) | Dialog closes (Esc, ×, overlay) | the header **Manage tags** button (base-ui's default final focus) |
| (d) | Rename activated | the rename input, all text selected |
| (d) | Rename Cancel or Esc | that row's **Rename** button |
| (d) | Rename success | that row's **Rename** button, which follows the row to its new sorted position |
| (d) | Delete success | the next row's **Rename**, else the previous row's, else the dialog close button |
| (d) | Merge success | the **target** row's Rename button |
| (e) Nested ConfirmDialog | Opens | trapped inside it, first on **Cancel**. Cancel is the safe default for a destructive or one-way action. |
| (e) | Cancel or Esc | the control that opened it: the rename **Save** (merge), or the row's **Delete** (delete) |
| (e) | Any dismissal | **the parent Manage tags dialog stays open.** Esc closes only the topmost dialog. |

**Mechanism:** base-ui supports nested dialogs. An `AlertDialog.Root` rendered *inside* the open
`Dialog`'s React tree registers as a child: Esc and outside-press dismiss only the topmost popup,
and the parent's focus trap yields to the child's. An AlertDialog also ignores outside presses by
design. **Verify at implementation** with a component test covering four points: Esc on the
ConfirmDialog leaves the Manage tags dialog open, Cancel restores focus as listed above, focus
cannot tab out of the ConfirmDialog, and Esc in the rename input does not close the parent dialog.
Pass `initialFocus` / `finalFocus` explicitly wherever the table differs from base-ui's defaults.

### Live regions [R6]

These follow the ui-ux-pro-max rule "Contextual Live Badge Updates": **one** contextual, atomic
message rather than a live region per chip, and never a bare number.

### Primary CTA, empty, error, destructive (checker summary)

- **Primary CTA this phase:** `Save` (note editor), plus `Merge tags` in its confirm. Both are verb-first and specific to their context.
- **Empty states:** `No tags yet` in the dialog; `add note` and `+ tag` on the card. An empty chip row or empty note renders no blank space.
- **Error states:** each names the problem and the next step, either `— try again.` or `— remove one first.`, or keeps the user's input (note).
- **Destructive actions:**
  - **Delete tag:** a count-stating ConfirmDialog.
  - **Merge:** a ConfirmDialog naming both tags. It is one-way, so it gets a confirm even though it uses the primary style.
  - **Remove tag chip:** no confirm, because it is reversible by re-adding (D-03).
  - **Clear note:** no confirm, because it is an explicit Save of empty text (D-06).

## Data Contract (informational — the planner confirms it against the real handlers)

Not owned by this UI-SPEC. It is recorded so the `api.ts` types start from something concrete. `WatchlistEntry` (`web/app/lib/api.ts:61`) gains:

```ts
tags: { id: number; name: string }[]   // sorted by name; [] when none (never null)
note: string | null                    // null = no note (singular, CONTEXT D-28)
```

`GET /tags` returns `{ id, name, carrier_count }[]` (carriers only, D-11). The rename-collision
409 carries `{ target: { id, name }, carrier_count_after_merge }`, and the merge call names its
target by id. Routes and status codes are fixed in CONTEXT D-20…D-27. The note saves through
`PUT /watchlist/{id}/note`, not PATCH. Every call goes through `apiFetch`, whose 401 interceptor
already covers them.

**Optimistic chip state (CONTEXT D-24, amends D-03):** chip add/remove uses functional route-level
updaters, and pending chips are held in a per-row pending set keyed by a temporary id. A rollback
removes only its own item, and a `refresh()` never wipes a pending chip. The client's exact-match
pinning applies `.normalize("NFC")` before lower-casing (D-31).
