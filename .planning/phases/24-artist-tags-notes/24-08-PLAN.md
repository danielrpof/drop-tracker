<objective>
Close verification gap 1 (SC2 / TAG-04, code review WR-03). Today the per-artist cap trigger fires on `BEFORE INSERT` only,
so a raw `UPDATE artist_tags SET artist_id = <artist at 10 links>` gives that artist an 11th link with no error. Add
additive migration 000011. It re-creates `check_artist_tags_max_per_artist()` with an early return for UPDATEs that leave
`artist_id` unchanged, and attaches the function to a new `artist_tags_cap_update_trigger BEFORE UPDATE OF artist_id`.
With that in place, the database refuses an 11th link whether it arrives by INSERT or by moving an existing link. Merge's
`UPDATE ... SET tag_id` stays untouched (D-19).

Why a new migration rather than editing 000010: 000010 is not yet in a release tag (v1.13.1 ships through 000009). However,
the dev database and every developer fixture have already applied version 10. golang-migrate never re-runs an applied
version, so an in-place edit would silently leave those databases on the INSERT-only trigger.

Purpose: make SC2's "the database refuses it even when the API check is bypassed" true for every write path that can add
a link to an artist.
Output: the 000011 up/down pair, five new DB-level tests in `internal/db/tags_schema_test.go`, bumped schema-version pins, an
ADR 0004 amendment, and the migration applied to the live dev database.
</objective>
