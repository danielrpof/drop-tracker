<objective>
Close the re-verification BLOCKER (24-VERIFICATION gap 1, code review CR-01). SC2 / TAG-04 says the database refuses an
11th link even when the API check is bypassed. That is still false under concurrency. The shared trigger function
`check_artist_tags_max_per_artist()` (000010, re-created by 000011) short-circuits with a plain `IF EXISTS` visibility test.
A link that another transaction is deleting but has not committed still looks present. So a re-attach or a move of that same
link skips the artist lock and the count. After the deleter commits, the row is written anyway, and a third attach of a
different tag counts 9 and lands an 11th link. The verifier reproduced this on both the INSERT and the UPDATE path, and
confirmed that the `FOR KEY SHARE` rewrite closes it.

Ship that rewrite as additive migration 000012, which re-creates the function only (D-18's skip-existing semantics are kept,
now proven under a row lock). Pin the exact three-session interleaving with forced, `pg_stat_activity`-gated DB tests that
fail on 000011's body and pass on 000012's. Make the WR-07 subtest pin the guard it claims to pin. Amend ADR 0004 and apply
000012 to the live dev database.

Why 000012 rather than editing 000011: the dev database and every developer fixture already applied version 11, and
golang-migrate never re-runs an applied version. An in-place edit would silently leave those databases on the racy body.

Purpose: make "the database refuses it even when the API check is bypassed" true under concurrency, not just for serial writes.
Output: the 000012 up/down pair, new and updated DB tests in `internal/db/tags_schema_test.go`, bumped schema-version pins, an
ADR 0004 amendment, and the migration applied to the live dev database.
</objective>

The helper drives exactly the S1/S2/S3 interleaving in `<behavior>`:
- Seed through `seedArtistNamed` (suffix `label + "-a"`) and `insertTag`, naming tags with the `label` prefix so repeated runs in one test never collide.
- Derive a context with a 20 s timeout (`context.WithTimeout`) for every statement, so a wedged statement is cancelled instead of hanging.
- Run S2 in a goroutine that holds its own `pool.Begin` transaction. It reports its PID on one channel and its statement error on another, then waits on a release channel before committing and reports the commit error.
- Run S3 on `pool.Acquire` (PID from `conn.Conn().PgConn().PID()`) in a second goroutine. It sends its statement error on a channel and releases the connection.
- Gate S2 by polling `pg_stat_activity` (50 ms interval, 5 s deadline) for `wait_event_type = 'Lock'` before committing `tx1`. If S2 is never seen waiting, fail with a message saying the race window was not opened.
- Gate S3 with one loop, same interval and deadline. It non-blockingly checks S3's result channel (a result means `s3ReturnedEarly = true`) and polls S3's PID for `wait_event_type = 'Lock'`. If neither happens before the deadline, fail. The test never releases S2 until one of the two has been observed. Without this gate a 000011 database could pass vacuously.
- Then release S2, collect S2's commit error and S3's result, and read `finalCount` with `SELECT count(*) FROM artist_tags WHERE artist_id = $1`.
- Every early exit must first release S2 (close the release channel exactly once) and roll back `tx1`. `pgxpool.Close` in the pool's `t.Cleanup` waits for every acquired connection, so a leaked blocked goroutine would hang the test binary instead of failing it.
- Never call `t.Fatalf` from a goroutine (review WR-05). Goroutines send errors on channels, and only the test goroutine fails the test.
- At most 3 connections are held at once (`tx1` or S3, plus S2, plus the poll), which stays under the pool's MaxConns of 4.
