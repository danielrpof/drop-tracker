<objective>
Give the tag vocabulary its global operations: list with watched-only counts, rename, merge-on-collision,
and delete. List is the tracer (it is also the autocomplete source plan 24-05 lazy-loads, D-30), then
rename + delete, then the merge transaction.

Purpose: TAG-05 and TAG-06 on the server, and the one read the card autocomplete and the Manage tags
dialog both use (D-22).
Output: four new `queries/tags.sql` query groups, `Service.List/Rename/Merge/Delete`, four handlers and routes.

Context-drift notes:
- D-22 says a merge "returns 404/409" when the target was renamed or deleted meanwhile. With the locked
  `{into: <target_id>}` body the server cannot tell a renamed target from an unchanged one, so this plan
  implements: 404 `tag not found` when the source or the target no longer exists; 400 when `into` equals the
  source id; a renamed target is merged into under its current stored name (D-23). The SPA treats any non-2xx
  as the merge-failed toast. The residual (a target renamed from a second tab while the modal confirm is open)
  is accepted as T-24-15.
- RESEARCH's `Service.Merge` sample uses `s.pool.Begin`; here it is `s.db.Begin` on the `tags.DB` seam from plan 24-01.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser -> GET/PATCH/DELETE /tags, POST /tags/{id}/merge | Untrusted ids and names; the operator session and CSRF header gate every call. |
| Service -> Postgres transaction | Merge rewrites many rows; ordering and locking decide whether a legal merge trips the cap or deadlocks. |
