<objective>
Give the running binary a truthful identity: the commit it was built from, injected at
link time in CI and falling back to `dev` for any local build.

Purpose: feeds `/status`'s `instance.app_version` (STAT-01) and Phase 19's about block
(SYS-02). It is also the only per-image provenance signal this project has.
Output: `internal/buildinfo` (`Version`, `Short`), a `VERSION` build argument and the
`-X` link flag in the Dockerfile, the matching build argument on the CI build step, and a
pipeline assertion that the shipped binary really carries it.
</objective>

## Locked decisions this plan implements

| Decision | Shape locked here |
|---|---|
| D-13 (changed) | The version is `${{ github.sha }}` passed as a build argument on the `build-scan` image build. Not the svu tag: svu runs in `release`, after the build, and injecting it would force either an svu computation inside the sensitive build job or a second build in `release` — which is exactly the single-build guarantee 07-REVIEW CR-02 established. |
| CONTEXT `<specifics>` | The fallback string for a flagless local build is `dev`. |
| CONTEXT `<specifics>` | The about block shows a short SHA. |

**Planner calls made under 18-RESEARCH.md's open questions, locked here:**

- **Inject the full 40-character SHA; truncate for display in Go** (`Short()`, 12
  characters). This keeps the CI change to a single build argument with no cut step, and
  keeps full traceability inside the artifact.
- **`ARG VERSION` carries no default.** The Dockerfile's standing rule is that no `ARG` or
  `ENV` instruction may carry a configuration value. Rather than write an exception into
  that rule for a default, the argument is declared bare and the link flag substitutes
  `dev` when it is unset — so the rule keeps holding literally, and the Go package's own
  `dev` fallback stays the single definition of the fallback. The comment block still gets
  one amending sentence, because a bare `ARG` is new and a reader must be told why it is
  not a configuration value.
- **The pipeline asserts the injection worked.** 18-RESEARCH.md assumption A6 records that
  nothing today would notice a silently-ignored link flag. A step in `build-scan` extracts
  the binary from the image it just built and greps for the SHA. This is cheaper and more
  direct than standing an app plus a database up to call `/status`.

## Pitfalls this plan is specifically written against

- **A wrong `-X` import path is silently ignored by the Go linker — no error, no warning.**
  The version would stay `dev` on every production image and nobody would notice. The flag
  must name the fully-qualified module path. Two gates below exist only for this.
- **The Dockerfile's top comment forbids an `ARG` carrying a configuration value.** A diff
  that adds `ARG` without amending that block will be bounced on review, and rightly.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CI workflow expression → shell script | A GitHub context value crosses into a `run` body; this is the standard expression-injection surface in Actions. |
| build argument → shipped image layer | Whatever is passed as a build argument may persist in image metadata and layers, which are published to a public registry. |
| built image → registry consumers | The pushed image must be the one that was scanned; anything that reintroduces a second build breaks that identity. |
