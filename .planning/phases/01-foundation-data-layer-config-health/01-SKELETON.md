# Walking Skeleton — drop-tracker

**Phase:** 1
**Generated:** 2026-08-05

## Capability Proven End-to-End

An operator can run `docker compose up -d --wait postgres`, start the single `drop-tracker`
binary with nothing but environment variables, and `curl http://localhost:8080/health` to
receive `200 {"status":"ok","db":"up"}` — proving that configuration parsing, structured
logging with request-ID correlation, the Postgres connection, migrate-on-boot, sqlc codegen,
and HTTP routing are all wired together in one process.

### Interpretation of the "UI — one interactive element wired to the API" checklist item

drop-tracker is an API-first backend service. CLAUDE.md and ROADMAP.md both scope the
React/Vite frontend to **Phase 6 (Frontend & Release History)**, and CONTEXT.md's locked
phase boundary explicitly excludes any UI, watchlist, or external-API logic from Phase 1.

This skeleton therefore treats **the `/health` HTTP endpoint itself as the interactive
element**. For a headless service the HTTP API *is* the interaction surface, and it is
exercised by a documented, runnable command:

```
docker compose up -d --wait postgres
DATABASE_URL='postgres://drop_tracker:drop_tracker@localhost:5432/drop_tracker?sslmode=disable' go run ./cmd/server
curl -sS -D - http://localhost:8080/health
```

This is a deliberate scope decision recorded here so it is not later read as an oversight or
as a skipped skeleton item. No frontend work was invented to satisfy the checklist. The first
real UI slice — search for and add an artist — is Phase 6 / UI-01.

## Architectural Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Language / runtime | Go 1.23+ (1.25 recommended) | Locked in PROJECT.md and CLAUDE.md — portfolio differentiation and closer fit to the systems/DevOps practice that is the point of the project. |
| Module path | `github.com/danielrpof/drop-tracker` | Matches the `origin` remote, so `go get` and ghcr.io image naming line up with the repository from day one. Rated **costly** to reverse: every package import in Phases 2-7 inherits it. |
| Process architecture | One binary, one entrypoint: `cmd/server/main.go` | PROJECT.md locks a single Go binary/service — API, scheduler and notifier share one process. RESEARCH.md flags the generic `cmd/api/` + `cmd/worker/` split as the top structural risk for this phase; taking it would force a disruptive restructure when Phase 3 adds the scheduler. |
| HTTP router | `go-chi/chi/v5` v5.3.1 | Locked in CLAUDE.md. 100% `net/http`-compatible, ~1000 LOC, zero external deps; every middleware in the stack composes on plain `http.Handler`. |
| Data layer | `jackc/pgx/v5` v5.10.0 via `pgxpool`, queries generated by `sqlc` v1.31.1 with `sql_package: "pgx/v5"` | Locked in CLAUDE.md. `lib/pq` is maintenance-only; sqlc's pgx target generates against `pgxpool.Pool` directly, so the two idioms must not be mixed. |
| Schema migrations | `golang-migrate/migrate/v4` v4.19.1, `.sql` files embedded with `go:embed` + `iofs`, applied by the service at boot | D-09: no separate manual migrate step for normal operation. Embedding means the binary is self-sufficient — no migration files to ship alongside the image in Phase 7. |
| Startup failure policy | Fail fast: bounded retry then `exit(1)` — 6 attempts, 500ms base delay doubling to an 8s cap (~20s worst case) | D-05 and D-10. Long enough for a Postgres container cold start, short enough that a genuinely dead database fails loudly instead of hanging. Parameters are exported named constants, not inline literals. |
| Configuration | `caarlos0/env/v11` v11.4.1, environment variables only, `notEmpty` on the DSN | D-05, OPS-03. `notEmpty` rather than plain `required` because `required` accepts a variable set to the empty string, which is exactly the half-configured boot the decision forbids. No configuration file, no dotenv auto-loading, no hardcoded fallback that can beat an operator-supplied value. |
| Configuration surface | The `Config` struct declares every setting through Phase 5 now, with optional defaults | D-06, D-07: the struct is the single source of truth from day one; a later phase starts *reading* a field rather than *adding* one. Rated reversible — adding or removing struct fields is a cheap local change. |
| Logging | stdlib `log/slog` + `go-chi/httplog/v3` v3.4.0; JSON by default, text opt-in | D-08 (`LOG_LEVEL=info`, `LOG_FORMAT=json` are production-sane defaults). httplog is maintained by the chi org itself and integrates with chi's `RequestID`/`Recoverer` conventions. |
| Correlation ID | chi's `middleware.RequestID`, echoed to the client as the `X-Request-Id` response header | OPS-02. Phase 3's poll cycles must reuse chi's out-of-request ID generator rather than inventing a second scheme — two competing schemes would make cross-subsystem correlation impossible. |
| Auth | None | PROJECT.md scopes v1 to a single-operator deployment; multi-user auth/SSO is explicitly out of scope. `/health` is intentionally unauthenticated for uptime-monitor consumption. |
| Deployment target | Local `docker compose` for Postgres only in Phase 1; the multi-stage non-root image published to ghcr.io lands in Phase 7 | CICD-03/CICD-07 own containerization. Phase 1 ships only what makes the local full-stack run reproducible. |
| Directory layout | `cmd/server/` for the entrypoint; `internal/{config,logging,db,httpserver,testutil}` for packages; `queries/` for sqlc sources; `internal/db/migrations/` for embedded SQL | RESEARCH.md's Recommended Project Structure. Left to Claude's discretion by CONTEXT.md; purely organizational, cheap to refactor (RESEARCH assumption A3). |
| DB-backed test fixture | Environment-supplied DSN (`TEST_DATABASE_URL`, falling back to `DATABASE_URL`) pointing at the compose Postgres, via `internal/testutil` — **not** `testcontainers-go` | Keeps the test dependency set to what is already in `go.mod`, needs no Docker socket access from inside the test process, and works unchanged against the GitHub Actions Postgres service container in Phase 7. Rated **costly** to reverse: every DB-backed test in Phases 2-7 inherits this shape. |
| Testing | Go stdlib `testing` + `net/http/httptest`; DB-backed tests skip visibly under `-short` or a missing fixture DSN | CLAUDE.md testing constraint. A skip prints `--- SKIP` naming `TEST_DATABASE_URL` so it can never be mistaken for a pass. |
| Initial migration content | One no-op migration pair (`000001_init`) creating no domain tables | D-01 assigns the watchlist schema to Phase 2. RESEARCH assumption A2 asked whether Phase 1 should ship zero migration files; it cannot — Go's embed directive fails to compile when its pattern matches zero files. One no-op migration satisfies D-01 *and* proves the embed → iofs → `schema_migrations` pipeline end-to-end. |

## Stack Touched in Phase 1

- [x] **Project scaffold** — Go module with six pinned dependencies, `cmd/` + `internal/` layout, `go vet`, `go build`, `Makefile` targets, `docker-compose.yml`
- [x] **Routing** — one real route, `GET /health`, on a chi router with the RequestID → httplog → Recoverer middleware stack
- [x] **Database** — a real write (golang-migrate applying `000001_init` and writing the `schema_migrations` row) and a real read (`pool.Ping` in the handler, plus the sqlc-generated query executed in `TestSQLCPing`)
- [x] **UI** — interpreted as the `/health` HTTP surface for this headless service; see the interpretation note above
- [x] **Deployment** — documented local full-stack run: `docker compose up -d --wait postgres` then `make run`, with `make test-integration` as the automated equivalent

## Out of Scope (Deferred to Later Slices)

Explicit so later phases do not re-litigate Phase 1's minimalism:

- Domain tables of any kind — artists, watchlist, seen-store, events (Phase 2 owns the watchlist schema, D-01)
- Watchlist CRUD API and the service layer over it (Phase 2)
- MusicBrainz and Deezer clients, rate limiters, and the live search proxy (Phase 3)
- `robfig/cron` scheduler and any poll cycle — including poll-cycle log lines, which ROADMAP success criterion 2 mentions but which cannot exist before the scheduler does (Phase 3)
- Detection/diff engine and the "seen" store (Phase 4)
- Discord webhook notifier (Phase 5)
- React + Vite SPA and `go:embed` of the built bundle (Phase 6)
- Multi-stage non-root Dockerfile, ghcr.io publish, Trivy, SBOM, gitleaks CI job, `svu` versioning, pre-commit hooks (Phase 7)
- Liveness/readiness split, migration-version reporting on `/health`, Prometheus metrics (D-03; metrics are project-wide out of scope for v1)
- Authentication, sessions, and access control (out of scope for v1 project-wide)
- Distributed locking or leader election for the scheduler (single instance in v1; CLAUDE.md records this as the trigger for revisiting `robfig/cron`)

## Subsequent Slice Plan

Each later phase adds one vertical slice on top of this skeleton without altering its
architectural decisions:

- **Phase 2 — Watchlist Core:** the first domain schema and CRUD slice. Adds migrations under the existing `internal/db/migrations/`, queries under the existing `queries/`, and routes on the existing chi router. Regenerates sqlc through the existing `make sqlc`; the existing `make sqlc-check` guards the result.
- **Phase 3 — External Clients & Search:** `internal/musicbrainz` and `internal/deezer` hand-rolled clients reading `MusicBrainzUserAgent`, `MusicBrainzRateLimitPerSec` and `DeezerRateLimitPer5s` — fields that already exist on `Config`. Adds the in-process `robfig/cron` scheduler to the same `cmd/server` binary, correlating poll-cycle logs with chi's out-of-request ID generator so the log shape matches Phase 1's HTTP lines.
- **Phase 4 — Detection Engine:** diff logic and the "seen" store, plus the project's first deliberate concurrency control (DTCT-05, no overlapping poll cycles) — the Postgres advisory lock the existing pool already makes available.
- **Phase 5 — Discord Notifications:** `internal/discord` posting to `DiscordWebhookURL`, another `Config` field that already exists.
- **Phase 6 — Frontend & Release History:** the React + Vite SPA, built to a static bundle and embedded into the same single binary via `go:embed` — the first slice that makes the "UI" checklist item literal rather than interpreted.
- **Phase 7 — Containerization & CI/CD Pipeline:** the multi-stage non-root image and the full GitHub Actions pipeline. Reuses `make sqlc-check` and `make test` verbatim as CI steps; `docker-compose.yml` grows the app service alongside the Postgres service this phase created.
