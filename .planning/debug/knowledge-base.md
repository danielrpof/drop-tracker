## guest-feature-label-missing — watchlist label never rendered on guest-feature cards because a new nullable column was never backfilled
- **Date:** 2026-08-25
- **Error patterns:** no error message, silent missing UI element, label/note not rendering, conditional render returns null, column all NULL, nullable ADD COLUMN without backfill, ON CONFLICT DO NOTHING, write-once insert, stale historical rows, feature works for new data but not existing data, watched_artist_name, guest_feature, EventCard watchlistNote
- **Root cause(s):** AND-gate — two conditions simultaneously required, neither sufficient alone. (1) Migration `000006` added `events.watched_artist_name` as a nullable column with **no backfill**, leaving all 1613 pre-existing rows NULL; AND (2) `InsertEvent` uses `ON CONFLICT (event_type, source, external_id) DO NOTHING` (D-20's deliberate write-once snapshot semantics, explicitly *not* the COALESCE-refresh shape `UpsertArtist` uses), so re-detecting an already-seen recording updates nothing. Together the NULL becomes permanent instead of self-healing; `EventCard`'s `watchlistNote()` then correctly early-returned `null` for the falsy value, suppressing the note on all 244 guest_feature cards. The code was correct throughout — it had no data to act on.
- **Fix:** Migration `000007_backfill_events_watched_artist_name` — an idempotent data repair setting `watched_artist_name = artists.name` via `events.artist_id` `WHERE watched_artist_name IS NULL`. Exact reconstruction rather than a guess: both detection call sites build a row from one watchlist entry, setting `ArtistID: entry.ArtistID` alongside `watchedName := entry.Name`, so the value is by construction the name of the artist `artist_id` already points at. `IS NULL` scoping makes it idempotent and unable to clobber a live snapshot. Down migration is a documented no-op (`000006`'s own down drops the column).
- **Files changed:** internal/db/migrations/000007_backfill_events_watched_artist_name.up.sql, internal/db/migrations/000007_backfill_events_watched_artist_name.down.sql, internal/db/migrate_test.go
- **Why not caught:** No gate existed for this class. Every gate the originating quick task (260825-g6i) ran was green and *could not* have caught it: Go unit tests and `EventCard.test.tsx` construct their own fixtures with the column populated, so they exercise the render path with data that never exists in a migrated database; `TestRunMigrations_AppliesFromScratch` runs against an **empty** `events` table, where a missing backfill is invisible by construction (zero rows trivially satisfy any backfill); `tsc`/`go vet`/`golangci-lint` cannot see data state. The verify/UAT step passed because the *other* change in the same task (release-chronology ordering) is a pure read-side query change needing no new column data, which masked the label regression. Nothing in review or CI asks "does this `ADD COLUMN` need a backfill for existing rows, and can the write path ever heal them?"
- **Recurrence guard:** Primarily this KB entry — the diagnostic pattern **"nullable `ADD COLUMN` + write-once `ON CONFLICT DO NOTHING` insert = permanently NULL historical rows"** — so a future Phase-0 recall surfaces it on any "feature works for new records but not existing ones" or "UI element silently absent with no error" symptom. Verified supporting artifact: `internal/db/migrate_test.go:TestRunMigrations_AppliesFromScratch` now asserts `schema_migrations` version `7`, which forces any future migration author to consciously update the expected version (a review touchpoint) — but note this guards migration-count drift only, **not** the backfill class itself. No automated gate for the class was added: an honest guard would be a migration-review checklist item or a lint/test that flags `ADD COLUMN` on a non-empty table whose insert path is `DO NOTHING`. Recorded as an open prevention gap rather than claimed as covered.

## backlog-songs-trigger-discord — an artist's entire back catalogue was delivered to Discord because notification suppression keyed on insert timing, not on how old the release actually is
- **Date:** 2026-08-26
- **Error patterns:** no error message, silent behavioral/logic bug, Discord notifications for old songs, backlog/back-catalogue alerts, old releases announced as new, notifications for releases from years ago, new artist's discography spams alerts, `seed_mode=false` in detection logs, `guest_feature_lookup_cap_reached_at`, `notified_at IS NULL`, ListUnnotified has no release-date predicate, seedNotifiedAt, isSeedMode one-shot latch, maxNewGuestFeatureLookupsPerCycle, per-cycle cap defers work to later cycles, multi-cycle detection pass, guest_feature, release_date, MusicBrainz partial dates, "used to work, started recently"
- **Root cause(s):** AND-gate — two conditions simultaneously required, neither sufficient alone. (1) Backlog suppression was decided by **insert timing** via a one-shot seed-mode latch — `isSeedMode` is `NOT EXISTS(SELECT 1 FROM events WHERE artist_id=$1 AND source=$2)`, true only until the very first event row for that pair exists — but since phase 13 (2026-08-24, commits `b9f0c62`/`2b19467`) the guest-feature pass is **deliberately multi-cycle**: `maxNewGuestFeatureLookupsPerCycle = 20` plus per-recording `ReleasesForRecording` error-skips defer the remainder of an artist's catalogue to later cycles, by which time the latch has flipped and every deferred backlog row is inserted with `notified_at = NULL`; AND (2) the delivery path applied **no release-date filter anywhere** — `ListUnnotified` is a bare `SELECT * FROM events WHERE notified_at IS NULL`, so NULL unconditionally meant "send to Discord". Together, any artist with more than 20 guest features dripped 9–20 back-catalogue rows into Discord every poll cycle, indefinitely, until their multi-hundred-recording catalogue drained. Quantified live: of 249 `guest_feature` rows delivered in one day, 242 had release dates older than a week, reaching back to 2015-05-21, and **0** were dated today. Two decisive signatures separated cause from coincidence: a *shared* `notified_at` across a cohort is `seedNotifiedAt`'s fingerprint (suppressed, no Discord), while *one distinct* `notified_at` per row is `MarkNotified`'s (a real send each) — and the fingerprint flips exactly at the phase-13 commit boundary.
- **Fix:** Replaced the insert-timing latch with a **per-row release-date freshness gate**, applied at both ends of the AND-gate so neither half alone can re-open the flood. (1) Insert side — `internal/detection`'s new `notifyGate` (which retired the now-dead `seedNotifiedAt`) suppresses a row if seed mode is on **or** the release date fails `onOrAfterCutoff`, a stable per-row property, making correctness immune to the lookup cap, lookup errors, rate-limiter stalls, cycle boundaries and restarts. Dates are compared as zero-padded ISO-8601 **strings**, never parsed to `time.Time`, because MusicBrainz dates are legitimately partial (`"2015"`, `"2015-06"`) — the same technique `withinDeluxeRecheckWindow`/`earlierDate` already use. The gate is constructed once per `Detect*` call, preserving D-13 (one seed cycle → one shared timestamp) and preventing a midnight-straddling pass from judging its first and last rows by different cutoffs. (2) Delivery side — `NotifyPending` acks-without-sending any pending row failing the same test, which drains the pre-existing outbox backlog (rows inserted by the old ungated code would otherwise **all** have flushed to Discord on the very first post-fix pass — the exact flood being fixed) and is defence in depth for the second AND-gate condition. Undated releases **suppress** on both sides (user decision), deliberately inverting the codebase's usual "err toward an extra alert" doctrine (`isGuestFeature`, `withinDeluxeRecheckWindow`) because an undated row is absence of evidence rather than evidence of freshness, and the pending backlog was 64% undated. `NOTIFY_MAX_RELEASE_AGE_DAYS` (default 7, rejected if negative) threads one value into both halves by construction; 7 rather than the literal "same date as today" because three normal lags sit between a release dropping and a row being inserted (community-edited MusicBrainz backfill, the 15m poll interval plus the per-cycle cap, and `release_date` carrying no timezone) — a zero-day window would trade this false-positive bug for a strictly worse silent-loss one. Operators wanting the strict reading can set 0.
- **Files changed:** internal/detection/detector.go, internal/detection/musicbrainz.go, internal/detection/deezer.go, internal/notifier/notifier.go, internal/config/config.go, cmd/server/main.go, .env.example, internal/events/service.go, queries/events.sql + internal/db/sqlc/events.sql.go + internal/db/sqlc/querier.go (doc-comment repoint only, hand-edited identically so `sqlc generate` stays a no-op), internal/detection/notifygate_test.go (new), internal/notifier/suppress_test.go (new), internal/notifier/notifier_test.go, internal/detection/detector_test.go
- **Why not caught:** No gate existed for this class, and one gate actively **pinned the bug as intended behaviour**. `internal/detection/detector_test.go:TestDetector_SecondCycleLeavesNotifiedAtNull` asserted, in its name, exactly the mechanism that produced the flood — correct when written (seed-mode *was* the whole design and detection was single-cycle), silently obsolete the moment phase 13 made the guest-feature pass multi-cycle. Phase 13's own tests were green and *could not* have caught it: they verified the cap defers work correctly, which it does. Nothing tested the **interaction** between "detection is now multi-cycle" and "suppression is single-cycle" — the two contracts live in different files (`musicbrainz.go`'s cap, `detector.go`'s latch) and neither's tests knew the other existed. `notifier.suppresses()`' surrounding delivery decision had zero release-age coverage because no such concept existed in the notify path. `go vet`/`golangci-lint` cannot see a semantic contract conflict between two files. Phase 13's verify/UAT step asked "does the cap work, does polling stay under rate limits" — the right questions for that change — not "does an artist with >20 guest features now leak their back catalogue", because the symptom only manifests hours later, in production, for large-catalogue artists, through an **external side effect (Discord) that no test observes**. The general lesson: when a change converts a previously single-pass operation into a multi-pass one, every invariant that silently assumed "one pass" becomes a latent bug, and existing green tests asserting the old timing-based behaviour are the least likely thing anyone thinks to re-read.
- **Recurrence guard:** Real automated gates, all mutation-verified (each was confirmed to fail when the fix is reverted, not merely to pass when it is present). Primary: `internal/detection/notifygate_test.go:TestDetectGuestFeatures_PastLookupCap_BacklogNeverGoesPending` — runs against real Postgres on an artist explicitly **out** of seed mode and past `maxNewGuestFeatureLookupsPerCycle`, the exact condition the old code had no defence for, asserting zero rows go pending; reverting the insert-side gate fails it with `"back-catalogue guest features queued for Discord delivery = 20, want 0"`, reproducing the precise production drip inside the suite. Supporting: `TestDetectMusicBrainz_NonSeedCycle_Backlog...` (same class, new_release pass); `TestNotifyGate_NotifiedAt`'s 13-case seed/freshness truth table mirrored case-for-case by `internal/notifier/suppress_test.go:TestStaleReleaseDate` against a fixed cutoff, so the two halves of the gate are provably in agreement and **cannot drift apart** — which is what would silently re-open the AND-gate; `TestStaleReleaseDate/absent_date_(SQL_NULL)_is_suppressed` pins the undated-suppresses decision specifically (restoring "undated = deliver" fails it); `internal/notifier/notifier_test.go:TestNotifyPending_StaleRowsAckedWithoutSending` models the production outbox at ship time (backlog + undated + partial-date + one fresh row) and asserts exactly one Discord request plus that all four rows are acked — an unacked stale row would be re-suppressed forever; disabling the delivery-side gate fails it with 4 requests, the captured bodies literally showing a 2015 release being posted. Runtime observability guard: the `"notify pass suppressed stale events"` per-pass Info summary makes over-suppression — the one real risk this gate carries — visible in production instead of silent. Plus this KB entry, for the transferable pattern **"a per-cycle cap or deferral added to a pass whose correctness invariant assumed a single cycle"**, and the sharper diagnostic **"suppression keyed on *when* a row was inserted rather than *what* the row is"** — a distinction to reach for on any 'used to work, started recently, only affects large/slow datasets' symptom. Known accepted narrowing, flagged not fixed: `detectDeluxeChanges` is bounded by a 90-day recheck window on the group's first-release date while the notify gate applies the tighter 7-day window to the winning release's date, so a deluxe edition of an 8–90-day-old album is delivered only if MusicBrainz dates the deluxe release itself recently. Zero `deluxe_change` rows have ever existed in production so this narrows nothing observable; exempting the event type is a product decision, deliberately out of scope here, documented in code at the deluxe insert site and to be revisited if `deluxe_change` starts firing and alerts go missing.
