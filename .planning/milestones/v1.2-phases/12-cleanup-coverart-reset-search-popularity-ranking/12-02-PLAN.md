<objective>
Capture Deezer's fan-count popularity signal into `internal/deezer.Artist` (D-03) and rank
`SearchArtists` results by it, descending, inside the Deezer client itself (D-04).

Purpose: Deezer already ships a popularity number on every `/search/artist` result and the
project simply throws it away, so the Watchlist search UI shows Deezer's raw catalogue order
instead of putting the artist the user almost certainly meant first.

Output: one new struct field, one sort in `Client.SearchArtists`, a corrected doc comment,
and the test rewrite that keeps the suite honest about the new ordering guarantee.

Deliberate deviation from 12-RESEARCH.md, recorded here for traceability: RESEARCH.md
Pattern 2 recommends `slices.SortFunc`. This plan specifies `slices.SortStableFunc`
instead. `slices.SortFunc` is not stable, so every artist sharing a fan count (very common
— unmatched artists decode to the zero value) would have Deezer's relevance order scrambled
arbitrarily among the ties. `SortStableFunc` keeps popularity as the primary key while
preserving Deezer's upstream relevance ordering as the tiebreaker, which is what D-04's
intent ("rank by popularity") actually wants. Cost is nil on a slice capped at the
per-source result limit. D-04 itself is unchanged: the sort is by fan count descending and
it lives inside `internal/deezer`.

Planning note (visible skip): spec-less probe fallback skipped — phase has no requirement
IDs to probe. `must_haves` are derived directly from CONTEXT.md's D-03/D-04.
</objective>
