# Phase 18.1: Code Review Report

**Reviewed:** 2026-09-10T08:37:29Z
**Depth:** standard
**Files Reviewed:** 8
**Status:** issues_found

## Summary

Phase 18.1 widens the `EventRecorder` seam (`DetectMusicBrainz` / `DetectDeezer`)
from `error` to `(int, error)` and rewires `internal/poller`'s `runCycle` to
aggregate per-cycle counters through a single-threaded channel fold over
`artistResult` values, plus a `defer`-registered `pollruns.Store.RecordRun` /
`RecordSkip`.

The core concurrency mechanics hold up under scrutiny:

- **Fold is genuinely single-threaded.** Every counter the `RunResult` carries
  (`artistsChecked`, `artistsErrored`, `eventsRecorded`) is derived in the
  post-`wg.Wait()` `for r := range resultCh` loop; `artistsSkipped` is only ever
  touched by the dispatch loop. No worker goroutine writes a shared counter (D-14
  satisfied).
- **`resultCh` buffer is correctly sized.** `cap == len(entries)` and the number
  of goroutines launched is `<= len(entries)` (one per non-skipped entry, fewer on
  a ctx break). Each goroutine sends exactly once, and the send completes before
  the deferred `wg.Done()`, so `wg.Wait()` → `close(resultCh)` can never race a
  send-on-closed-channel.
- **Panic path is correct.** `runOneArtist` uses a named return `res` and the
  deferred `recover()` reassigns it to `{checked:true, errored:true}`; the panic
  value goes only to the correlated log.
- **No information disclosure into `RunResult`.** Every field set in `poller.go` is
  a count, an enum, a timestamp, or the synthetic `source-<n>` cycle id. `Summary`
  is left unset and recomposed by `pollruns.composeSummary` from counts + outcome
  only. The List-error path wraps the driver error into `cycleErr` but that string
  reaches only the operator log, never a `RunResult` field (confirmed by
  `TestRunRecorder_RecordsErrorOutcomeOnListFailure`).
- The detection-package changes (`deezer.go`, `musicbrainz.go`) are a clean,
  mechanical widening — partial counts are returned alongside errors, and
  `DetectMusicBrainz` correctly sums the new-release, guest-feature, and
  deluxe-change pass counts.

No correctness or security BLOCKER was found. Three WARNINGs concern the
interaction between `RecordRun` and the overlap guard, a doc comment that
contradicts the code, and unrecovered panics in the new seam call sites.

## Warnings

### WR-01: `RecordRun` runs inside the overlap-guard critical section — a slow recorder skips the next tick

**File:** `internal/poller/poller.go:364-413`
**Issue:** The `RecordRun` defer is registered *after* `defer running.Store(false)`
(line 364), so LIFO runs `RecordRun` first, with `running` still `true`. The whole
duration of `p.runs.RecordRun(ctx, ...)` is therefore spent holding that source's
overlap guard. If a `RunRecorder` implementation is slow or blocks, every cron
tick that lands during that window is rejected with `ErrCycleInProgress` and a
`RecordSkip` — a lost poll cycle. 18.1-02-PLAN.md itself states "RUN-03 forbids one
that blocks or delays," yet the chosen defer ordering means a blocking recorder
*does* delay the guard release. `TestRunRecorder_ErrorSwallowed`'s "recorder is
slow" leg only asserts the cycle *eventually* returns and the guard is *eventually*
released — it does not assert the guard is free during the `RecordRun` call, so it
does not catch this.

Real-world impact is currently small because the only injected implementation
(`pollruns.Store`) is an O(1) mutex write that cannot block. But `WithRunRecorder`
accepts any implementation and the error-swallow-and-log code path shows the design
anticipates misbehaving recorders.

**Fix:** Register the `RecordRun` defer *before* `defer running.Store(false)` so
LIFO releases the guard first, then records:
```go
// registered first -> runs last (after the guard is released)
defer func() {
    // ... compose RunResult, call p.runs.RecordRun(ctx, result) ...
}()
defer running.Store(false)
```
Trade-off to note in the comment: a near-simultaneous next tick can then begin
before this cycle's entry is appended; `pollruns.Store` is mutex-safe and
`/status` history ordering is cosmetic, so this is acceptable. Alternatively, hoist
the recorder call out of the defer chain to a plain statement after the guard is
released (keeping the `runFinishedAt.IsZero()` fallback for the early-return
paths).

### WR-02: `artistResult.events` doc comment contradicts the code

**File:** `internal/poller/poller.go:304` (comment) vs `poller.go:337`
**Issue:** The struct field is documented as:
```go
events  int  // events recorded for this artist (0 on error / panic / bail)
```
but `runOneArtist` returns the **partial** count on the error path:
```go
events, err := fetchAndRecord(ctx, logger, entry)
if err != nil {
    return artistResult{checked: true, errored: true, events: events} // NOT 0
}
```
and `DetectMusicBrainz` / `DetectDeezer` deliberately return the rows they did
insert before failing (`return newRelease + gf, err`, `return inserted, fmt.Errorf(...)`).
The fold then does `eventsRecorded += r.events` unconditionally, so an errored
artist's partial inserts *are* counted in `RunResult.EventsRecorded` — which is the
correct behaviour (those rows are committed), but the exact opposite of what the
comment says. A future maintainer trusting the comment could "fix" the fold or
`runOneArtist` to drop events on error and silently under-count `/status`.

**Fix:** Correct the comment to state the actual contract, e.g.
`// events recorded for this artist; partial count is kept on error, 0 on panic / ctx-bail`.

### WR-03: unrecovered panic in `RecordRun` / `RecordSkip` (and `NotifyPending` / `store.List`) crashes the process

**File:** `internal/poller/poller.go:227` (`cron.New()`), `poller.go:361`, `poller.go:397`
**Issue:** `cron.New()` is constructed with no `cron.WithChain(cron.Recover(...))`,
so a panic in any cron job propagates out of the goroutine `cron` spawned and takes
down the whole single-binary process. This phase adds two new call sites that run
unguarded: `p.runs.RecordSkip(source)` on the CAS-fail path (line 361) and
`p.runs.RecordRun(ctx, ...)` inside the LIFO-first defer (line 397). A panic in the
`RecordRun` defer is especially bad — it fires during stack unwinding and would
mask any in-flight panic. The recorder-error path is carefully log-and-swallowed to
honour RUN-03 ("a recorder failure must never fail the cycle"), but a recorder
*panic* bypasses that isolation entirely.

`pollruns.Store` cannot currently panic, so this is latent, but the seam is a public
interface and the isolation intent is explicit elsewhere in the same function.

**Fix:** Either wrap the job registration in `cron.New(cron.WithChain(cron.Recover(cronLogger)))`,
or add a `recover()` around the `RecordRun` body in the defer (and around
`RecordSkip`) that logs and swallows, mirroring the existing recorder-error
handling and `runOneArtist`'s per-worker recover.

## Info

### IN-01: `poller` re-declares source string constants instead of reusing `pollruns`' exported ones

**File:** `internal/poller/poller.go:46-47`
**Issue:** `poller.sourceMusicBrainz = "musicbrainz"` / `sourceDeezer = "deezer"` are
independent string literals from `pollruns.SourceMusicBrainz` / `SourceDeezer`. They
are passed straight into `pollruns.RunResult.Source` and `RecordSkip(source)`. If
one pair ever drifts, `pollruns.NewStore` pre-seeds `KnownSources` with the old key
while runs land under the new key, so `/status` shows an empty history for that
source and a phantom bucket holds the data — a silent failure. Integration tests
(`TestPoller_RunMusicBrainzCycle_RecordsNewRelease` etc.) would catch a full
mismatch today, but not a whitespace/casing typo in an untested combination.
**Fix:** Reference `pollruns.SourceMusicBrainz` / `pollruns.SourceDeezer` directly
in `RunMusicBrainzCycle` / `RunDeezerCycle`, or add a compile-time
`const _ = ...; var _ = map[bool]struct{}{sourceMusicBrainz == pollruns.SourceMusicBrainz: {}}`
style assertion.

### IN-02: cancelled-cycle `RunResult` counters do not reconcile against watchlist size

**File:** `internal/poller/poller.go:468-477`
**Issue:** A worker that was dispatched but hit `ctx.Err()` before fetching returns
`artistResult{}` (`checked == false`); the fold does `if !r.checked { continue }`,
so it lands in **no** counter — not `ArtistsChecked`, not `ArtistsSkipped`, not
`ArtistsErrored`. For a cycle cancelled mid-dispatch,
`ArtistsChecked + ArtistsSkipped < len(entries)` with no field explaining the gap.
This is defensible (the `Outcome: cancelled` enum signals "numbers are partial"),
but it is undocumented on `pollruns.RunResult` and a `/status` consumer cannot tell
a cancelled-partial run from a bug.
**Fix:** Add a one-line note to the `RunResult` doc comment that the four artist
counters need not sum to the watchlist size when `Outcome == OutcomeCancelled`, or
add an `ArtistsUnprocessed` count for dispatched-but-bailed entries.

### IN-03: no test asserts the fold's counters for the "dispatched then ctx-bailed" branch

**File:** `internal/poller/poller_test.go` (`TestRunCycle_CounterInvariant`, `TestRunRecorder_RecordsCancelledOutcome`)
**Issue:** `TestRunCycle_CounterInvariant` exercises error + panic artists but never
a worker that takes a `sem` slot and then returns `artistResult{}` via the
`runOneArtist` ctx-bail. `TestRunRecorder_RecordsCancelledOutcome/"cancelled before
dispatch"` asserts all-zero counters but relies on the `select` sometimes picking
`ctx.Done()` first; the branch where a worker actually launches and bails is not
pinned with an exact-equality assertion. Given `go test -race` is unavailable on
this box and absent from CI, the fold's `!r.checked` path is effectively unverified.
**Fix:** Add a looped exact-equality case to `TestRunCycle_CounterInvariant` with a
gated fetch that lets N workers acquire slots, then cancels, and asserts
`ArtistsChecked == (dispatched - bailed)` and `EventsRecorded` exactly, across many
iterations.
