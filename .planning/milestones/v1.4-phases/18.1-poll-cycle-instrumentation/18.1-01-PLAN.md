## Concurrency-Correctness Section — the `-race` substitute (required deliverable)

`go test -race` fails on this dev box (ThreadSanitizer allocation failure under
WSL2) and is absent from CI. Correctness of the new counters is therefore
established **by construction**, not by detector. Five load-bearing points:

1. **No shared mutable counter.** `artists_checked`, `artists_errored` and
   `events_recorded` are derived exclusively by the single-threaded
   `for r := range resultCh` fold, which runs only after `wg.Wait()` has joined
   every worker. `artists_skipped` is incremented only inside the dispatch loop,
   which is itself single-threaded. No worker goroutine writes any variable the
   parent reads. (D-14 forbids the `sync/atomic` alternative explicitly; the
   existing `sync/atomic` import stays reserved for `nextCycleID` and the
   `atomic.Bool` overlap guards.)

2. **Exactly one result per dispatched worker.** Every path through `runOneArtist`
   returns an `artistResult`: success, fetch/detect error, ctx-bail, and — via the
   deferred `recover()` assigning the *named* return — panic. The goroutine body is
   a single unconditional send of that value; it contains no early `return`, so
   dispatched-count and sent-count are equal by inspection.

3. **No worker ever blocks on send.** `cap(resultCh) == len(entries)`, and the
   number of senders is the dispatched count, which is `<= len(entries)` because
   each entry is dispatched at most once. Capacity `>=` senders means every send
   completes immediately, so every worker reaches its deferred `wg.Done()`, so
   `wg.Wait()` always returns and the fold always runs. Sizing the buffer to
   `workers` instead would deadlock `wg.Wait()` forever — this is the single
   easiest way to break this phase.

4. **`sem` and `wg` semantics are unchanged.** The `select` on
   `sem <- struct{}{}` versus `<-ctx.Done()`, the `dispatch:` label and
   `break dispatch`, the `wg.Add(1)` before `go`, the deferred `<-sem` and
   `wg.Done()` and their LIFO order, and both `ctx.Err()` checks (the in-flight one
   now inside `runOneArtist`, the post-join re-check) are byte-identical in
   behaviour to today. The only sanctioned change to the worker body is the
   extraction into `runOneArtist`.

5. **The compensating control** is `TestRunCycle_CounterInvariant`
   (`18.1-03-PLAN.md`): ~1000 internal iterations over a fake source with K
   erroring and P panicking artists, asserting `checked == errored + succeeded`,
   `errored == K + P` and `checked == M - skipped` with **exact equality** on every
   iteration, and run additionally with `-count=3`. A Broken Windows Ledger
   `deviation` entry records the `-race` waiver, matching entries 9 and 10.
</concurrency_correctness>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| worker goroutine → parent `runCycle` frame | Per-artist results cross a goroutine boundary; a shared mutable counter here is a data race with no `-race` net (D-14). Only `artistResult` values on a buffered channel cross it. |
| upstream API response → `runOneArtist` | A malformed MusicBrainz/Deezer payload can panic a worker; the recovered panic value is arbitrary attacker-influenced data. |
| `runCycle` → `pollruns.Store` (in-process seam) | Everything written here is later readable through the gated `/status` endpoint. The run entry is the disclosure surface. |
| `pollruns.Store` → `/status` HTTP response | Out of this phase's scope (Phase 18 froze it), but it is the sink that makes the boundary above matter. |
