## Warnings

### WR-01: Hand-rolled Combobox lacks `aria-activedescendant`, degrading it below the native `<select>` it replaces

**File:** `web/app/components/history/HistoryFilters.tsx:131-181`
**Issue:** The new `Combobox` component (introduced this phase to replace a native `<select>` that was illegible on Windows Chromium) keeps DOM focus on the trigger `<button role="combobox">` at all times and represents the "highlighted" option only via a `data-highlighted` attribute on the `<li role="option">` elements (line 169). Per the WAI-ARIA APG combobox pattern (the pattern this component's own `role="combobox"`/`aria-expanded`/`aria-haspopup="listbox"`/`aria-controls` attributes are explicitly modeled on), a focus-stays-on-trigger combobox must set `aria-activedescendant` on the trigger to the `id` of the currently highlighted option, and each option needs a stable, unique `id` for that reference to resolve. Neither exists here: the `<li>` elements have no `id` at all (only a React `key`), and the button never sets `aria-activedescendant`.

Concretely, a screen-reader user who opens the dropdown and presses ArrowDown/ArrowUp gets no announcement of which option is now highlighted — the visual highlight (`data-highlighted`) and the keyboard-driven `highlightedIndex` state move, but nothing in the accessibility tree reflects it. The native `<select>` this component replaced did not have this problem (the OS owns option-focus announcement for free). This is a net accessibility regression introduced by the D-13 rewrite, not merely an untouched pre-existing gap.

**Fix:** Give each option a stable id and wire it through:
```tsx
// inside Combobox, near listboxId:
const optionId = (index: number) => `${listboxId}-option-${index}`

// on the trigger button:
<button
  ...
  aria-activedescendant={open ? optionId(highlightedIndex) : undefined}
>

// on each <li>:
<li
  id={optionId(index)}
  role="option"
  ...
>
```

### WR-02: `CoverArt`'s image-error fallback state never resets when `src` changes on a retained instance

**File:** `web/app/components/common/CoverArt.tsx:20-51`
**Issue:** `CoverArt` tracks load failure in local state (`const [failed, setFailed] = useState(false)`, line 21) set by the `<img>`'s `onError` handler (line 48). This state is never reset when the `src` prop changes on an already-mounted instance — there is no `useEffect(() => setFailed(false), [src])` or key-based remount. If a parent list re-renders the same `CoverArt` instance (same React key) with a different `src` after a prior image failed to load — e.g. a `WatchlistEntry`'s `image_url` changing after a background `refresh()` in `watchlist.tsx`, or a `SearchResultRow` instance being reused across two debounced searches that happen to share an `artist.id` key — the component would permanently show the placeholder icon even though the new URL might load successfully. This is pre-existing (not introduced this phase; the only diff to this file was a Prettier trailing-comma removal), but it's a real robustness gap in a component shared by both the History feed and the Watchlist rows, both of which are in this phase's review scope.

**Fix:**
```tsx
export function CoverArt({ src, alt, size = 96, className }: CoverArtProps) {
  const [failed, setFailed] = useState(false)
  useEffect(() => setFailed(false), [src])
  const showPlaceholder = !src || failed
  ...
```

### IN-02: `role="combobox"` value comparison silently breaks if an `artist_id` of `0` is ever possible

**File:** `web/app/components/history/HistoryFilters.tsx:229`
**Issue:** `value={value.artistId === null ? null : String(value.artistId)}` — this correctly distinguishes "no artist selected" (`null`) from any real `artist_id`. However, if `artist_id` were ever `0` (e.g., a future non-Postgres-serial id scheme, or a test fixture), `String(0)` is `"0"`, which is truthy and distinct from `""`, so the comparison logic itself remains correct — this is not currently a bug. It's noted only because the codebase elsewhere (Postgres `bigserial`, starting at 1) makes `artist_id === 0` unreachable today; no fix is needed unless that invariant changes.
**Fix:** None required today. If the id scheme ever changes to allow `0`, re-verify this comparison and the `HistoryFiltersValue.artistId: number | null` contract together.
