## Common Pitfalls

### Pitfall 1: Fixing D-05a by re-adding the already-existing failure-path test

**What goes wrong:** 08-REVIEW.md's WR-02 (written 2026-08-12) describes `watchlist.test.tsx` as having only one happy-path test. Following that snippet literally would add a duplicate of the failure-path test that already exists (added between 2026-08-12 and now, confirmed by direct read).
**Why it happens:** The review report is a point-in-time snapshot; the planner's downstream consumer (this RESEARCH.md) is the first pass to re-verify current file state.
**How to avoid:** Only add the success-path "row disappears after successful DELETE" test — see Code Examples below for exact placement.
**Warning signs:** If a task's acceptance criteria mentions "add a rejection/failure test," check the current file first — it may already be satisfied.

### Pitfall 2: D-04's CI step gating the wrong job

**What goes wrong:** Adding `prettier --check` as a new step *inside* the existing `frontend-test` job's step list is fine, but if it's added as a wholly separate job, it must also be appended to `build-scan`'s `needs:` list (exactly like `frontend-test` itself was in Phase 9 — see the `full-pipeline.yml:129` comment referencing 08-CONTEXT.md D-04/09-CONTEXT.md D-11) or it silently never gates anything, reproducing the exact CR-01 defect 08-REVIEW.md found and Phase 9 fixed.
**Why it happens:** This project has already made this mistake once (Phase 8's `frontend-test` job existed for one whole phase before it actually blocked the pipeline).
**How to avoid:** Prefer adding `prettier --check` as an additional step inside the existing `frontend-test` job (simplest — inherits its existing `needs:` membership for free) rather than a new top-level job. If a new job is chosen instead, add it to `build-scan.needs`.
**Warning signs:** A new job in `full-pipeline.yml` that isn't referenced anywhere in `build-scan`'s `needs:` array.

### Pitfall 3: D-11's fix accidentally changing behavior, not just message text

**What goes wrong:** `PoolConfig`'s comment (lines 172-176) explains the second parse call is "defensive rather than expected" — a differently-worded error is the entire fix. Don't refactor the control flow, add a new error type, or change what triggers the branch.
**Why it happens:** IN-01 sits right next to genuinely interesting concurrency-hardening code (the whole point of Phase 11); it's tempting to "improve" more than the review asked for.
**How to avoid:** Change exactly the format string on line 179's `fmt.Errorf` call, nothing else — matches 11-REVIEW.md's own suggested diff verbatim.
**Warning signs:** A diff touching more than the one format string in `PoolConfig`.

### Pitfall 4: D-13's fix applied globally instead of scoped

**What goes wrong:** Adding `color-scheme: dark` to `:root`/`html` globally (rather than scoped to the select, or matched to the `.dark` class already governing every other themed value in `app.css`) could have unintended side effects on other native form controls' browser chrome (scrollbars, other future inputs) that haven't been visually audited in this research pass.
**Why it happens:** `color-scheme` is often documented as a root-level fix in generic dark-mode tutorials.
**How to avoid:** Scope the declaration to the `.dark` class (consistent with how every other color token in `app.css` is scoped) or directly to the `<select>` elements via `selectClassName`'s Tailwind arbitrary-value syntax `[color-scheme:dark]` — narrower blast radius, matches this app's existing "unconditionally `.dark`, no toggle" design (app.css:127-132 comment).
**Warning signs:** A diff touching `:root` in `app.css` instead of `.dark` or the component file.
