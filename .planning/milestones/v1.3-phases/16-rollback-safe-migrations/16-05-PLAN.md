  <action>
    Create the README with five sections, in this order.

    **Section 1 — the two rules, stated separately.** Do not collapse them into one
    destructive-DDL umbrella; S4 is explicit that these are different failure modes with
    different audiences. First rule: backward-incompatible changes break rollback. The
    previously-released binary boots against the new schema, so a DROP, a RENAME, a type
    narrowing, or a SET NOT NULL shipped in the same release the code stops using the object is
    a latent outage waiting for the next rollback. Second rule: unsafe-forward changes break or
    lock the deploy. Adding a NOT NULL column with no default, a non-concurrent index build, a
    table-rewriting ALTER — none of these break the old binary; they fail or hold a long lock on
    a populated table during the deploy itself (Pitfall 9).

    **Section 2 — the N-1 invariant.** State it plainly and state its bound: the
    immediately-previous release tag's binary must run cleanly against HEAD's schema, and the
    automated rollback targets exactly that one hop, never two or more releases back (D-17).
    Name the two mechanisms that prove it — the `n1-boot` CI job on every migration PR, and the
    `internal/db` ahead-of-source test on every run. State that the expand half and the contract
    half must never ship in the same release, and that a contract is only safe once the expand
    release is provably not coming back.

    **Section 3 — expand, backfill, contract walkthrough**, anchored on the in-tree precedent:
    `000006` added `events.watched_artist_name` as a nullable column with no backfill (expand);
    `000007` is the idempotent backfill, scoped so it can be re-run safely and updates zero rows
    on a fresh database; a future release could drop the old path (contract) once the expand
    release can no longer be rolled back to. Keep it to a short numbered sequence with the file
    names as anchors — the migration files carry the detail, the README carries the shape.

    **Section 4 — before you merge a migration**: a copy-pasteable checklist sourced from
    PITFALLS.md Pitfall 8. At minimum: can the currently-deployed version run against this
    schema (if not, split it); up-only, additive, embedded; new columns nullable or defaulted;
    no DROP, RENAME, type narrowing, or NOT-NULL-without-default in the release the code starts
    depending on it; no concurrent index build in a boot migration, because golang-migrate wraps
    each migration in a transaction and a concurrent index build cannot run inside one;
    backfills idempotent and a no-op on a fresh database; one file per version number, strictly
    ascending; a released migration file is immutable — never renumber it and never edit it in
    place.

    **Section 5 — what `cmd/migration-check` enforces, and the annotation.** List the two
    finding classes and the patterns in each; note that "no blocking DDL" is a rule here and not
    a machine check (D-08); give the exact annotation syntax as locked at Plan 02's checkpoint
    with one worked example line; and state the hard limit — the annotation documents intent and
    cannot override the previous-release query cross-reference, which reds a DROP or RENAME of an
    object the shipped binary still queries (D-15).

    Do not write a general migration-authoring guide. golang-migrate mechanics, file-naming
    conventions, and local testing are deliberately out of scope for SC #3 (D-10).

    Confirm before committing that the new file does not disturb the embed set — a README is not
    matched by the migrations glob the embed directive uses, so the existing migration tests must
    still pass untouched.

    Run the full Definition of Done before committing.
  </action>
