<objective>
Bound the digest run and make its outcomes readable: a 20-chunk-per-run cap with an
explicit remainder marker, a ~3-minute whole-send wall-clock budget checked at chunk
boundaries, and the three observability changes that make a partial digest diagnosable
instead of ambiguous.

Purpose: `SendDigestIfDue` holds the `notifying` CAS lock it shares with
`NotifyPending` for its whole run (ADR-0002), so an unbounded chunk burst is time
real-time notification is dark — at cap 20 the unbounded worst case is roughly 14
minutes. The cap and the budget are what turn "deliver everything at once" into
"self-drain in bounded bursts inside the grace window, losing nothing" (D-24). Output:
a bounded, self-draining, observable digest send.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Scheduler tick -> shared `notifying` CAS lock | The digest run holds the lock `NotifyPending` also takes (ADR-0002); every second spent in the chunk loop is a second real-time notification is dark. |
| Discord webhook API -> drop-tracker error handling | 429 responses, including from an intermediary, determine whether a run completes; their handling decides what state is written. |
| Process shutdown signal -> in-flight digest | A deploy landing mid-digest races the drain deadline; what gets acked and what gets logged is decided here. |
| drop-tracker process -> structured logs | Log fields added here are the operator's only view of a partial digest. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-23-17 | Denial of Service | `SendDigestIfDue` holding the `notifying` lock | high | mitigate | `maxDigestChunks` caps the burst at 20 messages and `digestSendBudget` caps the run at roughly three minutes; both stop cleanly with the remainder pending, so real-time notification is never dark for the ~14-minute unbounded worst case. |
| T-23-18 | Denial of Service | outbound burst through one Discord webhook | medium | mitigate | 1s inter-chunk spacing (plan 23-01, D-23) plus the 20-chunk cap keeps sustained outbound rate well under the webhook ceiling that 400ms sits at; `sendAttempt` still honours one `Retry-After`. |
