# Phase 20 — UI Design Contract

> Visual and interaction contract for the SPA **Digest settings section** — a new card added
> to the existing `/system` view, giving an operator control over digest mode (on/off),
> cadence (daily/weekly), and visibility into the last digest send time.
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope of this phase's UI:** one new component (`web/app/components/system/DigestSettings.tsx`),
inserted into the existing `web/app/routes/system.tsx`; two new `api.ts` wrappers
(`getDigestSettings`, `updateDigestSettings`) and wire types; `SystemSkeleton`'s loading
shape extended with one more card. No new route, no new nav entry, no change to any other
screen. Real-time notification behavior itself is unaffected (Phase 21+).

**Design system is already locked.** Tokens, theme, fonts, and the component library were
fixed by the Phase 6 UI spec (`web/app/app.css`) and extended by Phase 19 (status palette,
`table`). This phase adds **zero** new theme tokens and **zero** new third-party dependencies.
It vendors **one** new shadcn registry component (`select`) from the official `base-maia`
registry, needed for the daily/weekly cadence control — every other control it needs
(`Switch`, `Card`, `Separator`, `Skeleton`) is already vendored.

- `.planning/phases/20-digest-settings-operator-control/20-CONTEXT.md` — decisions D-01…D-05

## Visual Hierarchy

**Placement in `system.tsx`:** the Digest settings `<Card>` renders directly **after**
`AboutInstance` and **before** the empty-watchlist `<Alert>` / source panels. Rationale:
`AboutInstance` and Digest settings are both instance-level configuration/identity content
(read mostly, occasionally changed by an operator); the source panels below are per-cycle
operational data. Grouping the two static/config blocks together at the top keeps the page's
existing top-to-bottom narrative (what is this instance → is it configured the way I want →
is it working) intact rather than interleaving config controls between health panels.

**Internal layout** mirrors `AboutInstance`'s definition-list pattern exactly
(`<dl className="grid grid-cols-[auto_1fr] items-center gap-x-4 gap-y-2">`), extended with
interactive controls in the value column for the first two rows:

1. `Digest mode` → `<Switch>` + inline "On" / "Off" text to its right
2. `Cadence` → `<Select>` with two items, "Daily" / "Weekly" — visible and focusable but
   `disabled` when digest mode is off (D-04), never hidden
3. `Last digest sent` → formatted timestamp, or the literal "Never sent yet"

Below the `dl`, a single shared inline status region (`aria-live="polite"`, `text-label`)
carries either a transient success confirmation or a persistent failure message — one region
for both controls, not two, since both write the same underlying settings row and a user
rarely needs to distinguish which field's save failed.

**Primary interaction** is the `Switch` (digest mode is the on/off gate everything else in
the milestone depends on); the `Select` is secondary and inert-looking (dimmed) until the
`Switch` is on.

## Copywriting Contract

All strings are **locked** — the executor pulls them verbatim, per project convention.
`{…}` are runtime interpolations.

### Card chrome

| Element | Copy |
|---------|------|
| Card title (`<h2>`, `text-heading`) | `Digest notifications` |

### Rows

| Row | Label (`<dt>`) | Value states |
|-----|-----------------|---------------|
| Digest mode | `Digest mode` | `<Switch>` + `On` (when checked) / `Off` (when unchecked), `text-body text-foreground`, immediately to the right of the switch |
| Cadence | `Cadence` | `<Select>` — options `Daily` / `Weekly` exactly (title case, matching the existing "MusicBrainz"/"Deezer" title-case convention, not the lowercase wire values `daily`/`weekly`). `disabled` (dimmed, per the `Select` component's own disabled treatment) when `digest_enabled === false` — value is still shown, just non-interactive (D-04) |
| Last digest sent | `Last digest sent` | `digest_last_sent_at === null` → literal `Never sent yet` (`text-foreground`, **not** the em dash used elsewhere in the System view — an em dash reads as "missing/error" per the project's own em-dash convention in `format.ts`, and this is neither; it is an honest, expected state on every fresh instance until Phase 22 ships). Otherwise `<time dateTime={iso} title={formatIsoTitle(iso)}>{formatAbsoluteTime(iso)}</time>`, reusing the exact formatters `SourcePanel` uses for `finished_at` |

### Instant-apply feedback (D-02, D-03)

| Trigger | Copy | Treatment |
|---------|------|-----------|
| `PUT` succeeds (either control) | `Saved.` | `text-label text-muted-foreground`, appears immediately, auto-clears after **2 seconds** (no toast primitive exists — D-03 rejected one; a short-lived inline line is the closest equivalent) |
| `PUT` fails (either control) | `Couldn't save — reverted to the previous value.` | `text-label text-destructive`, `aria-live="polite"`. The `Switch`/`Select` value reverts to its last-known-good state in the same render (D-03 keep-stale). Persists until the **next** save attempt (success replaces it with `Saved.`; a fresh failure replaces it with itself) — same persistence posture as the existing `refreshError` line in `system.tsx` |
| A save is in flight | *(no copy — see UI Considerations)* | Both `Switch` and `Select` are `disabled` for the duration of any in-flight `PUT`, preventing a second write from racing the first. No spinner text; the brief disabled state itself is sufficient feedback at this interaction's timescale |

### Page-level states (unchanged machinery, digest data folds in)

| State | What happens to the Digest settings section |
|-------|-----------------------------------------------|
| `loading` (initial fetch) | `SystemSkeleton` gains one more card-shaped skeleton block (3 short bars) in the position described in Visual Hierarchy — inserted between the About-block skeleton and the two source-panel skeletons |
| `error` (initial load, non-401) | Digest settings are fetched in the **same** `Promise.all([getStatus(), getDigestSettings()])` call the mount effect makes; either request failing produces the existing page-level `Couldn't load system status.` `EmptyState` + `Retry` — no separate digest-only error surface |
| `session-expired` (401) | No per-component handling needed — `apiFetch`'s existing D-16 interceptor covers both calls identically |
| `first-run` / `loaded` | The Digest settings card renders identically in both — it is never gated by `deriveLoadedShape`; a fresh instance with zero poll cycles still has a real (default) digest settings row from the migration-time seed `INSERT` (D-05), so there is no first-run variant for this card |
| Manual **Refresh** click | Also re-fetches digest settings alongside status, via the same `Promise.all`, so the card's values can never silently drift stale relative to the rest of the page |

### Destructive actions

**None.** Toggling digest mode off does not delete or discard anything in this phase — Phase
21 (not this one) defines what happens to queued events, and this phase's own success
criterion 3 requires a fresh install to behave exactly like v1.4 with digest off. No
confirmation dialog is needed for either control.

Shape-rooted UI *state* coverage for the Digest settings section, using the GSD

(`interactive-control`), the `Select` (`interactive-control`), the last-sent value
(`static-content`, data-driven), and the card as a whole (`form`-adjacent, since it's a
persisted read/write pair, but with no submit step). 4 elements × applicable categories →
resolved below.

Applicable state considerations resolved: **9 covered, 1 backstop, 0 unresolved.**

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|----------------------|
| empty | Last digest sent, `digest_last_sent_at === null` | ✅ covered | Explicit `Never sent yet` copy (Copywriting Contract) — never blank, never the em dash used for "unknown/error" elsewhere in this view |
| loading | Initial fetch (`Switch`/`Select`/last-sent all unavailable yet) | ✅ covered | Folded into the existing page-level `SystemSkeleton`; a dedicated 3-bar skeleton card in this section's position (Visual Hierarchy) |
| loading | A save (`PUT`) in flight | ✅ covered | Both controls `disabled` for the duration; re-entrancy guard prevents a second write racing the first (Copywriting Contract → "A save is in flight") |
| error | Initial digest-settings fetch fails (non-401) | ✅ covered | Same page-level `error` state as a `/status` failure (`Promise.all`) — no separate digest-only error surface exists |
| error | A save (`PUT`) fails | ✅ covered | Keep-stale-on-failure: control reverts, persistent inline `text-destructive` line (Copywriting Contract) |
| populated | Both controls loaded with real values, last-sent populated (post-Phase-22 world) | ✅ covered | Standard row rendering — `Switch` reflects `digest_enabled`, `Select` reflects `digest_cadence`, timestamp formatted via the shared `format.ts` helpers |

| zero-one-many | Cadence has exactly two fixed options (daily/weekly) — no zero/many case exists | ⊘ n/a | Closed two-value enum; the "many" arm of this category does not apply. Not a dismissal requiring a reason beyond this — the option set is fixed by the requirement (DGST-02), not data-driven |

| overflow | Card width on a narrow viewport | ✅ covered | Same `<Card>`/`dl grid-cols-[auto_1fr]` layout `AboutInstance` already uses at this width — no new overflow surface introduced |

## Data Contract (informational — confirm against the real Go handler at plan time)

Not a UI-SPEC-owned decision, but recorded here so the executor's `api.ts` types are
anchored to something concrete rather than invented mid-implementation. Per `20-CONTEXT.md` /
`ROADMAP.md`'s schema sketch:

```ts
// GET /settings/notifications (exact path TBD by the planner/backend — placeholder name)
export interface NotificationSettingsResponse {
  digest_enabled: boolean
  digest_cadence: "daily" | "weekly"
  digest_last_sent_at: string | null
  updated_at: string
}
```

`updateDigestSettings` is assumed to send **both** `digest_enabled` and `digest_cadence` on
every `PUT` (full-object semantics, matching ROADMAP's "PUT" verb choice over "PATCH") — the
`DigestSettings` component already holds both values in state, so this costs nothing extra
client-side. The planner must confirm this against the actual route contract once written;
if the backend instead accepts a partial body, `updateDigestSettings` narrows to only the
changed field with no UI-visible difference.
