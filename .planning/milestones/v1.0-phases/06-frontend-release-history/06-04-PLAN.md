  <action>
    Add the search half of the Watchlist tab, directly above the list plan 06-03 built.

    **The input.** Create `web/app/components/watchlist/SearchBox.tsx` exporting `SearchBox`: a labelled text input rendered at the top of the Watchlist tab per `D-02`, reporting its debounced query upward. Debounce roughly 300ms so a request is not issued on every keystroke, and abort the in-flight request with an `AbortController` when a newer query supersedes it — both because `GET /search` fans out to two live third-party APIs on every call, and because an out-of-order response would otherwise paint stale results. Show a small inline spinner inside the box while a request is in flight; no skeleton is needed given the fixed 10-result cap per source. An empty or whitespace-only query clears the results and issues no request, matching the server's own "q is required" rule.

    **The columns.** Create `web/app/components/watchlist/SearchResultsColumns.tsx` exporting `SearchResultsColumns`. Render one labelled column per key in the response's `sources` map, side by side — never interleave or de-duplicate across sources. This is not a layout preference: this project explicitly excludes cross-source entity reconciliation, so presenting the two catalogues as one merged list would assert that a MusicBrainz artist and a Deezer artist are the same entity, which nothing in the system ever computes. Keep the sources visually and textually separate so the operator can see which catalogue each result came from.

    Per column, branch on that source's own `status` field:
    - `"error"`: render the inline unavailable message in that column only, naming the source, while the other column stays fully populated. The UI-SPEC's contract copy for this case reads "MusicBrainz is unavailable right now — showing Deezer results only." — generate the equivalent sentence from the failing and healthy source names so it works for either direction.
    - `"ok"` with zero artists: keep the column and its label visible and render `No matches for "{query}"` with the query interpolated. The column must not collapse — the side-by-side layout has to hold at zero results.
    - `"ok"` with artists: one result row each, showing the artist's `image_url` through the shared `CoverArt`, the `name`, the `type`, and the `disambiguation` truncated to one line within the row's fixed width. Render every one of these strings as a plain JSX text node; never reach for React's raw-HTML injection escape hatch in this tree, since all of it comes from third-party catalogues.

    Cap each column at the API's fixed 10 results and let the column scroll internally when it exceeds the viewport, rather than pushing the watchlist list below it off screen.

    **Add and already-watching.** Each addable result gets a primary button reading "Add to Watchlist", styled with the indigo accent per the UI-SPEC's accent reservation. Clicking it calls `addWatchlist` with the result's `mbid`, `name`, `image_url` and — for Deezer results — `deezer_id`, and sends neither preference axis, so the API applies its own defaults. Setting release-type and mute preferences at add time is deliberately not offered here; those are edited afterward through plan 06-03's inline row toggles, which is the single preference surface. After a successful add, call the route's `refresh` so the new artist appears in the list below and the cross-reference below updates in the same pass.

    Cross-reference each result against the watchlist entries the route already holds, matching on `mbid`. A match renders a disabled control labelled "Already watching" with no add action. The 409 the API returns for a duplicate stays a defensive backstop and is never surfaced as user-facing copy — but do handle it: `06-RESEARCH.md` Pitfall 3 describes the narrow window where the watchlist fetch has not resolved yet and a fast operator can still click add. In that window, treat a 409 as success rather than an error toast, since the artist genuinely is on the watchlist, and refresh the list. Any other failure shows "Couldn't add this artist. Try again in a moment." and returns the result to an addable state so the operator can retry.

    **Wiring.** In `web/app/routes/watchlist.tsx`, mount `SearchBox` and `SearchResultsColumns` above the existing list, hold the search response and its loading and error state, and pass the loaded entries down for the cross-reference. Leave plan 06-03's list, toggles, remove and Undo behaviour untouched.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| MusicBrainz / Deezer → Go → browser DOM | Live third-party search results are rendered without ever being persisted first |
| browser → Go API | Search queries and add bodies cross into `internal/httpserver` |
| browser → third-party APIs (indirect) | Every keystroke can drive outbound requests to two rate-limited external services |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-18 | Tampering | XSS via search-result `name` / `disambiguation` straight from MusicBrainz and Deezer | high | mitigate | Rendered exclusively as plain JSX text nodes, which React escapes by default; a repo-wide negative grep in this task's acceptance criteria asserts React's raw-HTML injection prop appears nowhere under `web/app/` |
| T-06-19 | Denial of Service | Search-as-you-type fanning every keystroke out to two rate-limited third-party APIs | medium | mitigate | ~300ms debounce plus `AbortController` cancellation of the superseded request; the server additionally caps each source at its fixed `searchResultLimit` of 10, and Phase 3's per-source `rate.Limiter` is a whole-process budget that already bounds outbound traffic regardless of client behaviour |
| T-06-20 | Information Disclosure | Upstream failure detail reaching the operator's screen | medium | mitigate | The UI renders only the source's `status` field and its own composed sentence; `handleSearch` already replaces raw upstream error text with the fixed `"source unavailable"` string (T-03-01), so no third-party error text is available to leak |
| T-06-21 | Spoofing | A duplicate add slipping past the client-side "Already watching" check | low | accept | `POST /watchlist`'s existing 409 (Phase 2 D-09) is the authoritative boundary and stays in place; the client check is a UX affordance, not a security control, and the 409 path is handled as success rather than an error |
| T-06-22 | Tampering | Over-posting server-owned fields on the add body | low | mitigate | `addWatchlistRequest` omits every server-owned field and `DisallowUnknownFields` rejects extras (T-02-01); the client sends only `mbid`, `name`, `deezer_id` and `image_url` |
</threat_model>
