<objective>
Make the migrate-on-boot retry policy injectable and prove all four of its behaviours: it
applies migrations from scratch, it treats a second run as success, it gives up after a
bounded budget, and it never leaks the DSN on the failure path.

Purpose: D-10 is the decision that makes `docker compose up` work in one command — the
service tolerates a Postgres container that is still starting. It is also the decision most
likely to be silently wrong: the retry loop's terminating case and its `ErrNoChange` case
are both invisible on a happy first boot and both break production later. RESEARCH.md
Pitfall 1 describes exactly that failure — works on first boot, fails on every restart after.

Output: an options-based retry policy on `RunMigrations` with the D-10 defaults preserved,
and a migration test suite that covers success, idempotency, exhaustion, cancellation, and
redaction.
</objective>

  <action>
Give `internal/db/migrate.go` a small unexported policy struct holding `maxAttempts int`,
`baseDelay time.Duration` and `maxDelay time.Duration`, with exported package-level defaults
of 6 attempts, 500ms and 8s. These are RESEARCH.md's recommended values (assumption A1: a
worst case near 20 seconds, which covers a typical 2-to-10-second Postgres container cold
start without hanging on a genuinely dead database); export them as named constants so the
numbers are discoverable and adjustable rather than buried in the loop body.

Define `RetryOption` as a function taking a pointer to that policy, and export three
constructors — `WithMaxAttempts(int)`, `WithBaseDelay(time.Duration)` and
`WithMaxDelay(time.Duration)`. Have `RunMigrations` build a policy from the defaults, apply
each supplied option in order, and drive the existing loop from the resulting values instead
of from local constants. Do not change the `RunMigrations` signature — plan 01-01 already
declared it variadic precisely so this change touches no call site, and `cmd/server/main.go`
must compile with no edit.

Keep every behaviour of the existing loop intact while doing this. In particular:
`errors.Is(err, migrate.ErrNoChange)` returns nil, because without it every restart after
the first successful migration fails (RESEARCH.md Pitfall 1). The delay doubles per attempt
and is capped at the policy's maximum. The wait is a `select` over `time.After` and
`ctx.Done()`, so a cancelled context aborts the loop and returns the context's error rather
than sleeping out the remaining budget. After the final attempt the function returns an error
that states the attempt count and wraps the last underlying failure.

Harden the failure path against DSN leakage. golang-migrate and pgx both produce connection
errors that embed the DSN, and the DSN carries the Postgres password. Before logging a failed
attempt or wrapping the final error, reduce the underlying error to a form that cannot carry
credentials: parse the DSN once at function entry into a host-and-database description and
build log attributes and the returned error from that description plus the error's message
with the DSN's user-info portion removed. Never build a `slog` attribute from the DSN itself.
Log each failed attempt at Warn with the attempt number, the delay, and the redacted error.
  </action>

The two database-backed tests take their DSN from `testutil.RequirePostgresDSN(t)`, so they
skip visibly when no fixture is available. `TestRunMigrations_AppliesFromScratch` must reset
state before it runs: connect and drop the `schema_migrations` table if present, so the test

after another test. Register a cleanup that leaves the database migrated, so test ordering
does not affect the other packages' fixtures.

The three failure-path tests need no database. Point them at a DSN whose host is loopback and
whose port is one nothing listens on, so the connection is refused promptly rather than
timing out; do not use an unroutable address, which would make the test wait on TCP timeouts
and turn a one-second test into a slow one.

Capture log output through `logging.NewWithWriter` over a mutex-guarded `bytes.Buffer` and

message that happens to contain it.

production defaults: a test that used the real 6-attempt, 8-second-cap policy would take
around twenty seconds and would be the first test anyone disables. That is precisely why

a delay shorter than the configured base delay, and assert with `errors.Is` against the
context error rather than by string-matching the message.

`err.Error()` — because the redaction can be correct in one and missing in the other, and the
returned error is the one that reaches the operator's terminal through `main`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| process → Postgres (startup) | The DSN crosses here on every retry attempt. Connection errors returned across it routinely embed the full DSN including the password. |
| retry loop → logs and stderr | Failed-attempt Warn lines and the final wrapped error both reach the operator's terminal and any CI log. |
| embedded migration files → database schema | The `embed.FS` contents are executed as SQL against the live database at boot. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-04 | Denial of Service | `internal/db/migrate.go` retry loop | low | mitigate | The budget is bounded — 6 attempts, 8s delay cap — and exhaustion returns an error that terminates the process rather than looping forever against a permanently broken database (D-10). Proven by `TestRunMigrations_RetriesThenFails` and by the cancellable `select` covered by `TestRunMigrations_HonoursContextCancellation`. |
| T-01-01 | Information Disclosure | failed-attempt Warn lines and the final wrapped error | medium | mitigate | The DSN is reduced to a host-and-database description at function entry; log attributes and the returned error are built from that description and a user-info-stripped error message. Asserted against both sinks by `TestRunMigrations_NeverLogsDSN` and by a source check that no `slog` attribute is built from the DSN. Severity is medium rather than low because this is the code path that runs when connections fail, which is exactly when an operator copies the output into an issue or a chat. |
| T-01-16 | Tampering | embedded migration content | low | accept | Migration SQL is compiled into the binary by `go:embed`, so it cannot be swapped at runtime by anything short of replacing the binary itself; altering it requires a source change that passes code review. Accepted at ASVS L1 — binary integrity is CICD-04/CICD-05's concern (Trivy scan plus SBOM) in Phase 7, not an in-process control. |
| T-01-17 | Denial of Service | concurrent migrators | low | accept | Phase 1 runs a single service instance and a single in-process migrator during startup, so no contention exists. golang-migrate takes a Postgres advisory lock during `Up`, which is the backstop if a second instance is ever started; CLAUDE.md already records that scaling past one instance needs an explicit distributed-lock decision, and DTCT-05 in Phase 4 is where deliberate concurrency control enters the project. |
</threat_model>
