<user_story>
**As a** drop-tracker operator, **I want to** have new releases for my watchlisted artists
detected and durably recorded exactly once, **so that** Phase 5 can notify me without spam or
silence.
</user_story>

<objective>
Deliver the thinnest complete detection path end-to-end: a scheduled MusicBrainz poll cycle
diffs the release-groups it just fetched against a persistent seen store and records each
previously-unseen release-group as a `new_release` event row — idempotently, at the database
level, with no overlapping cycles.

Purpose: proves the whole Phase 4 architecture (schema -> sqlc -> detection package -> poller
seam -> live binary) on one real path before guest-feature and deluxe-change expand it.
Output: migration `000003_events`, `queries/events.sql`, the new `internal/detection` package,
the `poller.EventRecorder` seam, and real-Postgres tests proving DTCT-01, DTCT-04 and DTCT-05.
</objective>

<assumption_delta_decision>
**Signal:** `new_release` events are dual-source from this phase on (MusicBrainz release-group
MBIDs *and* Deezer numeric album ids), where Phases 1-3 had a purely MusicBrainz-centric
identity model (artists keyed on `mbid`, with a nullable `deezer_id` bolted alongside).

**Decision: add-alongside, not promotion.** A `source` discriminator column is added to the
`events` table and folded into the dedup key `(event_type, source, external_id)`. MBID stays
the primary identity for `artists`; `source` only disambiguates an *event's* provenance
namespace.

**Rationale:** dual-source reconciliation is explicitly Out of Scope (REQUIREMENTS.md), so
promoting a cross-source identity would build machinery no v1 requirement asks for. The
`source` column is the minimum that makes D-14's seed-mode check and D-15's per-source-
independent seeding expressible as queries, and it keeps a MusicBrainz MBID and a Deezer
numeric id from ever conflating as raw strings (04-RESEARCH.md Pitfall #5, Assumption A5).
</assumption_delta_decision>

<flagged_assumptions>
Surfaced, not silently dropped. Each is a consequence of a locked decision, recorded so a
later phase does not mistake it for an oversight.

1. **Dedup is global, not per-artist (D-10).** The dedup key deliberately excludes
   `artist_id`, so a release-group credited to two watchlisted artists produces exactly one
   `new_release` row, attributed to whichever artist's cycle detected it first. This is the
   correct reading of DTCT-04 ("never re-notify for a release it has already seen") and keeps
   Phase 5 from posting the same release twice, but it means Phase 6's per-artist history will
   show such a release under one artist only.
2. **Seed-mode edge under global dedup (D-14).** Because `HasAnyEvent` is keyed on
   `(artist_id, source)`, an artist whose entire back-catalogue was already recorded under a
   collaborator would keep zero rows of their own and therefore stay in seed mode. Their next
   genuinely new release would be recorded with `notified_at` pre-set instead of alerted. Rare
   (requires 100% catalogue overlap with an already-watched artist) and accepted rather than
   adding the `seeded_at` column D-14 explicitly rejects.
3. **The Phase 3 "poll result" log line is kept, not deleted.** Phase 3 D-04 said this phase
   "replaces the log statement with real diff logic"; the detection call is added immediately
   after it instead. `item_count` is the only visibility into a page-ceiling-truncated fetch
   (04-RESEARCH.md Pitfall #4), so deleting it would trade a prohibition for a literal reading.
</flagged_assumptions>

<task type="checkpoint:decision" gate="blocking">
  <name>Task 1: Decide where the deluxe-change track-count baseline is persisted</name>
  <decision>
    DTCT-02 compares a release's freshly fetched total track count against "the highest
    previously-seen count for that release-group" (D-02). Nothing in CONTEXT.md says where that
    running baseline lives. This plan writes migration `000003_events`, so the answer has to be
    settled before the schema is committed.
  </decision>
  <context>
    04-RESEARCH.md Open Question 2 and Pitfall #1 flag this as the phase's highest-risk open
    design gap. D-09 locked "one combined table" as the *seen store / event log*; it did not
    address a mutable per-release-group counter. D-20 locked "never overwrite an event's
    snapshot" — the display fields specifically (title, cover art URL, release date, artist
    name), not operational state.

    This is a one-way door: once migration `000003` is committed and Phase 5 (`notified_at`
    queries) and Phase 6 (release history) read the resulting shape, changing it means a data
    migration plus re-threading both later phases' queries. Undoing it is not a refactor.

    Either option resolves the false-positive hazard identically — the algorithm is
    establish-then-compare in both cases (first-ever release-detail fetch for a group records
    the baseline silently and fires no event; only a fetch after a baseline exists can fire
    `deluxe_change`). Only the storage shape differs.
  </context>
  <options>
    <option id="option-a">
      <name>Mutable `track_count` column on the `events` table (04-RESEARCH.md recommendation)</name>
      <pros>
        Keeps D-09's "one combined table" literally true — Phase 5 and Phase 6 thread exactly
        one table. No second table, no second sqlc model. `release_group_mbid` on the same row
        makes "highest previously-seen count for this group" a single MAX query. The
        `deluxe_change` row this phase later inserts carries its own `track_count`, so the
        baseline advances naturally with no extra write.
      </pros>
      <cons>
        Mutates one column on an already-inserted event row, which reads as a partial exception
        to D-20 until you notice D-20's stated scope is the display snapshot. Mixes operational
        state into an otherwise append-only log.
      </cons>
    </option>
    <option id="option-b">
      <name>Separate `release_group_baselines` table (release_group_mbid PK, track_count, updated_at)</name>
      <pros>
        The `events` table stays strictly append-only, so D-20 needs no scope reading at all.
        Operational baseline state is cleanly separated from the historical record. An upsert
        with GREATEST() expresses "highest ever seen" directly.
      </pros>
      <cons>
        A second table and a second sqlc model. D-09's "one combined table" language now has an
        adjacent table beside it, which a later reader has to reconcile. Slightly more schema
        surface for Phase 6 to understand.
      </cons>
    </option>
  </options>
  <resume-signal>Select: option-a or option-b (recommended: option-a — it matches D-09's stated intent and 04-RESEARCH.md's recommendation; D-20's own text scopes immutability to the display snapshot)</resume-signal>
</task>
