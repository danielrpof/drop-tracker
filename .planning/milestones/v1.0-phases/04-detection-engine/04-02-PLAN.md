<user_story>
**As a** drop-tracker operator, **I want to** only record the release types I asked for, and to
have a newly added artist's existing catalogue absorbed silently rather than blasted at me,
**so that** the alerts I eventually receive are signal rather than noise.
</user_story>

<objective>
Complete the `new_release` slice: apply both per-artist preference axes at detection time,
absorb a newly watched artist's existing catalogue into the seen store without queueing it for
alerting, and extend the same detection path to the Deezer poll cycle as an independent second
source.

Purpose: without this, the tracer records everything for everyone and floods the operator the
first time an artist is added.
Output: `internal/detection/filter.go`, per-source seed mode, `DetectDeezer`, and the
`ListUnnotified` query that makes seed behavior observable.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Deezer API -> `internal/detection` | Semi-trusted JSON (album titles, cover URLs, record types, numeric ids) crosses into decode and then into persisted rows |
| `watchlist` preference columns -> detection predicates | CHECK-constrained arrays read per artist per cycle and used to gate whether data is persisted at all |
| `internal/detection` -> Postgres | Deezer-sourced strings cross into the same table MusicBrainz-sourced strings occupy |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-07 | Denial of Service | seed mode on a newly added prolific artist | medium | mitigate | Seed rows are written with `notified_at` pre-set, so Phase 5's `ListUnnotified` query can never return them; a first cycle cannot become an alert flood (D-13) |
| T-04-08 | Spoofing | Deezer album id crossing into the dedup key | low | mitigate | `external_id` is formatted from the decoded `int64` with `strconv.FormatInt`, never from raw response text, and the `source` column keeps Deezer ids out of the MusicBrainz MBID namespace regardless |
| T-04-09 | Denial of Service | preference predicates reading `Entry.ReleaseTypes` / `Entry.MutedEventTypes` | low | mitigate | Both slices are read with range-based membership tests, never fixed-index access; both columns are CHECK-constrained at the database so no unexpected value can reach the predicate |
| T-04-10 | Information Disclosure | Deezer detection log lines | low | mitigate | Log artist MBID, artist name and counts only — never the upstream response body, and never a driver error string that could carry the DSN |
| T-04-11 | Tampering | Deezer cover URL persisted verbatim into `cover_art_url` | low | accept | Deezer supplies the URL; rendering and escaping belong to Phase 5's Discord embed and Phase 6's UI. Recorded so the downstream renderer treats it as untrusted |
| T-04-SC | Tampering | Go module dependency set | high | mitigate | Zero package installs this phase (04-RESEARCH.md Package Legitimacy Audit: not applicable). Task 3 asserts `go mod tidy && git diff --exit-code -- go.mod go.sum` |
