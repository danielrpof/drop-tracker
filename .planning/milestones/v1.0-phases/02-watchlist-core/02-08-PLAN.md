<objective>
Close gap G-02-2, the review's one Critical finding. `internal/db/migrate.go`'s `redactError`
strips only URL-form DSN userinfo. It has no handling for libpq keyword/value-form credentials —
the `password=...` form — even though `config.Config` places no format constraint on
`DATABASE_URL`, pgx and golang-migrate both accept that form, and the sibling `redactDSN` was
deliberately built on `pgconn.ParseConfig` for the express reason that a regex/URL-only approach
silently fails on it. Two functions in one file with the same stated purpose, one of which does the
job and one of which does not.

`redactError` is the only scrubbing applied to underlying error text on both paths that reach the
outside world: the per-attempt retry `Warn` line and the final returned error. Its coverage *is*
the guarantee, and OPS-03 states that guarantee absolutely.

The diagnosis added one refinement that shapes this plan. With pgx pinned at v5.10.0, the single
reachable runtime path that could feed a raw DSN into `redactError` — a `pgconn.ParseConfig`
failure — does not currently leak, because `pgconn.ParseConfigError.Error()` self-redacts before
`redactError` ever sees the text. That is incidental upstream behaviour (pgx's own source shows its
maintainers second-guessing it), it covers exactly one error type out of every error that can reach
this code, and it is not something this project controls. So: fix the function, but prove it at the
unit level against constructed error text. An integration-level test would pass identically before
and after the fix — which is precisely the flaw in the existing regression test this plan also
corrects.

This file carries zero Phase 2 commits; it is a Phase 1 file re-flagged during the Phase 2 review.
Treat it as an out-of-band fix, not as something that has to fit Phase 2's scope narrative.

Output: a second redaction pattern in `redactError`, a new in-package test file exercising both
unexported redaction helpers directly against a shared table of DSN forms, and an honest name and
comment on the migration test that never tested what it claimed.
</objective>

  <action>
Add a second redaction pattern and apply it in `redactError`.

**Pattern (`internal/db/migrate.go`).** Declare a package-level `kvPasswordPattern` immediately
below `userInfoPattern`, compiled from the raw-string regex
`(?i)\bpassword\s*=\s*(?:'(?:[^'\\]|\\.)*'|\S+)`. Read left to right: case-insensitive, a word
boundary so a longer identifier ending in the word is not matched, the keyword, optional whitespace
either side of the `=` as libpq permits, and then either a single-quoted value — allowing
backslash-escaped quotes and backslashes inside, which is how libpq escapes them — or an unquoted
run of non-whitespace. The quoted alternative must come first: Go's regexp prefers the earlier
alternative at the same starting position, so putting the unquoted branch first would make it match
only up to the opening quote's first space and leave the rest of the value in the output.

Give it a doc comment covering three things a future reader will otherwise have to rediscover.
First, why a second pattern exists at all: `userInfoPattern` requires an `@` and therefore
structurally cannot reach libpq's keyword/value form, nor a password passed as a URL query
parameter — and `config.Config` places no format constraint on `DATABASE_URL`, so both are shapes
this project accepts. Second, that it deliberately requires an assignment: text merely mentioning
the keyword, such as Postgres's own authentication-failure message, is left intact because
destroying it would cost real diagnostic value and protect nothing. Third, cross-reference
`redactDSN`, which solved the same problem for the DSN itself by delegating to `pgconn.ParseConfig`
— a route unavailable here, since `redactError`'s input is arbitrary error text that merely
*happens* to embed a DSN somewhere inside it and is not parseable as one.

**Apply (`internal/db/migrate.go`).** Rewrite `redactError` to run both patterns in sequence: the
existing userinfo strip first, then the keyword/value substitution over its result, replacing each
match with `password=<redacted>`. The order matters and should be stated in the comment — the
userinfo strip removes a whole `scheme://user:pass@` span including the scheme, and running it
first means the keyword/value pass only ever sees what survived. The replacement text contains no
`$`, so no capture-group expansion applies.

Extend `redactError`'s own doc comment. It currently claims a guarantee — that any error text
embedding a raw DSN can be scrubbed — that the implementation did not meet. State what is now
actually covered: URL-form userinfo, keyword/value assignments in any accepted spelling, and
password-bearing URL query parameters. Record explicitly that this does not rely on any driver's
internal redaction: pgx v5.10.0's `ParseConfigError` happens to self-redact today, that behaviour is
undocumented and covers exactly one error type, and a version bump could remove it with no signal
here.

Change nothing else in this file. `redactDSN`, `userInfoPattern`, `RunMigrations`,
`runMigrationsOnce` and the retry options are all untouched, and no import is added — `regexp` is
already imported.
