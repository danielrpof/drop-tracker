**Normalisation, in `internal/watchlist/service.go`.** Add an unexported
`normalizeSet(values []string, allowed []string, invalidErr error) ([]string, error)`. For each
submitted value it checks membership in `allowed`; on a miss it returns
`fmt.Errorf("%w: %q", invalidErr, value)` so the caller gets both the sentinel (for
`errors.Is`) and the offending value (for the 400 message). On success it returns a new slice
containing each allowed value at most once, ordered by its position in `allowed` — so
`["single","album"]` and `["album","single","album"]` both normalise to `["album","single"]`.
An empty or all-duplicate input yields `[]string{}`, never nil, so the JSON encoder emits `[]`
rather than `null`.

Two normalisation choices are the planner's, not the developer's — 02-CONTEXT.md left set
semantics unspecified and 02-RESEARCH.md did not address them. They are recorded here so a later
reader sees they were decided rather than defaulted: (a) duplicates are silently collapsed rather
than rejected, because a preference array is semantically a set and a caller sending the same
filter twice has expressed no contradiction; (b) output order is canonical rather than
submission order, so the response body for a given preference set is byte-stable across calls
and diffable in tests.

Call `normalizeSet` from `Add` for both axes before any database call — with
`ErrInvalidReleaseType` for `AddParams.ReleaseTypes` against `ReleaseTypes`, and
`ErrInvalidEventType` for `AddParams.MutedEventTypes` against `EventTypes`. When a slice is nil,
skip normalisation and substitute the D-08 default instead: a copy of `ReleaseTypes` for the
release axis, `[]string{}` for the mute axis. Validation must precede `UpsertArtist`, so a
rejected request leaves no artists row behind.

The two axes are validated against two separate allow-lists and never share a code path — D-05
makes them independent dimensions (catalog scope versus alert-noise control), and collapsing
them into one validated set would be the merge that decision explicitly ruled out.

**Handler, in `internal/httpserver/watchlist.go`.** Extend `addWatchlistRequest` with
`ReleaseTypes *[]string \`json:"release_types"\`` and `MutedEventTypes *[]string
\`json:"muted_event_types"\``. Pointer-to-slice, not slice: it distinguishes an absent key (nil
→ apply defaults) from an explicitly supplied empty array (non-nil, length 0 → persist an empty
set). Dereference into `AddParams` only when non-nil.

Wrap the request body before decoding: `r.Body = http.MaxBytesReader(w, r.Body, 65536)`. A body
past that ceiling makes the decoder fail, which the existing decode-error branch already turns
into a 400 — no separate branch needed (T-02-04).

After trimming, cap field lengths before any service call: `mbid` longer than 36 characters →
400 `"mbid must be at most 36 characters"`; `name` longer than 512 characters → 400
`"name must be at most 512 characters"`. Measure with `utf8.RuneCountInString`, not `len`, so a
name with multi-byte characters is not rejected for its byte count. 36 is the width of a
canonical MBID; note that this is a length bound only — format is not validated, and the
consequences of that are recorded as assumption A-02-01 in plan 02-01 (T-02-05).

Add branches for `errors.Is(err, watchlist.ErrInvalidReleaseType)` and
`errors.Is(err, watchlist.ErrInvalidEventType)` returning 400 with `err.Error()` as the message
— these sentinels wrap only the offending value, which came from the client, so echoing them
leaks nothing. Order these branches before the generic 500.

**Service tests.** Extend `internal/watchlist/service_test.go` with the behaviours above,
reusing the unique-mbid-from-`t.Name()` and `t.Cleanup` pattern from task 1. The
DB-default-parity test and the CHECK-constraint test are the two that prove the Go allow-list and
the schema have not drifted — keep them together and comment why they exist, since a future
migration that adds a release type must update both sides or these fail.
