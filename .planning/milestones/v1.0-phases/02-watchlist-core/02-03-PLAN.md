  <action>
Add the remove capability end to end as a hard delete (D-10).

**Query (`queries/watchlist.sql`).** Append `-- name: DeleteWatchlistEntry :execrows` over
`DELETE FROM watchlist WHERE id = $1;`. The `:execrows` annotation makes sqlc return the affected
row count as an `int64`, which is what lets the service distinguish "deleted" from "there was
nothing to delete" in one round trip. Do not add a preceding existence `SELECT`: two statements
would open a window where a concurrent delete lands between them, and the resulting behaviour
under the concurrency test would be two 204s. Run `make sqlc` and commit the regenerated output.

**Service (`internal/watchlist/service.go`).** Replace `Remove`'s interface-first placeholder
with a call to `DeleteWatchlistEntry`. When the call itself errors, wrap it with
`fmt.Errorf("delete watchlist entry: %w", err)`. When it succeeds and the affected count is 0,
return `ErrNotFound`; when the count is 1, return nil. Postgres takes a row lock for the
duration of the `DELETE`, so of two concurrent statements targeting the same id exactly one
reports 1 affected row and the other reports 0 — which is what makes the 204/404 split
deterministic rather than racy.

The delete is unconditional and physical. Introduce no status column, no soft-delete timestamp
column, and no filtering predicate in the list query — D-10 chose a hard delete precisely so that
nothing downstream can keep reading a row the user asked to be rid of. Do not add an explanatory
code comment naming the column that is absent; the gate below greps for exactly that name. The
`artists` master row
is deliberately left alone: the FK cascade runs from `artists` to `watchlist`, not the other
way, so removing a watchlist entry cannot take the artist with it (D-03).

**Handler (`internal/httpserver/watchlist.go`).** Add an unexported
`parseWatchlistID(r *http.Request) (int64, error)` helper: read `chi.URLParam(r, "id")`, parse it
with `strconv.ParseInt(raw, 10, 64)`, and reject anything that fails to parse or is less than 1.
Ids are `BIGSERIAL`, so 0 and negatives are never valid and rejecting them at the edge keeps
nonsense out of the query. Both this task's handler and plan 02-04's PATCH handler use this one
helper, so put it next to `writeError`.

Add `handleRemoveWatchlist`: parse the id (400 `"invalid watchlist id"` on failure, before any
service call), call `s.watchlist.Remove(r.Context(), id)`, map
`errors.Is(err, watchlist.ErrNotFound)` to 404 `"watchlist entry not found"`, map any other error
to a logged 500 `"internal error"`, and on success respond `w.WriteHeader(http.StatusNoContent)`
with no body and no Content-Type — 204 carries no payload, so do not call the JSON encoder.

**Route (`internal/httpserver/server.go`).** Register
`r.Delete("/watchlist/{id}", s.handleRemoveWatchlist)`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → `{id}` path segment | Untrusted, attacker-controlled string reaching a query parameter |
| Postgres → `GET /watchlist` response | Every stored watchlist row crosses back to the client in one payload |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-07 | Tampering | `{id}` path parameter in `handleRemoveWatchlist` | medium | mitigate | `parseWatchlistID` runs `strconv.ParseInt(chi.URLParam(r, "id"), 10, 64)` and rejects parse failures and values below 1 with a 400 before any service call; the resulting `int64` is bound as a sqlc query parameter and never interpolated into SQL text |
| T-02-08 | Information Disclosure | sequential `BIGSERIAL` ids exposed in `GET /watchlist` and required by `DELETE /watchlist/{id}` | low | accept | This is a single-operator deployment with no authentication boundary to enumerate across, so predictable ids disclose nothing an authorised caller could not already list. Recorded in 02-RESEARCH.md Security Domain as an accepted v1 risk; revisit only if multi-user auth is ever promoted from v2 |
| T-02-09 | Denial of Service | `GET /watchlist` returns the entire table with no pagination | low | accept | WLST-04 specifies listing all watchlisted artists, and a single operator's watchlist is human-scale — tens of rows, not millions. Pagination has no defined page size until Phase 6's UI exists; adding one now would be inventing a contract the frontend has not asked for |
| T-02-15 | Tampering | concurrent deletes of the same watchlist row | medium | mitigate | The single `:execrows` `DELETE` statement relies on Postgres row-level locking rather than a check-then-act pair, so exactly one of two racing requests observes 1 affected row; `TestWatchlist_Delete_ConcurrentSameIDYieldsOne204AndOne404` runs five consecutive times as the gate |
</threat_model>
