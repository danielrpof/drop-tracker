**Query (`queries/watchlist.sql`).** Append `-- name: UpdateWatchlistPreferences :one` over
`UPDATE watchlist SET release_types = $2, muted_event_types = $3, updated_at = now() WHERE id =
$1 RETURNING *`. Both arrays are always written; the partial-update semantics live in Go, which
reads the current row first and substitutes the untouched axis. Keeping the SQL total rather than
conditional avoids a `COALESCE`-per-column expression whose NULL-versus-empty-array behaviour is
exactly the distinction this plan has to keep sharp. Run `make sqlc` and commit the regenerated
output.

**Service (`internal/watchlist/service.go`).** Replace `UpdatePreferences`'s remaining
interface-first placeholder with a real implementation:

1. Validate first. For each non-nil pointer in `PreferencesParams`, run `normalizeSet` — with
   `ReleaseTypes`/`ErrInvalidReleaseType` for the release axis and `EventTypes`/
   `ErrInvalidEventType` for the mute axis. Return the sentinel-wrapped error immediately on a
   miss, before touching the database, so a rejected request cannot leave a partially-applied
   row behind.
2. Read the current row for `id`. Reuse the existing `ListWatchlist` result filtered by id
   rather than adding a fifth query — the phase's query surface stays at five, and the read is
   already proven by plan 02-03's tests. If no row matches, return `ErrNotFound`.
3. Substitute. A nil pointer means "leave this axis alone", so carry the value just read
   forward; a non-nil pointer means "use exactly this normalised set", including a normalised
   empty set. This is what makes `{"release_types": []}` and a body that omits the key produce
   two different rows — 02-RESEARCH.md Open Question 2 left partial-versus-full PATCH semantics
   open and recommended partial; this implements that recommendation, and the `*[]string` field
   type is what carries the three-way distinction (absent / empty / populated) that a plain
   `[]string` would flatten to two.
4. Call `UpdateWatchlistPreferences` with both resolved arrays and map the returned row into an
   `Entry`, joining the artist fields from the row read in step 2.

The two axes are resolved through two separate normalisation calls against two separate
allow-lists and are written as two separate columns. Nothing in this method may make one axis's
value depend on the other's — D-05 defined them as orthogonal dimensions (which release types the
artist is watched for at all, versus which event categories actually produce a Discord post), and
a cross-axis dependency here would be the merge that decision ruled out.

**Handler (`internal/httpserver/watchlist.go`).** Add
`updateWatchlistRequest` carrying exactly `ReleaseTypes *[]string \`json:"release_types"\`` and
`MutedEventTypes *[]string \`json:"muted_event_types"\``. Nothing else: `id`, `artist_id`,
`mbid`, `name` and the timestamps are not modifiable through this route (T-02-11).

Add `handleUpdateWatchlist`: bind the body with `http.MaxBytesReader(w, r.Body, 65536)` and a
decoder with `DisallowUnknownFields()`, exactly as the add handler does. Parse the id with the
existing `parseWatchlistID` helper and return 400 `"invalid watchlist id"` on failure. Reject a
body in which both pointers are nil with 400 `"no preferences supplied"` — an empty PATCH is a
caller mistake, and answering 200 to it would report a change that did not happen. Call
`s.watchlist.UpdatePreferences(r.Context(), id, params)`. Branch order: `ErrNotFound` → 404;
`ErrInvalidReleaseType` or `ErrInvalidEventType` → 400 with `err.Error()` as the message (the
wrapped text contains only the caller's own value); anything else → logged 500 via
`httplog.SetAttrs(r.Context(), slog.String("watchlist_error", err.Error()))` and a fixed
`"internal error"` body. On success: `Content-Type: application/json`,
`WriteHeader(http.StatusOK)`, encode the full updated `watchlist.Entry` so the caller can see
both axes' resulting state without a follow-up GET.

**Route (`internal/httpserver/server.go`).** Register
`r.Patch("/watchlist/{id}", s.handleUpdateWatchlist)`. That completes the four-route D-11 surface:
POST, GET, PATCH, DELETE, all flat with no `/api` prefix (D-14).
