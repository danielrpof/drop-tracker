<objective>
Make each of the three event types arrive in Discord as its own complete, scannable message,
and persist the two display fields Phase 4's detection code computes in memory but never
wrote down.

Purpose: the tracer proved delivery; this plan is what the user actually sees. It closes
NTFY-01's literal field list (which names a release type no column held until migration
000004), NTFY-02's guest-feature distinction, and NTFY-03's track-count delta — the three
success criteria a reader of the ROADMAP would check first.

Output: `release_type` populated on both sources' new_release inserts, `previous_track_count`
populated on the deluxe_change insert, and a complete `formatEmbed` with the per-type color,
emoji, link, and field table plus rune-safe truncation.

**Ordering note.** Task 1 must land before Task 2's deluxe-change and release-type assertions
can pass against real data, because the formatter reads columns Task 1 is the first code to
ever write.

**Canon-referral breadcrumbs** (prohibition probe, Stage 2): webhook-token-in-logs and
hostile-`DISCORD_WEBHOOK_URL` SSRF are canon security items — covered by `/gsd-secure-phase`
and carried as `T-05-01`/`T-05-03` in plan 05-01's threat model; not minted as prohibitions
here.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| MusicBrainz / Deezer content -> Discord embed | Community-editable `title`, `artist_name`, and `release_type` snapshot values are rendered into a message |
| `events.external_id` -> embed URL | A stored external id is interpolated into a link the user will click |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-02 | Tampering | `internal/notifier/format.go` field population | medium | mitigate | Every community-sourced string is rune-truncated to Discord's documented field limits before marshaling (title 256, field value 1024). This is both correctness (an oversized field makes Discord reject the whole request, silently dropping a real notification) and the render-layer handling Phase 4 deferred from `AR-04-01`/`AR-04-04`. |
| T-05-06 | Tampering | `internal/notifier/format.go` link construction | medium | mitigate | Embed URLs are built by escaping `external_id` into a fixed path template with `url.PathEscape`; free-text snapshot fields (`title`, `artist_name`) are never interpolated into any URL. A test asserts a URL-unsafe external id is percent-escaped and the result still parses. |
| T-05-07 | Spoofing | Misleading embed link text | low | accept | A community-editable title next to a legitimate link can read misleadingly, but Discord embeds do not parse `@mentions` and do not auto-unfurl a nested link, so the blast radius is a visually odd field rather than an active exploit. Accepted exactly as Phase 4 accepted the same class at the storage layer (`AR-04-01`/`AR-04-04`). |
| T-05-08 | Information Disclosure | `release_type` normalization drift | low | accept | Storing the filter's own normalized value keeps stored data inside the `detectableReleaseTypes` vocabulary; a drifting upstream value renders as an unexpected label, never as an authorization decision — `release_type` is display-only in this phase. |
