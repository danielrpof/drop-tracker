# Roadmap: drop-tracker

## Overview

drop-tracker starts from an empty repo and builds outward from the data layer: a Postgres schema, config, and health-checked service skeleton first, then a fully tested watchlist CRUD API, then rate-limited MusicBrainz/Deezer clients with live search, then the detection engine that diffs poll results into new-release/guest-feature/deluxe events, then Discord notifications for those events, then the React UI that ties watchlist management and release history together, and finally the single-image containerization and full GitHub Actions CI/CD pipeline (lint, test, security scan, SBOM, semantic versioning, ghcr.io publish) that is the actual point of the project. Each phase produces something a user (or operator) can directly observe working before the next phase builds on it.

**v1.2 Cleanup & Display Fixes** picks up from a shipped, hardened v1.1 and closes the two items left in the backlog plus one further round of user-visible display bugs found during everyday use, without adding new capability: `CoverArt.tsx`'s stale-placeholder bug (never resetting on a changed `src`), Deezer-fan-count-based search popularity ranking with a MusicBrainz country-code disambiguation fallback (absorbing backlog Phase 999.1), and three History-tab display/data bugs — missing release dates, missing guest-feature album art, and MusicBrainz artist art never rendering — the last closed with a new hand-rolled `internal/artistart` matcher wired into both add-time and a cooldown-bounded startup backfill sweep (absorbing backlog Phase 999.2).

## Phase Details

### Phase 12: Cleanup: CoverArt Reset & Search Popularity Ranking

**Goal**: Close two loose ends left after v1.1 closes: (1) `CoverArt.tsx`'s image-load-error state never resets when `src` changes on a retained component instance, so a component that once failed to load keeps showing the placeholder forever even if a later `src` would succeed — flagged in `.planning/v1.1-MILESTONE-AUDIT.md` as pre-existing, non-blocking tech debt; (2) promoted from backlog Phase 999.1 — search results aren't ranked by popularity and same-named artists (e.g. multiple "Drake"s) are hard to disambiguate, since MusicBrainz's search API doesn't rank by popularity and its `disambiguation` field is often blank.
**Depends on**: Phase 11
**Requirements**: No REQUIREMENTS.md IDs mapped — `12-CONTEXT.md`'s locked decisions D-01 through D-10 are the authoritative scope, traced through each plan's `requirements` field
**Plans**: 3/3 plans executed

Plans:
**Wave 1**

- [x] 12-01-PLAN.md — CoverArt error-state reset on `src` change (`useEffect([src])`, not a `key` remount) plus its regression test (D-01, D-02)
- [x] 12-02-PLAN.md — Deezer fan-count (`NbFan`) capture and a stable descending popularity sort inside `internal/deezer`'s client itself, ties broken by Deezer's own relevance order (D-03, D-04)

**Wave 2** *(blocked on Wave 1 completion)*

- [x] 12-03-PLAN.md — MusicBrainz `country` field surfaced end-to-end as a disambiguation fallback (nullish-coalescing after `disambiguation`), plus guardrail tests proving MusicBrainz's own result order is preserved and Deezer's fan count never crosses the HTTP boundary (D-05 through D-10)

Notes: All ten locked decisions (D-01–D-10) closed with automated coverage; no manual UAT gaps. Deezer's popularity sort and MusicBrainz's country fallback deliberately stayed on separate paths — no ranking logic was added to the MusicBrainz client itself (D-06/D-07), and `NbFan` is asserted absent from the `SearchArtist` wire struct (D-05).

### Phase 13: Fix History Dates, Guest-Feature Art & Artist Art

**Goal**: Resolve three outstanding display/data bugs users are still hitting after Phase 12: (1) History tab entries (single/feature/deluxe) don't show a release date next to each item; (2) guest-feature release cards don't show album art even though new-release cards do; (3) artist art from MusicBrainz still doesn't render, despite Deezer artists being linkable to MusicBrainz artists so Deezer pictures could be used. Absorbs backlog Phase 999.2 (Deezer artist-art backfill) where it overlaps with bug 3.
**Depends on**: Phase 12
**Requirements**: No REQUIREMENTS.md IDs mapped — `13-CONTEXT.md`'s locked decisions D-01 through D-09 are the authoritative scope, traced through each plan's `requirements` field
**Plans**: 3/3 plans executed

Plans:
**Wave 1**

- [x] 13-01-PLAN.md — New `internal/musicbrainz.ReleasesForRecording` single-entity lookup sources guest-feature `release_date`/`cover_art_url` with a precision-aware earliest-date rule, a no-releases fallback, per-recording error isolation, and a 20-lookup-per-cycle cap; `EventCard.tsx`'s `GuestFeatureBody`/`DeluxeChangeBody` both render the release date (D-01–D-05)
- [x] 13-02-PLAN.md — New `internal/artistart` package: `Matcher.Match` (strict close-name equality + guarded shared-album-title tie-break, fail-closed on any ambiguity), the `ArtMatchAttemptedAt` cooldown migration and its two sqlc queries, and the `ActivityGate` concurrency primitive (D-06, D-08, D-09)

**Wave 2** *(blocked on Wave 1 completion)*

- [x] 13-03-PLAN.md — Wires the matcher into both call sites: synchronous add-time resolution behind an optional `watchlist.Service` dependency (bounded 8s timeout, never fails the add), and a cooldown-bounded, activity-yielding startup backfill sweep; `cmd/server/main.go` reordered so `mbClient`/`dzClient` precede `store`, with one shared `Matcher`/`ActivityGate` wired into both (D-06, D-07, D-09)

Notes: Nine locked decisions (D-01–D-09) closed with automated coverage. ## Milestone Summary

**Decimal Phases:** None this milestone.

**Key Decisions:**

- `useEffect([src])` reset over a `key={src}` remount for CoverArt (D-01) — keeps the fix scoped to one component with zero call-site changes across History/Watchlist/search rows
- Deezer popularity sort lives inside `internal/deezer`'s client, using `slices.SortStableFunc` (not `SortFunc`) so ties — the common case, since an unmatched artist decodes `NbFan` to zero — preserve Deezer's own relevance order instead of being scrambled
- MusicBrainz gets no new ranking logic; its `country` field is surfaced only as a disambiguation-label fallback, never a sort key (D-06/D-09) — popularity (`NbFan`) is explicitly excluded from any UI-facing signal
- Strict close-name equality + guarded shared-album-title tie-break for MusicBrainz→Deezer artist-art matching, fail-closed on any ambiguity — a wrong-artist photo misrepresents identity and was judged worse than no photo (Phase 13's own threat model, T-13-06)
- A shared `ActivityGate` priority-yielding primitive coordinates add-time matching and the backfill sweep against one rate budget, rather than giving the backfill sweep its own independent budget that could push combined MusicBrainz traffic over its real ~1 req/sec ceiling

**Issues Resolved:**

- Three code-review warnings found during Phase 13 UAT verification (`earlierDate` panic on a short date, `Backfill.Stats` double-increment, `Service.Add` `ActivityGate` leak on panic) — all fixed in place with regression tests rather than deferred

**Issues Deferred:** None.

**Technical Debt Incurred:** None recorded — both phases closed with all locked decisions covered by automated tests and no open UAT gaps.
